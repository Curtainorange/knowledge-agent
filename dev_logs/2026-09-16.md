## 备注

- **文档的读者决定了它的写法**：同一份内容，「给开发者看」和「给评审方看」是两种文档。
  前者的价值在于**降低上手成本**（环境怎么搭、改哪儿、什么顺序练手），
  后者的价值在于**论证设计合理性**（为什么这样设计、约束如何保障、需求如何覆盖）。
  本次改动不是「删内容」，而是**换视角重写**——同样讲解耦，前者说「加新能力改这 2 个文件」，
  后者说「扩展代价经量化验证仅涉 2 处注册式改动，构成解耦有效性的判据」。
- **删除操作指引不等于删除信息**：原 §2 的「五分钟跑起来」被删除，但环境搭建与启动
  并非无用信息——它以「§12.4.1 安装与启动」的正式形式并入部署设计，信息未丢失、
  定位更准确。**同一信息在不同章节的归属，本身就是专业性的体现。**
- **修订说明要写「为什么改」而非只写「改了什么」**：本次 V3.1 修订说明明确写出
  「由开发指引改为设计目标与约束」，使评审方理解版本演进的意图，而非只看到条目变化。
- **删掉的开发流程内容并未废弃**：提交规范、DoD、检查清单中真正有价值的约束
  （依赖方向六条、交付质量十条、合规检查十一条）全部保留，只是去掉了团队协作的操作细节。
  内部流程留在 `dev_logs/`，设计约束留在设计文档——**受众分离**。
- **旧版 HTML 的处理原则**：用户重命名的 `系统设计文档(修改）.html` 虽已被新版取代，
  但属于用户主动重命名的文件，**未擅自删除**，列入待办待确认。
  对用户操作过的文件，即使判断为冗余，也应先确认再动。
- **格式转换的「隐性丢失」是最难自查的一类问题**：源文件在原生环境里完全正常
  （浏览器会解析 CSS），只有在跨格式后才暴露。根因在于**转换器只认识目标格式的
  显式表达**——CSS 是浏览器世界的隐式契约（选择器 + 继承 + 层叠），
  而 docx 需要 OOXML 的显式声明（`w:tblBorders`）。
  经验：**跨格式交付的文档，关键样式要用「目标格式也认识」的显式写法承载**，
  不能只依赖 CSS。本例中 HTML 的 `border` 表现属性恰好是两端都认的交集。
- **诊断先分「结构」与「样式」两层，不要一上来猜内容丢失**。
  本次第一步查 `w:tbl` = 77（结构完好）→ 立刻排除「表格没被转换」「内容丢失」，
  范围收敛到「样式未映射」；第二步查 `w:tblBorders` = 0 即定位根因。
  若顺序反过来（先怀疑内容），会在错误方向上耗费大量时间。
- **度量方式错了，会制造出并不存在的「问题」**：本次用 `<w:t[^>]*>` 提取正文，
  误匹配 `<w:tblPr>` 等标签，得出「修复后文字多了 4.3 万字」的假结论，
  险些把一次零改动的修补误判为「改坏了内容」。
  **出现异常数值时，先核对度量口径，再怀疑被测对象。**
- **同一问题应同时提供「治标」与「治本」两条路径**：治标（修补现有 docx）
  让用户立刻可用，治本（修 HTML 生成逻辑）防复发。
  **只做治本，用户还要再转换一次；只做治标，换个文档又踩同一个坑。**
- **删除操作的结果必须独立核验，不能只信 API 返回值**：本次调用
  `SHFileOperation` 返回错误码 2（`ERROR_FILE_NOT_FOUND`），看似失败；
  但独立核验发现文件**确实已进入回收站**（字节数与删除时间均吻合）。
  若只看返回值，会得出「删除失败」的错误结论，进而重复操作或误报给用户。
  **凡破坏性操作，都以「最终状态核验」为准，不以「调用返回」为准。**
- **个人目录的删除一律走回收站，给自己留退路**：
  Windows 用 `SHFileOperation` + `FOF_ALLOWUNDO`（等价于资源管理器「删除」），
  不使用 `rm` / `del`。核验方式：直接解析 `C:\$Recycle.Bin\<SID>\$I*`
  元数据文件（记录原始路径、大小、删除时间），并确认对应的 `$R*` 内容文件存在。
  本次扫描 332 条回收站记录，定位到目标文件并确认其可还原。
  （PowerShell 的 `Shell.Application` COM 对象会被本机安全策略拦截，
  改用直接读取回收站文件系统的方式，无需 COM。）
