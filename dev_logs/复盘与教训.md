## 一、数据库与 ORM

### 1. L2 Conflict 表未注册（09-12）

**现象**：`app/domain/models/conflict.py` 文件存在，但 `Base.metadata.sorted_tables` 里没有
`conflicts`；`init_db()` 与 `alembic env.py` 都看不到这张表。任何
`ConflictRepository.create()` 首次写入会撞 `OperationalError: no such table: conflicts`。

**根因**：`app/domain/models/__init__.py` 把 `Conflict` 写进了 `__all__`，却没
`from app.domain.models.conflict import Conflict`。**`__all__` 只控制 `from ... import *`
的导出，不会触发模块加载**，SQLAlchemy 也就发现不了这个 ORM 类。

**防回归**：`tests/test_conflict.py` 加 `test_conflicts_table_is_registered`（断言 metadata
里能找到 `conflicts` / `claims`），以及 pair_key 无序、仓储真实读写、越权防护三项。

**教训**
- **`__all__` 不触发 import**：这是 SQLAlchemy declarative 体系下最容易踩的坑。
- **死代码检测不到 bug**：旧用例没碰到 Conflict 写路径（仓储处于「只读不写」态），
  必须主动写测试才能暴露。
- **commit 描述要核对落盘**：feature commit 说加了模型/迁移，提交时务必 `git status` 确认已暂存。

### 2. SQLite schema 漂移 —— create_all 不给已有表加列（09-13）

**现象**：用户报「三个页面打不开」，实为**所有需登录页面都进不去**：注册/登录 500，
报 `OperationalError: no such column: users.token_version`。

**根因**：`init_db()` 用 `Base.metadata.create_all`，它只创建**缺失的表**，
**不会给已存在的表加新列**。P0 迭代期间给模型加的新列（`users.token_version` /
`cost_logs.prompt_version` / `claims.topic` 等）在老 dev.db 里一直缺失。

**为什么没早点发现**：pytest 用内存库 + `create_all`，每次都是最新 schema，全绿；
但真实 dev.db 是**历史累积的库**。典型的「测试绿、真实环境崩」。

**修复**：`init_db` 增 `_ensure_sqlite_columns()`（启动时对比模型列 vs 实际列，缺列自动
`ALTER TABLE ... ADD COLUMN`）；`tests/test_db.py` 4 项覆盖。

**教训**
- **测试环境 ≠ 真实环境**：前者每次重建最新态，后者是历史累积态；加列/改 schema 必须有
  一条「老库升级」路径（自愈 或 alembic），否则测试永远拦不住这类问题。
- 「建表路径不一致 = 环境相关 bug」，与第 1 条同源。
- 这类「打不开」先看后端日志的 `OperationalError`，别在前端 JS 上浪费时间。

### 3. 仓储按 created_at 取「最新」的同秒写穿（09-13）

**现象**：L4 测试首次运行即挂——同一秒内 `generate_plan` 写 v1、紧接
`decide_adjustment` 写 v2，但 `latest_for_user` 仍返回 v1。

**根因**：两层叠加——
1. SQLite `CURRENT_TIMESTAMP` 默认精度是**秒**，同秒内多次写入时间戳相同；
2. 备份排序键 `id` 是 UUID 字符串，**字典序 ≠ 创建时间序**。

**修复 / 原则**
- 同主体的多次写（计划版本 / 文档快照 / 令牌版本）改用**主键版本号**排序；
- **时间戳只做平局打破，不做「最新」判定**。

**教训**
- 测试要主动造「同秒写」场景，而不是靠调试时「刚好撞上」。
- 时序假设 + 架构假设，默认都不要信。

### 4. 主键 default 生成的 id 与 service 层 id 分叉（09-14）

**现象**：给书籍加插图功能后，图片端点 404——`book.id`（主键）与 `file_path` 里的
`book_id` 是**两个不同的 uuid**。

**根因**：`BookService.upload` 先 `book_id = str(uuid4())` 用于生成文件路径，随后调
`BookRepository.create(...)` 时**没传 id**，而 `Book` 模型主键是
`default=lambda: str(uuid4())`，ORM 又生成了一个新 uuid。

此前没暴露，是因为没有「按 book.id 反查 file_path 文件」的需求——图片端点一加
（`Path(book.file_path).parent / book.id / "images"`），分叉立刻炸成 404。

**修复**：`BookRepository.create` 增加可选 `book_id` 参数，`upload` 显式传入，让主键 id
与文件路径 id 一致。

**教训**
- **「主键 default 生成的 id」与「service 层预先算好的 id」会静默分叉**。凡 id 既要当主键、
  又要拼文件路径 / 外部引用 / 幂等键，主键 id 必须由调用方显式传入。
- 这类 bug「平时不炸、一有反向引用就炸」；加功能时尤其警惕「之前只是碰巧没用到」的字段。

## 二、接口 · 鉴权 · 前端

### 5. 错误提示 —— 框架默认格式不等于给人看的格式（09-13）

**现象**：输入不合规信息时，登录/注册页提示区显示一整串英文 JSON
（`[{"type":"string_too_short","loc":["body","username"],...}]`）。

**根因**：FastAPI 默认把 pydantic **原始错误数组**透出（英文 msg + loc/ctx）；
前端 `CC.api` 对非字符串 `detail` 直接 `JSON.stringify` 显示。

**修复**：后端注册全局 `RequestValidationError` handler，把校验错误翻译成中文短句
（字段中文名 + 错误类型映射，多条「；」连接）；前端 `CC.api` 增 `errorText()` 兜底。

**教训**
- **错误信息是界面的一部分，不是日志的附属品**：面向用户的错误必须在服务端翻译成人话。
- 全局 handler 一次覆盖所有端点，比在每个响应模型里写提示更省心。
- 排查「界面有问题」按层推进：后端 API → 静态资源 → JS 语法 → CSS 类 → **提示文案**；
  前四层全通时，第五层（UX 细节）才是真相。

### 6. `<img>` 打不开 —— 浏览器直发的请求带不了 Authorization 头（09-14）

**现象**：epub 插图上传成功、正文里有 `[[IMG:name]]` 占位符，但阅读器里是裂图。

**根因**：`<img src="...">` 是**浏览器自己发起**的请求，不是 XHR，**无法携带自定义请求头**
（token 在 localStorage，不在 cookie）；而图片端点沿用 `get_user_id`（只认
`Authorization: Bearer`）→ 一律 401。

**修复**：新增 `deps.get_user_id_flexible`——Header 缺失时接受 `?token=<access token>`，
两类来源同走 `_authed_user`（鉴权强度不变，无 token 仍 401）；前端 `<img src>` 追加 `?token=`。

**教训**
- **凡「前端 `<img>` / `<video>` / `<a download>` 直接加载的后端资源」，鉴权都不能只靠
  `Authorization` 头**。两种解法：①查询参数 `?token=` 兜底；②前端 fetch → blob → objectURL。
- 设计鉴权时提前问：**「这个端点的请求是谁发出的？」** XHR 与浏览器原生加载是两条通道，
  鉴权方式必须都能覆盖。

### 7. 会话过期的 401 被「auth 前缀」挡掉，页面烂成空壳（09-15）

**现象**：读完书退出来，知识库列表全空（「共 0 条」）、顶栏用户名不显示、
点「退出」毫无反应。用户报「记录全部消失」——但数据库里一条没少。

**根因**：`app.js` 用「路径以 `/api/v1/auth/` 开头则不跳转登录页」来避免把
「密码错误」误报成「登录过期」。但**会话探针 `/api/v1/auth/me` 也在这个前缀里**，
而它的 401 恰恰就是「登录已过期」。于是令牌一过期：

    api() 既不跳转也不报错 → requireAuth 静默返回 null → boot() 直接结束
    → 列表停在静态默认值「共 0 条」、用户名从未写入、退出按钮从未绑定事件

**三个症状同源**。触发条件很常见：`access_token_minutes=120`（2 小时），
读一本书动辄一两小时，「读完书退出来」必撞。而前端把 `refresh_token` 存进了
localStorage **却从不使用**，access 一过期就只能强制重登。

**修复**
- 401 跳转改为**白名单**：只排除 login / register / password / account / refresh
  这些「401 表示凭证本身不对」的端点；`/auth/me` 归入正常跳转。
- **用上 refresh token**：401 时先静默续期再原样重试一次（并发共享同一次刷新），
  access 过期对用户彻底无感。
- `requireAuth` 在会话校验**之前**就渲染顶栏并绑定退出按钮 —— 校验失败也退得掉。
- 续期也失败才跳登录页，带 `msg` 原因 + `next` 回跳目标。
- `renderTopbar` 幂等（此前重复调用会重复绑定退出，实测绑 3 次）。

**防回归**：新增 `tests/test_web_auth.py`（源码不变量 4 项 + Node 运行时行为 1 项）；
`tests/js/session_behavior.js` 用 `vm` 跑**真实 `app.js`**（stub fetch/localStorage/location）。
**拿旧版 app.js 跑同一套断言能复现全部症状**（用户名空白 / 退出绑定 0 次 /
refresh 失效时也不跳转），新版全绿 —— 反向验证了测验确实抓得住这个 bug。

**教训**
- **401 的「不回跳」规则要用白名单，不能用路径前缀**。判据是
  「**这个 401 是不是在说『你还没登录』**」：login/register/password 的 401 说的是
  「凭证不对」（原样报错），`/auth/me` 的 401 说的才是「登录已过期」（跳登录页）。
- **「静默失败」比「报错」危险得多**。真正的伤害不是令牌过期（很常见），
  而是过期后**既不跳转也不提示**，直接渲染成死壳 —— 用户只会得出
  「我的数据没了」这个错误结论。凡「校验失败就 return」的写法都要追问：
  **失败态用户看得见吗？关键操作（退出）还能用吗？**
- **存了不用的凭证是隐藏的技术债**：`refresh_token` 从 P0 就写进 localStorage
  （`refresh_token_days=7`）却从未被读取。这类「只写不读」的字段平时无害，
  一到 access 过期就暴露「本可无感续期，却只能强制重登」。
- **「页面一片空」与「数据丢了」观感相同、排查路径完全不同**：第一步永远是
  确认「数据在不在库 / 后端接口正不正常」，再查前端。

## 三、环境与进程

### 8. 排查「功能全崩」先确认你看的是不是同一个服务器（09-13）

**现象**：注册报「服务器内部错误 HTTP 500」，此前还有「三个页面打不开」。

**排查转折**：本地起最新代码服务器复现不出 500，代码/测试/DB 都正常 → 扫端口发现
**8000 端口另有一个服务器在跑**（旧进程）→ `curl /openapi.json` 对比：
8000 只有 17 个端点，缺 L3/L4/L5/推送/偏好/账号安全全部端点。

**根因**：浏览器访问的是 **8000 上那个从未重启的旧代码进程**。与代码、数据库无关，
纯粹是「改了代码没重启服务器」。

**教训**
- **本地复现不出、代码与测试全绿时，先确认「你和服务端是不是同一个版本」**：扫端口 +
  比对 `/openapi.json` 端点清单，是最快的判定手段。
- 改完代码要重启服务器。

### 9. 「重启了却还是旧行为」—— `--reload` 的僵尸子进程继承 socket（09-14）

**现象**：改完代码（新增页面路由），重启服务器后新路由仍持续 404，反复 kill + 重启都不解决。

**排查转折**：`netstat -ano` 拿到监听 PID（10144）→ `tasklist` 查不到该 PID，**但端口仍可连接**
→ 用 PowerShell 列 python 进程，发现 `python.exe` 2108 的 `ParentProcessId` 正是 10144，
命令行是 `multiprocessing.spawn ... spawn_main(parent_pid=10144)`。

**根因**：`uvicorn --reload` 用 multiprocessing spawn 起 worker：父进程（reloader）是 10144，
worker 子进程是 2108。**杀掉父进程后，子进程继承并继续持有监听 socket**，用旧代码继续
响应——所以「重启」是假的。

**修复**：kill 真正持有 socket 的子进程，端口才释放；**改用不带 `--reload` 的启动方式**。

**教训**
- **`--reload` 的进程树不能按单个 PID 随便杀**。判断手法：**netstat 有监听、tasklist 查不到
  该 PID → socket 被子进程继承**。
- 开发期若要「改完立刻稳定生效」，宁可不带 `--reload`（确定性 > 便利性）。

## 四、工程方法

### 10. 「后端完成」不等于「功能完成」—— 收口前反查前端引用（09-14）

**现象**：收口复查发现 L5 归因诊断、推送通知、推送偏好三块能力 **API 全绿、编排全在、
测试全过，但前端零引用**——`/api/v1/l5/*`、`/api/v1/push/jobs`、`/api/v1/preferences`
没有任何页面调用。日志里标了 `[x] 已完成`，但那只代表后端完成，用户根本用不到。

**排查方法（可复用）**：脚本交叉核对两遍——① 扫 `web/*.html` 里 `CC.api('METHOD','/api/...')`
的全部调用；② 取后端 `/openapi.json` 端点清单。两边一比，零引用的 API 立刻现形。

**修复**：新增 `web/l5.html` / `web/notify.html`，首页功能卡片 6 → 8，业务页导航补入口；
`test_web` 加「新页隔离」与「导航入口覆盖」测试防再漏。

**教训**
- **判定「某能力已完成」时，必须拿 API 清单反查前端引用，确认有入口才算收口**。
  API 全绿 + 测试全过，仍可能用户完全用不到。
- 适用于任何「能力层」与「接入层」分离的项目：**测试覆盖的是能力，入口覆盖的才是用户**。
- 复查时用脚本交叉核对，比人工过一遍可靠得多。

### 11. 「数据没了」的排查顺序（09-15）

**现象**：用户报「阅读的书籍和知识记录存档全部没有了」。

**排查四步**（本次结论：数据完好，只是登录的账号不是存数据的那个）：
1. **库文件在不在** —— 列项目下所有 `.db`，确认 `dev.db` 存在且内容正常；
2. **服务器连的是哪个库** —— 注册一个「探针账号」，确认它落到目标库（验证后立即删除）；
3. **数据挂在哪个 user_id 上** —— 按 user_id 分组统计各账号的 books / knowledge / events；
4. **用户登录的是哪个账号** —— 数据按 user_id 隔离，**换账号登录就是一片空白**。

**教训**
- 数据按 user_id 隔离的项目里，「数据没了」很可能是「**换了账号**」，与数据安全无关。
- **排查数据丢失类问题必须先声明只读**（`sqlite3 'file:x.db?mode=ro'`）；确需验证
  「服务器 → 库」映射时，用一次性探针账号并立即删除。
- 手法留档：`PRAGMA table_info(t)` 探列、按 user_id 分组 `count(*)`、探针账号验证库归属。

### 12. 分桶聚合不能拿 key 字符串当排序键（09-15）

**现象**：给阅读日志加「按周 / 按月」视图时，若按 key 字符串排序，
`2026-W01` 与 `2025-W52` 的顺序会错乱。

**做法**：额外存「桶内最新日期」作为排序键，与展示用的 key 解耦。

**教训**：**展示标识 ≠ 排序依据**。凡把时间压成字符串当标识（ISO 周、`YYYY-MM`），
排序都要另留一个真实时间字段。

### 13. 滚动位置恢复要等布局稳定（09-15）

**现象**：阅读器「只恢复到章首附近」，而不是上次读到的位置。

**根因**：插图会把正文容器撑高，而滚动位置是在**图片加载完成前**按比例算出来的，
算出的 `scrollTop` 必然偏前。

**修复**：图片 `load` / `error` 后再按同一比例重算一次；同时**去掉这类图片的
`loading="lazy"`**——lazy 会让 `complete` 长期为假，校准回调根本不会触发。

**教训**：任何「按比例恢复位置」的逻辑，都要考虑**异步资源加载导致的布局变化**，
在布局稳定后补一次校准。

### 14. 视觉改动要先确认方向（09-14）

**现象**：用户说「背景不要太单调」，于是把背景改成「网格纹理 + 四角彩色光晕」多层叠加，
结果用户反馈「更丑了、不要网格」，只能整个 revert。

**教训**
- **审美是主观的**：涉及整体观感的改动，要么先给方案/选项让用户选，要么只做单点微调，
  不要一次性叠多层新元素。
- **「更丰富」≠「更好看」**：网格 / 纹理这类铺满全屏的叠加元素极易变成噪音。
- 用户说「单调」时，想要的可能是「更精致」，而不是「更花」。
- 改得不好看时，**先整体回退到用户已知可接受的状态**，再重新对齐期望。

### 15. 依赖注入的默认值是 None → 生产路径静默降级（09-21）

**现象**：从微信读书同步进来的 3 条知识，在知识库里全显示「未向量化」
（`embed_status=pending`），语义检索命中不到；而站内书籍摘录的 8 条都是 `embedded`。

**根因**：`WeReadSyncService._persist` 把 `self._embedding`（构造参数默认 `None`）直接交给
`IngestionService`，而后者只在 embedding **非 None** 时才计算向量：

```python
svc = IngestionService(self._session, self._embedding)   # 端点从不注入 → None → 不算向量
```

对照 `books/service.add_note` 的写法是 `IngestionService(self._session, build_embedding())`，
即「不注入就自己建」；微信读书这条链路漏了这一步。

**修复**：`_persist` 在 `self._embedding is None` 时调用 `build_embedding()`；
另加 `scripts/reembed_pending.py` 给历史 `pending` / `embed_failed` 条目补算（本次补了 3 条）。

**防回归**：同步用例断言「条目必须 `embed_status == "embedded"` 且 `embedding` 非空」。

**教训**
- **可选注入的默认值是 `None` 时，生产路径必须显式构造默认实现**，否则等于给功能装了一个静默开关。
- 这类 bug **测试最难发现**：单测不注入、生产也不注入，两边都走 `None` 分支；
  而断言只检查「条目写进去了」——**必须额外断言那条最容易被跳过的副作用**（这里是向量）。
- 它是靠「用户在界面上看到异常状态」才暴露的。**把状态字段暴露到 UI**（`embed_status` 直接展示）
  比埋在日志里管用。

### 16. 换模型供应商后，最危险的是「不报错、只悄悄变行为」的地方（09-22）

**现象**：把模型层从 DeepSeek 换成小米 MiMo 后，代码层面几乎没报错（抽象层做得好），
但接连冒出三处「静默失效」，全是脚本/工具类，**没有一处抛出异常**：

1. `scripts/smoke_agent.py` 声明「全程不触网、不碰真实库」，靠 `settings.deepseek_api_key = ""`
   来强制走 `MockProvider`。但 `model_provider` 的优先级是 `mimo > deepseek > mock`——
   本机 `.env` 配了 MiMo 之后，这个离线验收会**静默变成真机联调**（花钱 + 丢掉确定性）。
2. `scripts/smoke_l2.py` / `smoke_l3.py` 硬断言 `model_provider == "deepseek"`，
   于是「真机冒烟」在换供应商后必然失败，**报的却像是环境没配好**。
3. `scripts/check_cost.py` 把「非 DeepSeek」一律当成「没配 key 的 Mock」，
   打印「无法校准计费」——与事实相反的提示，会把人引向错误的排查方向。

**根因**：这些位置都把「当前供应商是谁」**写死**了，而不是**跟随配置**。
它们在单一供应商时期永远是「对」的，所以既不会被测试发现，也不会被 code review 发现。

**修复**：断言改成供应商无关（「非 Mock 即可」）；`smoke_agent` 两个 key 都清；
`check_cost` 按供应商分支取价、并把「MiMo 是否有缓存折扣尚未核实」降级为 INFO 而不判失败
（**未验证项不该伪装成失败项**）。

**教训**
- 「换配置就能换供应商」只说明**抽象层**做对了，不说明**周边**做对了。
  真正昂贵的不是接新供应商，是**找齐所有假设了旧供应商的地方**。
- **会报错的地方最安全，不报错的地方最危险。** 这三处的共同形态是「行为悄悄变掉」：
  离线变联机、断言变成了错误的提示、提示指向了错误的方向。所以换供应商之后
  **必须真机跑一遍每个 `smoke_*`**，并且专门看**降级路径**（`state=degraded` 这类）——
  降级不报错，只在内容上少东西，最容易整体漏掉。
- **常量（模型名）以接口实测为准，别信资料。** 这次按第三方资料把模型名写成
  `mimo-v2-flash`，真实调用报 `400 Unsupported model`；`GET /v1/models` 才拿到真名
  `mimo-v2.6-flash`。资料会过期，`/v1/models` 不会。
- 顺带一条：**「未验证」和「失败」必须分开**。MiMo 的缓存命中字段实测恒为 0，
  但「它到底有没有这个能力」我们并不知道——把它判成 FAIL 会让人去修一个可能不存在的问题。

**防回归**：断言全部改为跟随配置（`!= "mock"`），并在注释里写清
「两个 key 都要清，因为优先级是 mimo > deepseek > mock」，避免下次又被改回去。

### 17. 「优先级」被误当成「容错」：回退写在待办里躺了两轮（09-22）

**现象**：`MIMO_API_KEY` 非空就恒选 MiMo（`model_provider = mimo > deepseek > mock`），
看起来像「MiMo 优先、DeepSeek 兜底」。但兜底只发生在**选供应商**那一步（配置层）；
MiMo 在运行期失败时——模型名错 400、鉴权失败 401、余额或限流耗尽——**直接抛错**，
用户看到的是「这个能力不能用」。这条缺口 09-22 上午就写进了待办，当天收尾时才修。

**根因**：把「优先级」误当成「容错」。`mimo > deepseek > mock` 描述的是
**配置齐全时选谁**，不是**选中的那个坏了怎么办**。两者在代码上长得几乎一样
（都表现为"有 MiMo 就用 MiMo"），所以写的人、读的人、review 的人都会默认「已经容错了」。

**修复时踩到的两个「假回退」陷阱**——链搭好了、代码跑通了、但回退其实必然失败：

1. **模型名**：策略表里 `strat.model` 是主供应商的模型名，直接发给备用供应商会得到
   `400 Unsupported model`，回退第一步就死。改用各 Provider 自己的 `default_model`。
2. **请求约束**：`response_format` 是按主供应商的能力位算出来的，备用供应商不支持时
   会**直接拒收**（DeepSeek 在 reasoning=on 下正是这种）。约束必须按实际要用的供应商重算。

**另一处必须刻意设计的地方**：**Mock 不能进回退链**。没有 KEY 时整链退化为 Mock 是对的；
但**有 KEY 时失败绝不能回落 Mock**——Mock 返回的是确定性、看起来完全正常的假内容，
「模型挂了」会被伪装成「模型答了」，比直接报错危险得多。

**教训**

- **「优先级」不等于「容错」。** 判据很干脆：把主供应商的 key 改错，系统还能不能出结果？
  不能，就说明回退只活在配置层。
- **回退必须同时换「模型名」和「请求约束」**，否则链是通的、回退是死的。
  防回归做法：给「支持能力位 → 不支持」和「不支持 → 支持」两个方向各写一条用例。
- **验证回退的唯一诚实办法是故意让主供应商坏掉。** 只跑正常路径永远测不到回退分支，
  而回退恰恰是「只在出事时才走」的那一半代码。做法：临时把 `MIMO_MODEL` 指向一个
  不存在的模型名，一次调用即可确认真的切到了 DeepSeek（本次实测：MiMo 400 →
  日志「主供应商失败，回退到 DeepSeekProvider」→ 实际服务模型 `deepseek-flash`、回包正常）。
- 一般化：**凡是「只在异常路径上生效」的机制，验收标准必须是「人为制造那个异常」**。
  降级、回退、重试、熔断都属于这一类——它们的代码平时根本不执行，跑一万次正常流程
  也覆盖不到。
