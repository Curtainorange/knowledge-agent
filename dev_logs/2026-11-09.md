## 更正（09:35）：真正的故障在远端，我上一轮查错了对象

用户实际访问的是 **`http://10.100.128.129/cognition/`**，实测返回：

```
HTTP/1.1 502 Bad Gateway
Server: nginx/1.30.6
```

**502 是 nginx 自己产生的**，说明 nginx 活着、只是转发不到上游。而 `deploy/nginx/cognition.conf`
里写得很明确：`proxy_pass http://127.0.0.1:8010/` ——**上游是 8010，不是我上一轮折腾的本机 8000**。

所以整件事跟本机那台开发机没关系：

| | 开发机（本机） | 线上服务器 |
|---|---|---|
| 地址 | 127.0.0.1:8000 / 10.128.90.206:8000 | 10.100.128.129 → nginx `/cognition/` |
| 进程 | 手动起 uvicorn | 计划任务 `cognition-copilot`（SYSTEM / ONSTART） |
| 端口 | 8000 | **8010**，绑 127.0.0.1 |
| 代码位置 | `D:\知识学习智能体` | `E:\projects\renzhifujia` |

**教训（同类错误第二次犯）**：`复盘与教训` 第 8 条就是「排查『功能全崩』先确认是不是同一个服务器」。
这次用户说的是「服务器项目」，我却直接按本机 8000 排查，还用本机的截图证据下了结论。
**以后听到「服务器 / 线上 / 网址」，第一步先问或先确认访问地址与实际部署机器，再动手。**

## 服务器上的排查口径（只动本项目，不碰其他项目）

那台机器同时托管 RoamSync 等其它项目、共用同一个 nginx 80 端口。
**只允许操作计划任务 `cognition-copilot` 一个对象；不 reload nginx，不改任何 location。**

1. 任务在不在跑：`schtasks /query /tn "cognition-copilot" /fo list /v`
2. 上游在不在听：`netstat -ano | findstr ":8010 "`
3. 应用本身好不好：`curl.exe -s -o nul -w "%{http_code}\n" http://127.0.0.1:8010/health`
4. 为什么没起来：`type E:\projects\renzhifujia\logs\app.log`（NSSM/任务都往这里写，含轮转）

判据：任务 `Ready` + 8010 空 = 没启动（`schtasks /run` 即可）；任务 `Running` + 8010 空 = 起来了又挂，
看日志尾部 Traceback；8010 有 LISTENING 但 curl 不通 = 应用卡死，别急着 `/end`，先抓日志。

nginx 侧还有一份硬证据：`error.log` 里若有 `connect() failed (10061) ... while connecting to upstream`，
即直接证明「nginx 到头了、8010 没人接」，可以免掉上面 1–3 步的猜测。
