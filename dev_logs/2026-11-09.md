## 更正（09:35）：真正的故障在远端，我上一轮查错了对象

用户实际访问的是 **`http://10.100.128.129/cognition/`**，实测返回：

```
HTTP/1.1 502 Bad Gateway
Server: nginx/1.30.6
```

**502 是 nginx 自己产生的**，说明 nginx 活着、只是转发不到上游。而 `deploy/nginx/cognition.conf`
里写得很明确：`proxy_pass http://127.0.0.1:8010/` ——**上游是 8010，不是我上一轮折腾的本机 8000**。

所以整件事跟本机那台开发机没关系：

| | 开发机（本机） | 线上服务器 |
|---|---|---|
| 地址 | 127.0.0.1:8000 / 10.128.90.206:8000 | 10.100.128.129 → nginx `/cognition/` |
| 进程 | 手动起 uvicorn | 计划任务 `cognition-copilot`（SYSTEM / ONSTART） |
| 端口 | 8000 | **8010**，绑 127.0.0.1 |
| 代码位置 | `D:\知识学习智能体` | `E:\projects\renzhifujia` |

**教训（同类错误第二次犯）**：`复盘与教训` 第 8 条就是「排查『功能全崩』先确认是不是同一个服务器」。
这次用户说的是「服务器项目」，我却直接按本机 8000 排查，还用本机的截图证据下了结论。

## 服务器上的排查口径（只动本项目，不碰其他项目）

那台机器同时托管 RoamSync 等其它项目、共用同一个 nginx 80 端口。
**只允许操作计划任务 `cognition-copilot` 一个对象；不 reload nginx，不改任何 location。**

1. 任务在不在跑：`schtasks /query /tn "cognition-copilot" /fo list /v`
2. 上游在不在听：`netstat -ano | findstr ":8010 "`
3. 应用本身好不好：`curl.exe -s -o nul -w "%{http_code}\n" http://127.0.0.1:8010/health`
4. 为什么没起来：`type E:\projects\renzhifujia\logs\app.log`（NSSM/任务都往这里写，含轮转）

判据：任务 `Ready` + 8010 空 = 没启动（`schtasks /run` 即可）；任务 `Running` + 8010 空 = 起来了又挂，
看日志尾部 Traceback；8010 有 LISTENING 但 curl 不通 = 应用卡死，别急着 `/end`，先抓日志。

nginx 侧还有一份硬证据：`error.log` 里若有 `connect() failed (10061) ... while connecting to upstream`，
即直接证明「nginx 到头了、8010 没人接」，可以免掉上面 1–3 步的猜测。

## 线上故障结论（11-09 09:45 收口）

**现象**：`http://10.100.128.129/cognition/` → 502；任务 `cognition-copilot` 状态「就绪」，
`netstat` 无 8010 监听，`health=000`；日志最后一条停在 **11-07 08:00**（内容正常，无 Traceback）。

**恢复**：`schtasks /run /tn "cognition-copilot"` → `health=200`，网站恢复。

**排除掉的假设（每个都有证据）**：

| 假设 | 证据 | 结论 |
|---|---|---|
| 任务超时被终止（`ExecutionTimeLimit` 默认 3 天） | `/xml` 里**没有** `ExecutionTimeLimit` 元素 | 否 |
| 11-04 断电导致 | 断电在 11-04 10:04，日志活到 11-07 08:00 | 否，是另一次事故 |
| python 崩溃 | `Application` 日志 EventID 1000 只有 `SearchApp.exe`（Windows 搜索崩在 edgehtml.dll） | 否，噪音 |
| nginx 配置错 | 502 是 nginx 自身产生，`proxy_pass` 指向 `127.0.0.1:8010` 正确 | 否 |

**11-07 08:00 进程死亡的确切原因仍未知**。`findstr` 搜整份 10MB 日志时被 `写入错误` 打断，
证据不可信。**但根因不再是阻塞项**——真正的问题是「死了没人知道」：
任务的触发器只有 `ONSTART`（下次运行时间 `N/A`），进程一死就永久停在「就绪」。

**交付**：`deploy/watchdog.bat`（新建 `cognition-watchdog`，每 5 分钟探 `/health`，
非 200 就 `schtasks /run` 原任务）。**不碰原任务、不碰 nginx、不碰其他项目。**

三个关键设计决策，都是踩过坑才这么写的：

1. **用 `ping -n 13` 做延时，不用 `timeout`** —— 任务以 SYSTEM 身份跑，没有控制台，
   `timeout` 会直接报「输入重定向不受支持」，延时会静默失效、连续探测把服务打死。
2. **重启后仍不通就只记 `STILL DOWN`，绝不 `schtasks /end` 强杀** —— 强杀可能打断
   SQLite 正在进行的写事务，把「服务没起」升级成「数据损坏」。卡死要人来看日志。
3. **install 前两重校验**：同名任务已存在就拒绝（不覆盖别人的），
   被守护的任务命令行里必须含 `E:\projects\renzhifujia` 才继续（不守护别人的任务）。
   这与 `update.bat` 第 29 行的思路一致——**脚本本身必须能拒绝做错事**。

踩坑：`update.bat` 用 `/fo list`（不带 `/v`）去 `find` 任务命令行，但 `list` 输出**不含**
命令行（只有 TaskName / Next Run Time / Status），那条校验形同虚设。
本脚本改用 `/fo list /v`，输出里有 `Task To Run` 才能真匹配。
