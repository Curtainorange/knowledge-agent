## 备注

- **周期任务不需要调度器状态**：把「每周一次」表达成幂等键（含 ISO 周），worker 每轮无脑 ensure 即可，省掉 cron 表达式与「上次执行时间」的持久化。这个技巧同样适用于 L3 周简报。
- **幂等约束必须两条建表路径都声明**：模型声明 `unique=True` 覆盖 `create_all`（dev/测试），迁移里显式建唯一索引覆盖 alembic（生产）。只写一处会让另一条路径静默失去幂等——与 09-12「漏 import 导致表没注册」是同一类陷阱：**建表路径不一致 = 环境相关 bug**。
- **后台线程与测试天然冲突**：worker 一旦默认启动，测试断言会被后台写库搅乱。用 `worker_enabled` 开关 + 显式 `run_once()` 把执行时机交回测试，比让测试去「等」后台行为可靠得多。
- 前端踩到同一个 ASI 隐患家族（09-12 记录过）：`conflicts.html` 所有语句都带分号、不以 `[` 或 `(` 起行，并继续用 `node --check` 兜底。
- 提交消息里出现反引号会被 shell 当命令替换吃掉内容——本次已遇到并改用消息文件修正。**带反引号的 commit message 一律走 `-F <file>`**。
- **JWT 吊销不必引存储**：把「令牌版本」放进 payload、与用户表当前版本比对，改密/注销即 +1，所有旧 access 与 refresh 同时失效；比维护黑名单简单，也不用等自然过期。
- **改密要同时返回新令牌**：版本 +1 会踢掉所有设备（含本机），若不回送新令牌，用户改完密码立刻被自己登出——功能正确但体验莫名其妙。
- **计费的失真往往不在单价而在口径**：单价就算填对，忽略「缓存命中价约为未命中 1/50」仍会高估一个量级；实测第二轮就有 79% 前缀命中。同理，高峰价是空闲的两倍，写死单一单价必然错一半时间。
- **埋点必须自带保存点**：埋点失败时若整事务 rollback，会把调用方尚未提交的业务改动一起丢掉——用 `begin_nested()`（SAVEPOINT）只回滚埋点那一小段才是真正的「旁路」。
- **模块级惰性单例 + 测试改阈值 = 跨用例污染**：表现为「单独跑过、一起跑挂」。限流器这类单例要在夹具里每例前后重建，否则前一个用例调小的阈值会泄漏给后面所有用例。
- 平台名与模型 ID 会变：`deepseek-v4-flash` 已更新为 `deepseek-flash`（旧名仍可调用但会重定向）。凡以配置项承载模型名的地方都要留一句「接入前核对官方文档」的注释。
- **别让模型做算术**：凡是统计数字会进入产出的地方（L3 的追问依据、L2 的冲突明细），计数都必须由本地聚合得出，模型只做分类与生成。模型算错一个数，整条产出的可信度就归零。
- **模型的输出形态会变，且只在真机暴露**：本次 UC-L3-02 因「字符串值里直接换行」解析失败一次，单元测试与本地 Fake 都拦不住——这类回归只能靠录制真实产出做夹具（golden set）来防。
- **降级要分级**：能拿到主题分布就先返回主题分布，不要因为追问生成失败而整体失败——部分结果比「抱歉出错了」有用得多。
- **版本号才是「最新活动」的稳定判据**：不要按 `created_at` 拿「最新」——同秒内多次写入会被 SQLite 默认精度写穿、按 UUID 字典序再排一遍又会被随机性带偏（`LearningPlanRepository.latest_for_user` 这次踩中）。同主体多次改写（plan 版本、文档快照、用户令牌版本…）都该按主键版本号排，时间戳只做平局打破。**主动写一个被同秒写穿场景的测试**——「单跑过、一起跑挂」的姊妹 bug 是「调试里跑过、集成跑挂」，都是「时序假设」未被覆盖。
- **越权防护翻译成正确的 HTTP 码**：仓储抛 `PermissionError` 表达的是「**该 plan 存在但不属于你**」，对应 HTTP 403；若把它翻译成 404 会向攻击者泄漏"这个 id 存在但没权限访问"，等于帮他们验证账号枚举。错误码本身也是信息。
- **提示词版本化要「文本与版本同处、指纹锁死」**：版本号若与提示词文本分开放，改文本的人很容易忘了 bump 版本。解法是把两者放进同一个 `PromptSpec`，再用 golden 记录文本 sha256——改了文本就 hash 不匹配、测试立刻红，逼着同步 bump 版本并更新指纹。**防脱节的不是纪律，是测试。**
- **推送抑制闸门必须全在本地**：去重 / 收敛 / 免打扰三条规则若交给模型判断，等于为「判断要不要打扰用户」本身再花一次调用、还引入不稳定。它们都是可枚举的事实（hash 是否存在、忽略次数、频率档位），代码里短路判断即可——与「别让模型做算术」同源。
- **置信度校准把「模型自信」与「证据充分」分开**：模型给 0.9 但只有 2 条行为数据，归因依据不足就不该高置信。校准 = 数据充分度缩放 + 信号一致性微调，纯本地、可解释、可单测。**阈值类参数不要写死 0.5，要跟着证据量走。**
- **`create_all` 不给已有表加列，是「测试绿、真库崩」的温床**：P0 用 SQLite + `create_all` 快速迭代，模型一加新列，老库就缺列、运行时 `no such column` 500；而测试用内存库每次都是最新 schema，全绿掩盖了问题。解法：启动时做「缺列自愈」（对比模型列 vs 实际列，`ALTER TABLE ADD COLUMN` 补列），或干脆切 alembic 管理。**任何「建表/加列」的机制，都要覆盖「已存在的库」，不能只覆盖「从零新建」。**
- **框架默认错误格式不等于给人看的格式**：FastAPI 把 pydantic 校验错误以「英文 msg + loc/ctx」数组透出，前端若原样 `JSON.stringify` 就是一坨英文 JSON 怼在输入框下——登录注册这种「用户第一次接触、最容易填错」的界面首当其冲。校验错误要在**服务端**翻译成人话（全局 handler 一次搞定所有端点），前端再兜一层只取可读 msg。**错误信息是界面的一部分，不是日志的附属品。**
- **排查「功能全崩」先确认「你看的是不是同一个服务器」**：本轮三个页面打不开 + 注册 500 的真凶，是浏览器访问的 8000 端口跑着一个**从未重启的旧代码进程**（端点少一半）。在自己的环境复现不出、代码与测试全绿时，别急着改代码——先扫端口、比对 `/openapi.json` 的端点清单，确认服务端跑的是哪一版。**改完代码要重启服务器**（开发期加 `--reload`）。
