## 实测数据（token 口径）

- 口径 = `cost_logs` 的 **id 水位线差分**：每轮开始前记 `MAX(id)`，结束后统计
  `id > 水位线 且 task_type='book_digest'`。比时间窗可靠（同秒不漏、不受时区影响、不混入 worker 的其他任务）。
- **实测 1**：《时间管理》7488 字，1 块 → 13.4s，`status=done verdict=pass`，token 当时为 0（记账 bug）。
- **实测 2**：《插图本》27 字（`--force` 绕过预检）→ **1238 token（482 入 + 756 出）、¥0.0035、8.3s**，
  验证器判 `hard: 正文过短（27 字，阈值 1500）`——「能跑出 done」≠「读到了正文」，这条被拦住了。
  费用可复算：482×¥1/百万 + 756×¥4/百万 = ¥0.003506，与报告一致。
- **实测 3**：扫描版《天才假象》连续两轮 → `failed` → `dead`，**0.0s / 0 token**
  （`_looks_scanned` 在切块前就拦了，一次模型都没调）。第三轮 `stopped=circuit_open`、退出码 2。
- 每轮估算公式（用实测校准，27 字书三项全中）：
  `块数 = min(ceil(字数/12000), 24)`；`输入 ≈ 0.65×字数 + 500×块数`；`输出 ≈ 300×块数 + 450`。
  21 万字的书 18 块 ≈ **145k token / ¥0.17 / 一轮读完**；28 万字以上会 `truncated`，需第二轮续读。

## 备注

- **`max_attempts_per_task` 必须 < `max_consecutive_failures`**（默认 2 < 3）。这是踩出来的：
  一开始两者都是 3，结果**一本书的 3 次重试正好把全局熔断打开**——熔断器退化成单任务的重试计数器，
  等于「一本扫描版书读不了，整个队列停摆」。现在单任务耗尽先转 dead，熔断只拦跨任务的系统性问题。
- 失败任务会回 `pending` 重试，所以「连续失败 3 轮」完全可能由**同一本书的 3 次重试**构成；
  测试里要测跨任务熔断时得显式把 `max_attempts_per_task` 调成 1。
- `--book-id` 一开始会误领队列里更早的 pending 任务（`claim_next` 全局取最早），
  表现为「我让你跑这本，你跑了那本」。已给 `claim_next(only_keys=...)` 加过滤并补测试。
- 为什么状态库独立、不塞进 `dev.db`：这是**工具层**的 runtime 状态，不该进业务表结构（要迁移、会污染生产库）；
  删一个文件即重置，调试成本低得多。
- 验证器「独立」的含义要说清：不是「另一套算法」，而是**不共用判据来源**。
  扫描版那条护栏（`_looks_scanned`：占位符 ≥10 且有效字 <1500）与验证器（有效字数 <1500）同时错才漏判，
  共用一份判据的话，放宽护栏就等于放宽验收。
