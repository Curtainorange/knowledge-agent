## 一、鉴权与账号安全

- **改鉴权的切入点是依赖，不是端点**：只改 `deps.get_user_id` 的实现，所有既有端点就
  自动获得鉴权——因为这些端点本来就依赖它。改动面最小，不必逐个端点改造。
- **PBKDF2 把迭代数写进哈希串**（`pbkdf2_sha256$iter$salt$hash`）：将来调高全局迭代数
  不会锁死老用户（校验用串内参数，重新哈希才用新参数）。
- **JWT 解码必须显式传算法白名单**（`algorithms=["HS256"]`），否则存在 alg 混淆 /
  alg=none 攻击面。
- **必须区分令牌类型**（access / refresh）：否则长期 refresh 凭证可直接访问业务接口，
  等于绕过 access 的短期过期策略。
- **登录失败统一提示 + 拉平耗时**（账号不存在时也跑一次哈希），防账号枚举。
- **限流要双维度取最严**：只按账号会被「每个账号试几次」广撒网绕过；只按 IP 会在 NAT 下
  连带误伤。**不存在的账号也要计数**，否则「是否被锁」会变成账号存在性的旁路探测。
- **限流时间基准用 `time.monotonic()`**：NTP 校正或用户改系统时钟都不会让锁定提前失效。
- **内存桶要懒惰清理 + 设桶数量上限**，否则海量随机 username 攻击会让内存无界增长。
- **JWT 吊销不必引存储**：把「令牌版本」放进 payload、与用户表当前版本比对，改密/注销
  即 +1，所有旧 access/refresh 同时失效；比维护黑名单简单，也不用等自然过期。
- **改密要同时返回新令牌**：版本 +1 会踢掉所有设备（含本机），不回送新令牌的话用户
  改完密码立刻被自己登出——功能正确但体验莫名其妙。
- **测试里查库断言必须用服务端签发的真实 `user_id`**，不能用用户名代替（仓储 guard 会拦截）。
- 验证「固定 JWT_SECRET 生效」的方法：起服务 → 登录取 token → **重启服务** → 用旧 token
  请求 `/auth/me`，同时确认启动日志里没有「临时密钥」告警。

## 二、数据库与事务

- **慢操作绝不能压在数据库写事务里**：模型加载 / 网络下载 / 向量计算一旦被包进写事务，
  SQLite 的**库级写锁**会让其它所有写请求连锁 500（现象：`database is locked`）。
  修法：先 commit 落库释放锁，再补算向量；连接 `timeout` 提到 30s。
- **失败冷却状态不要挂在「每请求新建」的对象上**：`build_embedding()` 每请求新建实例，
  而「加载失败冷却」状态存在实例上 → 冷却永远不生效，每次录入都重新尝试下载并卡住。
  修法：按 backend 复用单例 + 提供 `reset_embedding_cache()`。
- **建表路径必须一致**：`create_all`（dev/测试）与 alembic（生产）都要声明约束与索引，
  只写一处 = 环境相关 bug（参见「复盘与教训.md」第 1、2 条）。
- **书籍全文先整本存 SQLite（P0）**：量级上来再改对象存储 + 字符偏移索引。

## 三、模型调用与计费

- **别让模型做算术**：凡统计数字会进入产出的地方（主题分布、冲突同比），计数必须**本地聚合**——
  模型算式不可靠，而「12 篇里 9 篇停在入门层」这种数字恰恰是结论的依据，错一个就不可信。
  模型幻觉出来的 `item_id` 一并丢弃。
- **降级要分级**：部分结果比「抱歉出错了」有用（如归类失败仍保留主题分布）。
- **模型输出形态会变，且只在真机暴露**：裸换行 JSON、markdown 围栏、前后夹带文字都会让
  标准解析失败。加固共享解析层（`strict=False` + 截取最外层花括号），并录制真实产出做
  **golden set** 回放——这是唯一能在无网 CI 里拦住这类回归的手段。
- **计费的失真往往不在单价而在口径**：忽略「缓存命中价约为未命中 1/50」会高估一个量级；
  同理高峰价是空闲的两倍，写死单一单价必然错一半时间。
- **提示词版本化要「文本与版本同处、指纹锁死」**：版本与文本分开放，改文本的人容易忘
  bump 版本。解法：同一个 PromptSpec 同时放两者 + golden 记 sha256，改了文本 hash 不匹配
  测试立刻红。**防脱节的不是纪律，是测试。**
- **推送抑制闸门全放本地**：去重 / 收敛 / 免打扰是可枚举事实，代码短路判断即可；
  交给模型 = 为「判断要不要打扰」再花一次调用还引入不稳定。
- **置信度校准要把「模型自信」与「证据充分」分开**：样本太少时 0.9 也打折；
  阈值类参数不要写死 0.5，要跟证据量走。
- **走 `reasoning=off` 省钱**：归类、生成式提问等不需要思考模式的任务显式关掉，省下的
  溢价直接体现为成本。

## 四、前端

- **项目全部页面共用一份 `style.css`**（原生 CSS、无框架、无外部依赖）：改样式只需改这一处。
  改前先收集所有 HTML 用到的 class + 校验花括号平衡，确保不遗漏、不破坏。
- **ASI 坑**：以 `[` 或 `(` 开头的续行会被 JS 解析成对上一行结果的索引/调用，
  **语法检查查不出来、只在运行时崩**。用 `node --check` 兜底 + 具名函数调用规避。
- **算「选中位置」必须与后端全文偏移体系对齐**：用 `Range` + 预置 range 的
  `toString().length` 得到章节内字符偏移，再叠加 `chapter.char_start` 得到全文偏移——
  这样才能做高亮与回溯。
- **重新渲染内容后必须恢复 `scrollTop`**，否则每存一次知识就跳回顶部。
- **按比例恢复滚动位置要考虑异步资源**（插图加载会撑高布局）：在图片 `load/error` 后
  再校准一次；这类图片不要加 `loading="lazy"`（会让 `complete` 长期为假，校准不触发）。
- **验证「想法进了向量」的手法**：用**只出现在想法里**的措辞去挖，命中即证明不是靠原文匹配。
- 纯 CSS 足够用：品牌 logo 用 `::before` + 渐变、柱状图用 `flex` + 高度百分比归一化，
  不必为一个小视觉引第三方库。

## 五、工程方法

- **埋点要自带 SAVEPOINT**：整事务 rollback 会带走调用方未提交的业务改动。
- **模块级惰性单例 + 测试改阈值 = 跨用例污染**（表现为「单独跑过、一起跑挂」）：
  夹具每个用例重建实例来隔离。
- **后台线程与测试天然冲突**：用 `worker_enabled` 开关 + 显式 `run_once()` 把执行时机
  交回测试，比让测试去「等」后台行为可靠得多。
- **改 `run_once` 这类公共编排要检查旧断言**：加新周期任务会打破旧测试对 `succeeded == N`
  的精确断言；修法是用 monkeypatch 关掉新开关，让旧测试聚焦原意图。
- **commit message 里有反引号必须走 `-F <file>`**：否则 shell 命令替换会吃掉内容。
- **`git add -A` 会带入 `scripts/` 下的临时文件**：提交后需摘除（未 push 时
  `rm + git add -A + git commit --amend --no-edit` 安全）。
- **错误码也是信息**：跨用户越权应返回 403 而非 404，否则等于帮攻击者验证账号枚举。
- **周期任务不需要调度器状态**：把「每周一次」表达成含 ISO 周的**幂等键**，worker 每轮
  无脑 ensure 即可，省掉 cron 表达式与「上次执行时间」的持久化。

## 六、环境与调试

- **判断「连不上」要分层看**：DNS 能解析 ≠ TCP 可达 ≠ 应用能拿到数据。
  `curl -w "HTTP %{http_code} dns=%{time_namelookup} connect=%{time_connect}"` 一眼看清卡在哪层。
  另外：用户说的「有网」通常指能上网，**不代表目标域名可达**。
- **模型源被阻断的通用解法**：换可达镜像预取到本地（如 ModelScope），再用 onnxruntime
  自己推理，彻底摆脱运行时对 HuggingFace 的依赖——顺带获得完全离线能力。
- **环境有 safe-delete 钩子会拦截 `os.remove`**（走 trash 失败会抛 OSError）；删临时文件
  用 `os.unlink` 绕过。
- **读响应头要不区分大小写**：urllib 转 dict 后键可能被小写化，`headers.get("Retry-After")`
  会取不到。
- **上传不用 multipart**：`python-multipart` 未装，raw body + 文件名 header 更省事；
  但**中文文件名必须 URL 编码**（HTTP header 只接受 latin-1）。
- **epub 不引入 ebooklib**：标准库 `zipfile` + 已装 `bs4` 就够，少一个依赖少一个坑；
  图片相对路径要**双目录回退**（先相对 xhtml 所在目录，再相对 OPF 目录）。

## 七、技术文档写作

- **文档的取舍原则：代码里读得出的不抄，读不出的必须写。** 字段名、函数签名、SQL 语句
  这类信息代码里一读就有，抄进文档只会造成「两份真相」——代码改了文档没改，文档就成了
  负资产。真正该写的是代码里读不出的东西：**依赖规则、为什么这样选、复用点在哪、边界在哪**。
  判断标准：**如果这条信息能靠读一个文件得到，就不写；要跨 3 个文件才能推出，必须写。**

- **技术选型文档要写四段，不是一段。** 只写「我们用了 FastAPI」毫无价值。
  有价值的是：**选了什么 / 为什么（解决什么具体问题）/ 放弃了什么（对手的缺点）/
  何时该换（触发条件）**。缺了「放弃了什么」，读者无法判断这个决策是否已被充分权衡；
  缺了「何时该换」，这个决策会变成永久枷锁——后人不敢动也不知道能不能动。

- **解耦规则必须可机械检查，否则等于没写。** 「注意分层解耦」是口号；
  「`grep -r "from app.llm" app/api/` 必须为空，违反即 PR 驳回」才是规则。
  每条规则都应附一条能跑的命令或一个能点的复选框。

- **检验解耦是否成功，看「加新功能要改几个已有文件」。**
  本项目的硬指标：**新增一个能力（如 L6）只改 2 个已有文件**（`main.py` 注册 +
  `gateway.py` 策略表），其余全是新建。如果被迫改了 3 个以上，说明有耦合需要下沉——
  这是比任何架构图都可靠的判据。

- **复用清单要写「不该复用什么」。** 只列可复用项会诱导过度抽象。
  同样重要的是反面清单：万能 `BaseService`、能力之间互相调函数、
  把 prompt 拼在业务代码里、用裸 `dict` 传结构化数据——
  这些「复用」的维护成本远高于收益。

- **把踩过的坑固化成「必须遵守的规则」，而不是留在复盘里。**
  复盘文档是「事后读物」，新人不会主动去翻。但把它提炼成
  **「新增表必须注册到 `__init__.py`」** 这样一条放进设计文档的规则，
  就成了「事前检查项」。复盘的终点应该是设计文档的一条约束。

- **暂缓项必须标注「这是刻意取舍，不是遗漏」。** 技术债登记表如果只列债务不写理由，
  后人会误读为「当初没考虑到」。写明**偿还时机与触发条件**（「知识条目 > 5000 条时迁 pgvector」），
  才能让后来者知道该不该动、什么时候动。

- **MD → HTML 的转换器要复用现有样式骨架，不要另起一套。** 本项目 HTML 文档
  从既有文件里正则提取 `<style>` 块复用，保证新文档与旧文档视觉一致；
  Mermaid 用固定 CDN 版本（10.9.1）避免上游升级导致渲染差异。

- **校验 Mermaid 图表时注意 ER 图的基数语法。** `||--o{` 里的 `{` 是**语法符号不是括号**，
  做括号平衡检查时必须先剔除，否则会误报「括号不平衡」。


### 补充：文档的受众决定写法（2026-09-16）

- **同一份技术内容，「给开发者看」与「给评审方看」是两种文档。**
  前者的价值在于**降低上手成本**——环境怎么搭、要改的东西在哪个文件、按什么顺序练手；
  后者的价值在于**论证设计合理性**——为什么这样设计、约束如何保障、需求如何覆盖。
  这不是「删内容」，而是**换视角重写**。
  例：同样讲解耦，开发者版说「加新能力只需改这 2 个文件」，
  评审版说「扩展代价经量化验证仅涉及 2 处注册式改动，构成解耦有效性的判据」。

- **受众分析要在动笔前完成。** 判断方法只有一个问题：
  **读这份文档的人要拿它做什么决策？** 答案是「决定怎么改代码」→ 写上手内容；
  答案是「判断这个设计合不合理」→ 写论证与约束。

- **删除操作指引 ≠ 删除信息。** 开发指引里的「如何启动」并非无用信息，
  它只是**归属错了章节**。以「安装与启动」的正式形式并入部署设计后，
  信息完整保留、定位更准确。**同一信息放在哪一章，本身就是专业性的体现。**

- **修订说明要写「为什么改」，不能只写「改了什么」。**
  只列条目变化，读者只看到动作；写明意图（「由开发指引改为设计目标与约束」），
  读者才能理解版本演进的方向。

- **受众分离是处理内部流程内容的正确方式。**
  提交规范、DoD、团队协作细节不属于设计文档的受众关注范围，
  但其中的**技术约束**（依赖方向六条、交付质量标准、合规检查项）必须保留。
  做法：内部流程留在 `dev_logs/`，设计约束留在设计文档。

- **正式化不是堆砌术语，而是消除「第一人称操作口吻」与「内部黑话」。**
  具体替换：「不许」→「不得」、「铁律」→「约束」、「何时该换」→「重新评估条件」、
  「踩坑」/「复盘第 N 条」→ 指向文档内的设计条目引用。
  其中最后一类最关键：**内部记录引用对文档读者不可追踪**，
  必须转成文档内自洽的引用（如「见附录 C 第 7 条」）。

- **对用户重命名或操作过的文件，即使判断为冗余也不得擅自删除。**
  列入待办并说明情况，由用户确认。

## 八、交付文档流水线（Markdown → Word，2026-09-17）

- **内容已定稿时走 S2→S3，不要走 S1 重写。** `docs/*.md` 要出 Word 版，走
  `tencent-docx` 本地流水线（S0 解析输出路径 → S2 版式生成 → S3 HTML→DOCX）。
  交给 S1「创作」会重写正文，造成**内容漂移**——论文/作业/规格这类文本，
  正文一字不能变，只换版式。

- **体裁选型有硬约束：`general`（modern-minimal）适合 Word 阅读。**
  它的正文 11pt、行高 1.7；而 `business-report`（business-modern）正文只有 9pt，
  且其 `genre_fit` 门禁**强制要求 `.executive-summary`**——原文没有摘要时选它，
  门禁必挂，且补摘要等于**注入原文没有的内容**（违反「只美化不注入」）。
  判据：**原文没有的章节，绝不为了过门禁而造。**

- **产物落点沿用项目约定：`docs/` 下 md 与 docx 成对存放**，不留在流水线的
  `output/<request_id>/stage3/` 里（那里是中间产物区，用户找不到）。

- **托管 venv 可能只有骨架、没有依赖，也没有 pip。** `~/.venv-html-to-docx`
  装依赖用这条链，不要指望 `setup-html-to-docx.sh`（本机 bash 缺 coreutils，
  连 `dirname`/`tail`/`ls` 都没有，脚本跑不起来）：
  ```bash
  "$HOME/.venv-html-to-docx/Scripts/python.exe" -m ensurepip --default-pip
  "$HOME/.venv-html-to-docx/Scripts/python.exe" -m pip install \
    --only-binary=:all: -r <plugin>/skills/html-to-docx/scripts/requirements.txt
  ```
  `--only-binary=:all:` 是必须的，否则 lxml 会走源码构建。

- **沙箱 bash 无 coreutils，调用转换器用绝对路径 + PYTHONPATH**：
  ```bash
  PYTHONPATH=<plugin>/skills/html-to-docx/scripts \
    "$HOME/.venv-html-to-docx/Scripts/python.exe" -m html_to_docx convert in.html -o out.docx
  ```
  不要 `cd` 进 scripts 目录再跑（`cd` 在 shim 下不可靠）。

- **`html-review` 是脚本化门禁（0 次 LLM），几条容易踩的规则**：
  ① 裸值检查连 `padding: 0.5em 0.8em` 都算违规——**所有 margin/padding/font-size
  必须走 `var()`**，字面量只能出现在 `--自定义属性` 定义处；
  ② `:root` 块必须含 `--fs-body`/`--color-text`/`--ff-body`；
  ③ 封面各块的 `text-align` 必须是**行内 style**（写在 `<style>` 里不算）；
  ④ 所有 `<table>` 必须有 `<thead>`（且表头用 `<th>`）与 `<tbody>`；
  ⑤ 不得嵌套表格；⑥ `genre=general` 时 genre-fit 维度直接满分。
  改完先本地跑一遍（退出码 0 = 通过）再进 S3，避免返工。

- **转换器会把「【待填】」这类占位符自动识别为 Word 可填写书签**，
  所以「待人工确认」的字段保持原文写法即可，用户直接在 Word 里填，
  不必为了好看而删掉占位符。

## 九、PDF 解析接入（书籍阅读扩展，2026-09-20）

- **选型优先「纯 Python、无二进制」**：PDF 文本抽取用 `pypdf`（BSD、纯 Python），
  不用 pdfplumber（依赖链长）与 PyMuPDF（二进制 + AGPL）。与 epub 解析「只用标准库」
  的取向一致，部署时不需要额外系统依赖。

- **PDF 没有章节，分章要么读书签、要么认命按页分**：有 outline 就用书签标题与页码
  聚合页区间（首个书签之前的页归入「开篇」）；没有书签就「一页一章」，标题写「第 N 页」。
  **不要拿页首行当章名**——那通常是从上一页续下来的半句话，做目录项会误导读者。

- **抽取后的清洗要「宁漏勿误」**：页眉页脚剔除只考察页首 1 行 / 页末 1 行，并要求同一
  签名（去掉数字与空白后）覆盖 ≥60% 的页、总页数 ≥6。曾用「首尾各 2 行」，结果把
  「仅数字不同」的正文行（`chapter body line 3` 这类）一并删掉。
  **漏删一个页眉只是难读，误删正文是内容丢失。**

- **元数据要过一遍占位值黑名单**：`untitled` / `anonymous` / `Microsoft Word` /
  `xxx.doc` 这类导出工具写死的值很常见，直接采纳会让整个书架都叫 untitled，
  命中就回退到文件名。

- **中文 PDF 的抽取质量由文件自身的文本层决定**（嵌入字体 + ToUnicode CMap），
  不是解析器能补救的；遇到乱码先怀疑 PDF 本身，别改解析器。
  验证时可以临时用 reportlab + 系统字体（`C:/Windows/Fonts/simhei.ttf`）生成中文样本，
  **样本放临时目录，不进仓库**。

- **同一文件的多处改动不要一次性并发提交**：本次两次出现「工具回执成功、但改动没落盘」
  （漏了一个常量定义、漏了一处变量改名），靠 `grep` 复核才发现。改完同一文件的多个片段后
  **必须回读 / grep 复核**，不要只信成功回执。
