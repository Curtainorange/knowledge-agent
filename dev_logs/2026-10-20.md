## 备注

**今天定下的几个决策（后续别反复）**

- **单人实施**：用户要求"按计划来、时间不限"，所以按单人串行推进，不再等 3 人方案。
  这意味着 E/F/C 分批交付，每批完整（测试 + 提交），不交半成品。
- **不回填历史冲突归因**：惰性触发（用户点开才跑），避免一次全库 reasoning 调用。
- **C 模块按来源分级**：微信读书无全文 → 只能做摘录级对比，UI 标 `basis`。
  这是数据源限制，不是实现取舍。
- **`agent_summary` 可引用但不得单独构成依据**：每条建议至少 1 条 `library` 级。

**实读代码的关键事实（后续别重复查）**

- `source` 真实只有 `book` / `weread` / `manual` 三种；模型注释里的
  notion/obsidian/feishu/bookmark 全是预留、未实现。
- `/knowledge/stats` 原本已有 `by_source` / `by_embed_status`，状态条不必新建接口。
- `greeting.build_opening()` 原是纯模板 5 分支，加"先确认"要改函数本身而非提示词；
  相关测试绑定文案，改断言时保留了覆盖意图（改成反断言，不删测试）。
- `l4_orchestrator.generate_plan()` 的 `GeneratedPlan.tasks[]` 只有 `week_index + subject`，
  `plan_tasks` 表也没有时长/类型 → F 模块的"负荷上限"目前无字段可依。
- `book_orchestrator.read_whole_book()` 已产出 `chapters_note[{topic,gist,points}]`，
  C 模块直接复用做对齐，不必重读原文。
- 网关有 `STRATEGY_TABLE` / `JSON_TASK_TYPES` / `PROMPT_VERSION_BY_TASK_TYPE` 三处
  需要同步登记新 task_type，漏一处就会静默落到 `default`（今天 `reading_suggestion`
  就是这么发现问题的：provider 收到的 task_type 是 `default`）。
- 改任何提示词文本必须同步 bump version + 更新 `tests/golden/prompts.json` 的 sha256。
