## 备注

### 调研事实（实测，2026-11-18）

- 该仓库**不是软件、没有 API/CLI**，是「静态书单 + GitHub Pages 搜索页」：
  `md/*.md` 是分类书单（约 700 个分类文件），`docs/all-books.json` 是已生成的全量索引。
- 索引体量与字段：**24,071 条**，7.1 MB，字段 `title / author / link / category / language / level / formats`。
- 链接指向：**24,002 条全部是 `url89.ctfile.com`（城通网盘）**，带分享密码 `?p=8866`；
  另 69 条是字面量「链接未找到」。**没有一条直链**。
- 站点活跃度：24,193 star / 3,367 fork，但**最后提交 2026-01-13**（近 10 个月未更新），无 LICENSE。
- 城通分享页实测（`url89.ctfile.com/f/...`，HTTP 200）：返回的是 **Vite/Vue 单页应用空壳**，
  7588 字节 HTML 里没有任何文件信息，真实下载地址由 `urlstatic.ctfile.com/assets/index-*.js`
  运行时动态换取。**纯 HTTP 请求拿不到直链**，要做只能上无头浏览器。

### 结论（判断，不是事实）

- **「自动找书」已存在**：`app/agent/book_finder.py` 已能用联网检索把「只记得情节」定位成书名。
  这个仓库真正的增量不是「找」，而是**「确定去哪拿」**——给书名配一条可点的资源链接，
  且是离线确定性数据（不花 token、不出网、不受模型幻觉影响）。
- **「自动下载」不建议做**：① 技术上一页 SPA + 倒计时 + 免费限速 + 反爬，脆弱且要维护；
  ② 网盘免费分享失效率高，24k 条里能活多少未知，失败要给用户看一堆死链；
  ③ 版权上这批是未授权电子书，仓库自己的声明也写着「24 小时内删除」。
  折中做法：卡片给「打开下载页」，由用户自己下 —— 责任边界清楚，也够用。
- 若落地，顺序必须是「先登记 `raw.githubusercontent.com` → `--write-doc` → 再写码」，
  因为导入脚本的出网字面量会被 `harness_check.py` 扫到（注释里的 URL 也算）。
- 数据落 `data/book_catalog.json`（`data/` 已 git-ignored），导入走离线脚本手动跑，
  不让运行时联网去更新索引。

### 实现后才发现的（别当成「已经做过的筛选」）

- **「行 ≠ 书」——这一条一开始做错了。** 24,071 行里有 12,654 行是同一本书挂在多个标签下
  （`md/` 按标签组织，一本《思考，快与慢》同时属「思维 / 心理学 / 决策」就出现三行）。
  最初按「书名+作者+链接」三元组去重，把除第一个以外的标签静默删掉了——每本平均丢 1.1 个。
  **正确做法是按链接合并、标签取并集。** 这三行不是脏数据，差别恰恰在标签上。
  标签数分布：1 个 2,457 本 / 2 个 5,440 / 3 个 3,156 / 4 个 280 / 5 个 13 / 6 个 2。
- 原始数据里 `formats` 是**统一填的** `["epub","mobi","azw3"]`——合并后 11,348 本**全部**含 epub。
  也就是 `has_epub` 目前恒为 True，「只有 mobi 就不给链接」这条分支在现有数据上走不到。
  逻辑保留（换一批数据源就不一定了），但不能对外说成「我们筛出了有 epub 的书」。
- **排序坑（初版真机翻车）**：把「字符相近」和「包含」放同一档，查「刻意练习」第一条给的是
  「天才源自刻意练习」，查「人类简史」第一条给的是「人类酷刑简史」——因为同分后按长度排，
  短的那条赢了。改成四档（精确 1.0 / 前缀 0.92 / 包含 0.85 / 相似封顶 0.75）后才对。
  这类问题**构造用例测不出来**，必须拿真数据查几本常见书。
