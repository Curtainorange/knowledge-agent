**1. 对话入口的架构收口**

原来对话入口只接了 3 项能力，这一周把 **10 项全部接入**。但这里真正值得说的是架构，不是数量：

- **新增一层意图路由**：把一句话变成「能力 + 参数」。命令式的说法（「记一下…」「同步微信读书」）走**本地确定性规则、零模型调用**；只有判不出来才问模型，并且这个模型任务固定关掉思考模式——因为它**每一轮都要跑**。分流失败一律回落通用对话，因为链路里挂着写库这类有副作用的能力。
- **卡片协议独立成模块**，作为前后端唯一契约。编排层只做分发，执行统一交给一层执行器。
- **同步与异步共用同一段执行逻辑**：异步只改「在哪儿跑」，不改「跑什么」。不这么做，同一个能力迟早会有两套实现并静默分叉。
- **异步回合不引入新表、不引入消息队列**：复用项目已有的任务框架（自带幂等、重试、死信），**把状态直接落在会话消息上**——先写一条「进行中」的卡，后台跑完就地把那条消息改成结果。这样结果不需要另找地方存，重新打开页面看到的是最终结果，而不是一条永远转圈的卡。
- **两处并发与调度的细节**：后台进程原本用固定间隔轮询，改成**可被唤醒的事件等待**，否则「异步」会退化成纯等待；另外没有后台进程时**自动退回同步执行**，否则那张卡会永远转圈，用户既看不到结果也等不到失败。

**2. 模型层重做：从一个供应商到一条供应商链**（详见第二节）

**3. 检索层重做：从「全量传进内存再筛」到「库内检索」**（详见第二节）

**4. 让 L2 冲突检测的产出进入推理链路**

冲突检测原先的问题很具体：**能检测出来，但结果躺在那儿不进任何推理**——上层只拿到一个「本周冲突 N 处」的计数。这一周做了三处改造：

- 把冲突**双方的具体主张**写进简报与诊断的输入（此前只有计数，追问和归因只能围绕一个计数器转）；
- 学习计划的生成与偏离归因里，注入**与目标语义相关的**未解冲突（目标向量与主张向量的余弦相似度，低于阈值就不注入）；
- 为此抽出一个共享模块承载冲突的读取口径——因为执行层反向依赖了三个编排器，直接复用会**造成循环导入**。

## 二、学到的技术（约 4 分 30 秒）

【本段为重点，语速放慢】分三块：**模型层**、**检索层**、**如何让质量可度量**。

### 第一块：模型层——约束的位置、重试与回退的边界

这一周接入了第二家模型供应商（小米 MiMo，与原来的 DeepSeek 二选一、互为备份）。**接完之后我最深的体会是：真正的成本不在「接一个新供应商」，而在「找齐所有默认假设了旧供应商的地方」。**

**技术点一：能力口径必须用接口实测，不能信资料。**
我按第三方资料填了模型名，真实调用直接报 `400 Unsupported model`。用 `GET /v1/models` 实测才发现，那个模型名**在这家账号下根本不存在**。同样地，两家供应商的「思考开关」字段完全不同，而且其中一家**默认是开启的**——不显式关掉，成本会失控。

**技术点二：结构化输出，关键在「把约束放在哪里」。**
这是这一周最有价值的一次对比实验。同一个简报任务，各跑 6 次：

| 做法 | 成功率 | 失败形态 |
|---|---|---|
| 自由文本 + 本地宽容解析 | 3 次里挂 1 次 | JSON 真的被写坏了，本地解析救不回来 |
| 让服务端返回 JSON 对象 | 5/6 | 能解析，但**嵌套结构被压平**（结构校验失败） |
| **让服务端按给定 Schema 约束** | **6/6** | — |

结论：**「必须是什么形状」这件事，讲给服务端听，比事后在本地修补可靠。**

原来本地已经有**三层兜底**（剥围栏、取最外层花括号、宽容解析），但再多兜底也救不了**语法已经坏掉的 JSON**——兜底能处理「格式不规范」，处理不了「已经写错」。

同时这条不能一刀切：另一家供应商在思考模式下对这类约束有已知兼容弱点，**当初绕开它不是错的决定**。所以最终做成**按供应商能力位分派**——声明支持哪种就用哪种，两边各拿各自的最优解。

还有一个工程细节：Schema 不是手写的，是从**数据模型自动派生**的。手写 9 份的结果一定是改一处忘一处、和本地校验器漂移。

**技术点三：容错要区分「重试」和「回退」，并且不能伪装成成功。**

- 主供应商**按重试策略试满 3 次仍失败**才切备用，备用也享受同样的重试次数；
- 切备用时**必须同时换模型名、并重算输出约束**——把 A 家的模型名发给 B 家会被直接判「模型不支持」，不支持原生约束的供应商收到 Schema 也会拒收。这两点不做，回退等于必然失败；
- **模拟实现永远不作为真实失败的回退目标**。否则「模型挂了」会被伪装成「模型答了」——这是最危险的假象，因为它让你带着错误结论继续往下走；
- 成本记账改为**按实际服务的模型名取价**：回退发生时是备用供应商在干活，按主供应商的单价记账会让这一笔整笔错记。

真机验证方式：故意把模型名指向一个不存在的模型，日志显示真实切到备用供应商并正常返回，服务模型字段确认已切换。

### 第二块：检索层——从内存全量筛到库内检索

原来的做法是把用户的全部知识条目读进内存、再逐个算相似度。这一周重做成**库内检索**：定义统一的向量库接口，内存实现与数据库实现（PostgreSQL + pgvector）各实现一份，上层只传过滤条件，由存储层返回 top-k。

**一个设计取舍值得说**：条目向量化失败时，**仍然把它的标题和正文写进索引**。因为「算不出向量」不应该等于「这条内容搜不到」——它还可以被关键词通道命中。

**踩到一个很典型的坑，我单独讲：**
数据库后端的 SQL 里我写了 `:vec::vector`（一种类型强转写法）。框架识别绑定参数时用了一条正则，其中含一个「后面不能跟冒号」的前瞻条件，结果**把参数名识别成了 `ve`**，编译后整条 SQL 原样发给了数据库。

**它为什么最阴？三个条件叠在一起：**

1. 构造 SQL 时不报错；
2. **不连真数据库的测试全绿**；
3. 调用失败又被上层的兜底接住、降级成「只有关键词通道」。

于是表现**不是报错，而是检索质量悄悄变差**。这正是我之前汇报里说过的「降级会掩盖缺陷」的另一种形状。

现在的做法：全部改成标准写法（用显式的类型转换函数），并**新增 14 项不需要真数据库的测试**，核心断言是「框架识别到的绑定参数集合，必须和代码传进去的参数字典完全一致」——不对称就是这类坑；再配一个假会话走完整路径，防止绕过。

同一块还修了两处同类问题：

- **关键词检索拿整句话去做模糊匹配**，而内存后端是按二字窗口重叠打分的——「B+树 范围查询」这类多词查询在数据库后端**几乎必然零召回**，关键词兜底等于没有。改成按「词 + 词内二字窗口」展开预筛，SQL 只出候选、得分仍由同一个打分函数给出（**同一份语义必须只有一个来源**）；
- 表名要拼进 SQL（标识符走不了绑定参数），补形状校验；顺带转义模糊匹配的通配符——查询里带 `%` 的「增长了50%」不该被当通配符。

### 第三块：让「检索质量」从感觉变成数字

这一周做了一件一直拖着的事：**给检索建评估集**——20 条语料、16 条查询，并设定护栏线（前 5 条命中率不低于 0.95、第 1 条命中率不低于 0.75）。

同时把两个检索通道的融合方式改成**按排名融合（RRF）**。原来的做法是「归一化加权 + 给单通道乘一个 0.1 的硬编码惩罚」——那是拍脑袋定的参数；按排名融合不需要调权重，而且**测试强制要求它不能比旧做法更差**（旧做法保留为可选项，用于对照）。

另外落地三件「让系统能自检」的事：

- **嵌入模型版本记录**：换过向量模型后，旧向量与新向量不能混用。现在记录每条内容是用哪个模型、多少维度算的，并提供**增量重建**脚本；数据库加列走启动自愈，不需要手工迁移。
- **没有密钥时的降级档**：不配置真实模型时，走**确定性规则**做意图定位，而不是拿模拟输出冒充模型结论。
- **一个自检端点**：一次调用检查数据库、模型、嵌入、向量索引一致性、陈旧向量五项，出问题时立刻能定位到是哪一层。

## 三、踩过的坑与沉淀的技术方法（约 1 分 30 秒）

这一周踩的坑不多，但有两个比功能更值钱。

**一、改了配置却没生效。**
我往配置文件里加了新密钥，代码写得没问题，但服务行为一直不对。原因是**配置文件只在进程启动时读取**——旧进程还在跑旧配置。这件事提醒我：**「代码是对的、服务却没生效」是最难查的一类问题**，因为它不报错。现在的习惯是：改配置必重启，并且启动后确认日志里确实加载了新配置、没有落回模拟实现。

**二、只写不读，通常意味着同一条规则被实现了两遍。**
核查时发现有一列数据（主张的向量）**每轮都重新算，却从没被读过**。表面看只是浪费，顺着查下去发现：写的时候和读的时候**各自写了一套文本处理逻辑**——这一次恰好等价，但只要有人改一个常量，两边就会**静默分叉**：相似度照旧算得出来，只是它度量的已经不是同一个东西了。现在统一收口成一个函数，并改成「优先读库、缺失才补算回写」——顺带把组对阶段的模型调用降到了零。

**【停顿】我把这一周的技术方法总结成三句：**

- **不报错不等于跑通了**——降级链会把错误悄悄吃掉；
- **容错要有，但不能伪装成成功**——模拟结果绝不能冒充真实结果；
- **先定性、再定位**——排查数据类问题全程只读，不改动任何数据。

## 四、下一步（约 40 秒）

1. **数据库向量后端还欠一次真机验证**：SQL 契约（绑定参数、关键词预筛）已经用「不连库的测试」钉住，但「真的能取到近邻」「向量字面量能被扩展的输入函数解析」「建表与扩展安装在真库上跑得通」这三件，只有连上真实 PostgreSQL 才算验过。切后端时按这个清单走一遍。
2. **候选对比较目前是平方级复杂度**：检索侧的瓶颈解决了，但冲突检测阶段的候选对仍是全量两两比较。主张数量上来后那一步会成为下一个瓶颈，打算先用向量近邻缩小候选范围。
3. **容错还缺可观测性**：回退与修复目前只在日志里，界面和监控看不到「这一周有几次是靠备用供应商救回来的」。计划落一张事件表，否则这类容错会长期隐形。
4. **对话的多轮指代**：分流目前只看当前这一句，不含会话历史，「再来一次」这类话会落到通用对话。需要把最近一两轮作为分流上下文。

## 附：问答准备（备用，不必念）

### 【概念类·优先准备】智能体的概念，以及与大模型 / 豆包这类网页 AI 的区别

**Q：什么是智能体？它和大模型是什么关系？**
A：我分层说。大模型提供的是**理解和生成**的能力，它本身是无状态的——给一段输入、出一段输出，结束。智能体是在模型外面再包一层结构：**记忆 + 工具 + 规划 + 自主性**。模型在里面是被调用的一个组件，不是全部。类比的话，模型是引擎，智能体是车——还需要轮子（工具）、仪表盘（记忆）、方向盘（规划）。

在我这个项目里，这一层是具体的，不是概念：
- **记忆**：知识条目、观点主张、学习行为事件都持久化在库里（现在 22 条条目、49 条主张、589 条行为事件），跨会话累积；
- **工具**：10 项能力，不只是回答问题，还能写库、改学习计划、同步外部阅读数据；
- **规划**：把学习目标拆成周计划（当前 29 个任务），检测到偏离时重排；
- **自主**：不只在被问时响应——到点会自己扫描冲突、推送周简报，打开会话时它会先开口。

一句话：**大模型是"会说话的大脑"，智能体是"有记忆、会用工具、会自己动的手"。**

**Q：你的项目和豆包这类网页 AI、和大模型有什么区别？**
A：我不比较谁更强，我说**结构上的差别**。可以用四个问题来判：

1. **有没有跨会话的持久状态？** 网页 AI 每次对话基本从头开始；我的系统存的是**这一个人**的知识、观点和行为轨迹。
2. **能不能改变外部世界？** 网页 AI 输出文字就结束了；我的系统输出会写进数据库、改掉学习计划、触发下一轮扫描。
3. **会不会主动发起？** 网页 AI 是你问才答；我的系统到点自己扫冲突、推简报，你打开对话框它先开口。
4. **输出会不会反过来改进它自己？** 我采纳一条诊断，计划就跟着改写；我标记一条冲突是误报，同类冲突以后就不再算。这是闭环。

这四个问题上，纯大模型都是"否"。

**有一个证据我觉得最有力**：这一周我刚把模型供应商整体换了一遍（两家互为备份、运行时自动切换，切换时模型名、输出约束、计费全都按新供应商重算）。**如果换个模型系统就散架，那它本质上是给某个模型套了个壳；我的项目里模型是插拔的组件。**这本身就说明——模型不是智能体的全部。

反过来我也说清楚边界：我的系统**不是完全自主的智能体**，它是"规则 + 模型混合"——能用规则确定的（分流、计数、阈值判断）一律不交给模型，模型只做它擅长的语义判断。自主行为目前也限于定时扫描和主动推送。

**20 秒版本**：豆包是"你问它才答、答完就忘"的通用助手；我的系统是"它一直在看着你，会主动开口，改的是你自己的状态"。

**Q（追问）：那带联网检索 / 外部知识的模型算智能体吗？**
A：那叫检索增强，不叫智能体。**它解决了"知道更多"，没解决"能做什么"和"会不会自己动"。**上面四个判定问题它最多答对一个——而且它取到的外部知识是公共知识，不是关于"你"的持久状态。真正的分界线是**有没有行动和自主**，不是有没有知识。

**Q：为什么要接第二家模型供应商？**
A：两个原因。一是**可用性**——单点故障时业务不中断；二是**可替换性验证**——不实际换一次，就不知道架构是不是真的解耦。接第二家时暴露出**三处默认假设了旧供应商的旧代码**，全是静默失效、不报错的（一处是验收脚本会意外打真实模型、一处是断言写死了旧供应商名、一处是成本脚本把新供应商当成了没配密钥）。这类问题只能通过实际替换来发现。

**Q：为什么把结构化输出交给服务端约束，而不是继续用本地解析？**
A：做过对比实验：自由文本解析最差（3 次挂 1 次）、返回 JSON 对象中等（嵌套结构会被压平）、按 Schema 约束 6 次全过。本地宽容解析只能救「格式不规范」，救不了「语法已经坏了」。但也不是一刀切——另一家供应商在思考模式下有已知兼容问题，所以做成**按能力位分派**，两边各拿最优解。

**Q：检索改动之后，怎么证明效果没有变差？**
A：建了评估集（20 条语料、16 条查询），并写了护栏断言：前 5 条命中率不低于 0.95、第 1 条不低于 0.75，且**新的融合方式不得差于旧的加权方式**。这样以后改检索参数，跑一次测试就知道是变好还是变坏，不用靠感觉。

**Q：异步操作会不会让用户干等？**
A：不会。先发「进行中」的卡片，后台跑完**就地改写那条消息**；任务失败或进死信，那张卡会落成明确的失败卡并给出重试落点，而不是永远转圈。另外没有后台进程时系统会自动退回同步执行。

**Q：这一周最大的技术收获是什么？**
A：**不是功能数量，而是对「失败」的理解更细了。**以前我认为失败就是报错；这一周遇到的最危险的几个问题，全都是**不报错**的——SQL 写错被降级链吃掉、配置没生效服务照常跑、向量重复计算但两边口径不同。所以我现在更看重「让失败可见」：给检索建评估集、加自检端点、模拟结果绝不冒充真实结果。

## 附：三分钟精简版

**开场（15 秒）**
本周把 10 项能力全部接进对话入口，并重做了模型层与检索层；测试从 299 项做到 **522 项**，本周提交 21 次。

**一、做了什么（40 秒）**

- 对话入口架构收口：意图路由（命令式走本地规则、零模型调用）、卡片协议独立成模块、同步与异步共用执行逻辑、异步回合不引入新表（状态落在会话消息上）
- 模型层：接入第二家供应商，做成供应商链
- 检索层：从「全量传进内存再筛」改成「库内检索」，统一向量库接口 + 数据库后端
- L2 冲突双方主张进入简报 / 诊断 / 计划链路的推理输入

**二、学到的技术（100 秒）**——重点

- **模型层**：模型名以接口实测为准（资料是错的）；两家思考开关字段与默认值不同；**结构化输出对比实验**（自由文本 3 挂 1 / JSON 对象 5/6 / Schema 约束 **6/6**）→ **约束交给服务端比事后修补可靠**，并按能力位分派；Schema 由数据模型自动派生
- **容错边界**：重试 3 次才回退；切备用**要同时换模型名与重算约束**；**模拟结果绝不冒充真实结果**；成本按实际服务的模型名取价
- **检索层**：统一向量库接口 + 数据库后端；踩到 SQL 绑定参数被正则误判——**不报错、测试全绿、被降级链吃掉，只是检索质量悄悄变差**；关键词检索的口径与打分收口
- **可度量**：检索评估集（20 语料 / 16 查询 + 命中率护栏）；融合改为按排名融合，不再拍脑袋调权重；嵌入模型版本记录与增量重建；无密钥时走确定性规则；五项自检端点

**三、坑与方法（25 秒）**
配置改了没生效（配置只在启动时读）；只写不读意味着同一条规则写了两遍。三句话：**不报错不等于跑通；容错不能伪装成成功；先定性再定位。**

**四、下一步（15 秒）**
数据库向量后端的真机验证、候选对比较的平方级复杂度、容错的可观测性、对话的多轮指代。
