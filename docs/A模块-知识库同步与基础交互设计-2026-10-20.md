# A 模块设计：知识库同步与基础交互

- 范围：内容怎么进库 → 进库后是否**可用** → 建议引用哪几条 → 怎么溯源回原文
- 状态：**设计稿，待澄清确认后开工**
- **修订提示**：`agent_summary` 的定性已由 `docs/验收自检与修正-2026-10-20.md` 修正 3 明确——允许引用，但不得作为唯一依据（每条建议至少 1 条 `library` 级）。冲突时以修正文档为准。
- 日期：2026-10-20
- 与 B 模块的分工：**A 定义"什么算可用依据"，B 定义"怎么选、怎么生成建议"**。两者不重复。

---

## 一、需求复述（6 条）

1. A 模块不是"再加同步渠道"，而是**给"依据"立规矩**：哪些内容有资格被引用、引用到什么颗粒度、用户怎么核对。
2. 现有同步能力其实够用（内置阅读器划词、微信读书 API、手动记一条），问题在于**状态不透明**：用户不知道哪些进了库、哪些只是库里有但检索不到、哪些根本没进来。
3. 关键认知：**"已入库" ≠ "可被作为依据"**。条目 `embed_status=pending/embed_failed` 时语义检索召不到它，虽然它在库里。这个中间态现在对用户完全不可见，会导致"我明明存过，它却说没找到"。
4. 每条建议必须能三跳溯源：**建议 → 证据块 → 原文片段（quote）→ 定位（内置书字符区间 / 微信读书 deepLink）**。任何一跳断了，这条依据就不该出现在建议里。
5. 未入库内容不得作为依据，落地点是**书名识别 + 白名单校验**：用户提到未同步的书，明确告知不能当依据，而不是悄悄不引用。
6. 同步状态要给用户一个可读的体检结论（多少书 / 多少划线 / 多少想法 / 多少还没向量化），而不是让用户去猜。

## 二、实读代码后必须纠正的两个前提

| 事项 | 代码事实 | 影响 |
|---|---|---|
| `source` 枚举 | 真实只有三种：`book`（内置书划词，`books/service.py:176`）、`weread`（`weread/service.py:29`）、`manual`（`ingestion/service.py` 默认）。模型注释里写的 `notion/obsidian/feishu/bookmark` **全是预留、未实现** | 同步状态条只能按 3 类展示；文档/UI 不得出现未实现的来源，否则等于承诺不存在的能力 |
| 统计接口 | `GET /api/v1/knowledge/stats` 已返回 `total / by_source / by_embed_status / top_tags` | 状态条**不需要新建接口**，只需补「上次同步时间」与「未向量化数」。这是本模块最省工期的一点 |
| 内置书去重 | 微信读书靠 `source_item_id = hl:{bookmarkId} / reviewId` 去重；内置书摘录 `source_item_id = book_id`（整本书同一个值），**同一段文字划两次就会入库两条** | 现存缺陷，必须在本模块修掉，否则证据池里会出现重复条目、建议重复引用 |

## 三、需要确认的澄清问题（6 条）

| # | 问题 | 我的默认假设 |
|---|---|---|
| Q1 | 智能体的**通读笔记**（`book_agent_readings`）算不算"已同步阅读内容"？它不是用户写的，但基于用户上传的书 | 算，但必须用不同 `kind` 标注（`agent_summary`），UI 上不与用户划线混排 |

## 四、交互流程（文字版）

### 4.1 三级可用性模型（本模块的核心）

```
L1 已入库      knowledge_items.is_deleted = false
                 ↓ 向量化成功
L2 可召回      embed_status = embedded（或 keyword 降级召回）
                 ↓ quote 能命中 raw_content + locator 可跳转
L3 可溯源      证据块完整（quote + locator）
                 ↑
      只有 L3 的条目有资格进入建议的 basis_item_ids
```

- L1 但非 L2：库里能看到，但建议找不到它 → 状态条必须显示"有 N 条还没准备好"
- L2 但非 L3（quote 抽不出）：**允许召回但不允许引用**（防止"有依据但引的是别处"）
- 这套判定写成 `grounding.usable_items()` 一个函数，B 模块直接调用，不再各写一遍

### 4.2 同步流程（三分支）

```
[用户进入 knowledge.html 或对话里说"同步"]
   │
   ├─ 分支 1：内置阅读器（已上传的书）
   │    用户在 reader.html 划词 → 可附想法 → POST /books/{id}/notes
   │    入库：source=book, source_item_id=book_id, source_locator={chapter_index, char_start, char_end}
   │    查重：同 book_id + 同区间 + 同文本 → 命中则返回"已存过"，不新建
   │
   ├─ 分支 2：微信读书
   │    点"同步" → WeReadSyncService.sync()
   │    入库：source=weread, source_item_id=hl:{bookmarkId} / reviewId
   │    幂等：已存在（含软删）跳过；返回 total/scanned/created/skipped/failed
   │
   └─ 分支 3：手动记一条
        对话里"记一下：…" → source=manual, tags 由用户给
        （无 book_id，溯源只能定位到条目本身）
   ▼
[同步后：状态回执]
   "这次同步：3 本书、新增 12 条划线、4 条想法；跳过 8 条（已存过）；2 本失败。
    其中 5 条还在做向量化，暂时检索不到。"
```

### 4.3 依据溯源流程（用户视角）

```
建议卡上每条建议 →「依据 2 条」
   ├─ 点开：证据列表，每条显示
   │    [划线] 《原则》· 第三章 极度透明 —— "…原文片段…"      [跳到原文]
   │    [笔记] 我在 3 月 12 日记的 —— "…想法…"                [跳到条目]
   │    [通读] 智能体通读《原则》第 3 章要点 —— "…gist…"       （仅展示，不可跳转原文）
   ├─ 点「跳到原文」
   │    source=book    → /reader.html?book=…&char=…  高亮该区间
   │    source=weread  → 微信读书 deepLink（外链，新窗口）
   │    source=manual  → /knowledge.html?item=…      定位该条目
   └─ 证据不足时，卡片不显示"依据 0 条"，显示"依据不足，未生成"
```

### 4.4 未入库拦截流程

```
用户输入提到书名（"我在读《X》" / "《X》里说…"）
   ▼
书名抽取（本地规则 + 书名号匹配优先，其次库内书名模糊匹配）
   ▼
在 books / knowledge_items(source_locator.book_title) 中查
   ├─ 命中 → 正常走 B 的确认流程
   └─ 未命中 → 拒绝作为依据
        "《X》还没同步进来，我不能拿它的内容当依据。
         要么现在同步（微信读书里有的会自动带过来），
         要么你先告诉我你在里面看到了什么，我按你说的记一条。"
        （绝不调用模型去"回忆"这本书——那正是幻觉来源）
```

## 五、字段清单

### 5.1 三级可用性判定（`grounding.usable_items()` 返回）

| 字段 | 类型 | 说明 |
|---|---|---|
| `item_id` | str | `knowledge_items.id` |
| `level` | str | `l1` / `l2` / `l3`（见 4.1） |
| `source` | str | `book` / `weread` / `manual` |
| `retrieval` | str | `vector` / `keyword`（降级路径） |
| `quote` | str | ≤120 字，必须能在 `raw_content` 中命中 |
| `locator` | object | 见 5.3 |
| `can_cite` | bool | = `level == 'l3'` |

### 5.2 证据块（与 B 模块 `evidence[]` 同一口径，此处补 locator 细节）

| 字段 | 类型 | 说明 |
|---|---|---|
| `evidence_id` | str | `ki:{item_id}` / `bs:{book_id}#{chapter_index}` |
| `kind` | str | `knowledge_item` / `agent_summary` |
| `source` | str | `book` / `weread` / `manual` / `agent` |
| `title` | str | 书名 · 章节 / 条目标题 |
| `quote` | str | ≤120 字 |
| `locator` | object | 见 5.3 |
| `retrieval` | str | `vector` / `keyword` |
| `relevance` | float | 余弦；keyword 召回时置 0.55 上限 |

### 5.3 `locator` 结构（按来源分）

| 来源 | 字段 | 跳转方式 |
|---|---|---|
| `book` | `book_id, chapter_index, chapter_title, char_start, char_end` | `/reader.html?book={book_id}&char={char_start}` 高亮区间 |
| `weread` | `book_id, book_title, chapter_uid, chapter_index, chapter_title, range, deep_link, marked_at` | `deep_link` 外链（已存在于 `_collect_book` 的 locator 构造） |
| `manual` | 无 | `/knowledge.html?item={item_id}` |
| `agent_summary` | `book_id, chapter_index, chapter_title` | 只展示，不可跳（通读笔记不对应原文字符） |

### 5.4 同步状态回执（复用 `knowledge/stats` + 补 3 项）

| 字段 | 来源 | 说明 |
|---|---|---|
| `total` | 已有 | 条目总数 |
| `by_source` | 已有 | `{book: n, weread: n, manual: n}` |
| `by_embed_status` | 已有 | `{embedded: n, pending: n, embed_failed: n}` |
| `by_book` | **新增** | `[{book_id, title, source, count, last_at}]`，书级明细（前端折叠） |
| `last_synced_at` | **新增** | 微信读书上次同步时间（`weread/service.status()` 已有该值，合并进来即可） |
| `not_ready` | **新增（计算）** | `pending + embed_failed`，状态条提示"有 N 条暂时检索不到" |

> 注：`not_ready` 一律由代码算，不由前端相加——两处各算一次必然分叉。

### 5.5 新增字段：内置书去重键（轻量方案，不改表结构）

写入前查：`user_id + source='book' + source_item_id=book_id + raw_content=content + locator.char_start/char_end 相同` → 命中则跳过并返回已有条目。

- 实现位置：`app/books/service.py::add_note`
- 不做唯一索引（治历史重复数据 + 迁移风险，2 天窗口承担不起）
- 唯一索引列为 P1 待办，写进 `dev_logs` 待办而不是嘴上说说

## 六、规则

### 6.1 入库与幂等

| 规则 | 内容 |
|---|---|
| 来源白名单 | 只接受 `book / weread / manual` 三种；其他值一律拒绝写入（`ValueError`），防止预留枚举被误用 |
| 微信读书幂等 | `source_item_id` 精确匹配，**软删的也算已存在**（保持现有约定） |
| 内置书幂等 | 5.5 的四元组查重；命中返回 `already_exists=true` + 既有 item_id，前端提示"这条已经存过" |
| 内容格式 | 想法拼进 `raw_content`（`\n\n【我的想法】`），保证语义检索能命中"你的理解"——沿用现有约定，不改 |
| 向量化失败 | 置 `embed_failed`，不阻断入库；进入关键词降级召回 |

### 6.2 可用性判定（进建议池的硬条件）

```
can_cite(item) =
      item.is_deleted == False
  AND item.user_id == 当前用户
  AND len(quote(item)) > 0                      # quote 抽得出
  AND quote ⊂ item.raw_content                  # 校验命中，不是模型编的
  AND (level == l3)                             # locator 完整（manual 允许 locator 为空但 item_id 可跳）
```

不满足 `can_cite` 的条目**可以出现在"库里有相关内容但不是依据"的提示里，但绝不能进 `basis_item_ids`**。

### 6.3 引用与溯源

| 规则 | 内容 |
|---|---|
| 每建议至少 1 条 L3 依据 | 否则走 B 模块的 `insufficient_evidence` |
| 依据条数上限 | 每条建议 ≤5 条证据（多了用户不会看） |
| 同书去重 | 同一本书的证据最多 2 条（防"一本书撑起全部建议"） |
| 展示顺序 | 用户划线/笔记在前，智能体通读在后（用户内容优先） |
| 不可跳转的证据 | `agent_summary` 显示"通读笔记"标签，无跳转按钮，避免用户点了没反应 |

### 6.4 未入库判定

| 规则 | 内容 |
|---|---|
| 书名提取 | 优先 `《…》` 书名号；其次与库内 `books.title` / `source_locator.book_title` 做包含匹配 |
| 命中判据 | 书名完全相同或互为包含（≥4 字）才算命中，防"原则"命中"原则与边界" |
| 未命中行为 | 明确告知 + 给两条出路（同步 / 口述后记一条）；**不调用模型生成任何该书内容** |

## 七、异常情况处理

| # | 场景 | 触发 | 系统行为 | 用户看到 |
|---|---|---|---|---|
| A-E1 | 库为空 | `count_active == 0` | 不进建议流程 | "库里是空的。先记一条，或同步微信读书" |
| A-E2 | 条目未向量化 | `embed_status != embedded` | 降级关键词召回，证据标 `retrieval=keyword`，`relevance` 封顶 0.55 | 状态条提示"有 N 条还在准备，检索可能不全" |
| A-E3 | 向量化失败 | `embed_failed` | 同上；单条不阻断 | 同上（不逐条报错，避免噪音） |
| A-E4 | quote 抽不出 | `raw_content` 为空/极短 | 该条不可引用，从证据池剔除 | 不出现在依据里（不解释） |
| A-E5 | 重复划词 | 同区间同文本 | 返回既有条目，不新建 | "这条已经存过了" |
| A-E6 | 微信读书同步部分失败 | `failed_books > 0` | 部分成功照常入库，回执如实报数 | "2 本失败（可重试），其余已同步" |
| A-E7 | 微信读书未配置 | `weread_api_key` 为空 | 不出同步按钮，改为引导配置 | "还没连微信读书" + 说明 |
| A-E8 | 书被删除但条目还在 | `books.is_deleted` / 条目 `source_item_id` 指向已删书 | 证据仍可用（内容在条目里），跳转改为"原书已删除" | 依据可看，跳转置灰 |
| A-E9 | 条目被软删 | `is_deleted=true` | 立即从证据池消失；同步**不复活** | 依据里不再出现 |
| A-E10 | locator 越界 | `char_end > full_text 长度` | 视为不可跳转，证据仍可引用（quote 已校验） | 不显示跳转按钮 |
| A-E11 | 未同步书名 | 书名未命中 | 拒绝作依据，**不调模型** | "《X》还没进来，我不能拿它当依据" |
| A-E12 | 大批量同步超限 | `weread_max_items_per_sync` 命中 | 到量即停，如实报"剩下的下次再同步" | "这次同步了 50 条上限，剩余下次继续" |

## 十、我的判断（需要你表态的两点）

1. **A 模块最该做的不是加同步渠道，是把"库里有没有、能不能用、凭什么"三件事说清楚**。现在这三件事混成一个"知识库有 37 条"，用户无法判断建议为什么长这样。
2. **内置书重复划词入库必须在本期修**。它直接污染证据池——同一段话出现两次，建议就会引用两遍同样的依据，看起来像"证据充分"，实际是一条。这是会直接影响可信度的 bug，不是体验优化。
3. 需要你表态的两条：**Q2（去重做到哪一级）** 和 **Q3（未向量化条目能否作为依据）**。前者影响是否要动历史数据，后者影响"检索不全会不会被用户当成功能坏了"。
