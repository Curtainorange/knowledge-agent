## 一、需求理解（10 条）

1. **定位纠偏是第一优先级**：副驾不是专家，不预置结论、不替用户定目标。它只做两件事——把用户的真实问题问出来，把判断依据摆到桌面上。
2. **现有交互顺序是反的**：`greeting.build_opening()` 现在是「读状态 → 直接给建议分支」，5 个分支没有一条采集阅读目标、理解程度、当前疑问。要改成「先确认 → 再建议 → 再复核」。
3. **建议质量差的根因是信号单一**：现有信号只有 `read_progress`、笔记条数、学习事件数、未解冲突数（`l5_orchestrator.BehaviorMetrics`）。没有理解程度信号，就不可能适配不同阅读能力的用户。
4. **"没摘录 ≠ 没理解"必须在模型层显式建模**：现在 L5 把低摘录直接当归因证据。要引入「已掌握豁免」与「反证信号」两个概念，否则诊断必然误伤老读者。
5. **冲突检测停在"发现"，没走到"解释"**：`ConflictJudgment` 只有 `relation / conflict_type / detail / suggestion` 四栏，`suggestion` 是自由文本，所以模型只能写"建议自行安排对谈"。缺的是归因结构（前提、定义、边界、证据）与场景指引。
6. **认知缺陷要能被打断和否认**：单轮判定 + 不可撤回 = 用户只能被动接受。要多轮探查（先问再判），并且判定结论可被用户推翻，推翻后要收敛。
7. **阅读计划的问题不是"排得不好"，是"没依据"**：`generate_plan()` 把目标 + 前 60 条 item id 丢给模型，一次性出 `week_index + subject`。没有单周负荷上限、没有任务时长、没有复习点、没有兴趣权重，`rationale` 只是一段话。
8. **通读对比要用已有的结构化笔记，不要重读原文**：`read_whole_book()` 已经产出 `chapters_note[{topic, gist, points}]` + 全书总评，这是做跨书对齐的现成原料，重读两本书的成本和时延都不可接受。
9. **依据分级是硬约束，不是文案修饰**：知识库条目 / 智能体通读笔记 / 外部推荐，三者在数据结构和 UI 上必须分开标注。外部推荐不许伪装成"你的知识库说的"。
10. **2 天不可能把 4 个 P0 做成完整版**：只能做成"可演示的闭环 + 测试全绿"。哪些降级、哪些砍掉，我在第四节给明确取舍。

## 三、分模块修改方案

### A. 知识库同步与基础交互（P0 地基）

| 要素 | 内容 |
|---|---|
| 现状问题 | ① 建议不可溯源：卡片只给结论，不告诉用户用了哪几条知识条目；② 同步状态不透明，用户不知道哪些内容真的进了库；③ `greeting.collect_state()` 只读 5 个计数，不采集任何阅读上下文；④ 现有 `Conversation.state` 只有 `idle`，`messages` 是纯 JSON 列表，没有结构化槽位。 |
| 修改目标 | ① **"未入库内容不能作为建议依据"做成代码级门禁**，不靠提示词约束；② 每条建议可展开看到依据条目并可跳转原文；③ 同步状态可见（按来源分：书 / 划线 / 想法 / 全文）；④ 会话具备结构化「阅读上下文槽位」。 |
| 用户交互流程 | 进入对话 → 同步状态条显示"已同步 N 本 / M 条划线"（不足时提示去同步）→ 开场只问一个问题 → 用户回答落槽（见 B）→ 后续所有建议卡底部带「依据 N 条」。 |
| 规则/算法/数据接口影响 | ① `Conversation` 增 `reading_context` JSON：`{book_ids, goal, self_level, question, updated_at}`；② 新增 `app/agent/grounding.py`：唯一依据装配入口 `build_evidence(user_id, query) -> Evidence(items, missing)`，所有 LLM 调用的 user prompt 必须由它拼，**禁止直传裸文本**；③ `cards.py` 全部卡片增 `evidence` 字段：`[{item_id, title, source, locator, quote, basis}]`，`basis ∈ {knowledge_item, book_fulltext, agent_summary}`；④ `weread/service.py` 的 `SyncResult` 增 `by_kind` 明细；⑤ 新增 `GET /api/v1/knowledge/sync-status`。 |

### B. 主动建议与阅读效果确认流程（P0，最重）

| 要素 | 内容 |
|---|---|
| 现状问题 | 开场 5 个分支（未解冲突 / 有目标无计划 / 有计划 / 有积累 / 空库）全部是"直接给下一步动作"，一条都不问用户要什么；建议基于阅读记录而非理解程度；从未回访建议效果，形成"建议-执行"信息黑洞。 |
| 修改目标 | 把交互改成 4 步闭环：**探明意图 → 复述确认 → 有限建议 → 效果回访**。硬规则：槽位未填不出建议（最多给 1 个澄清问题）。 |
| 用户交互流程 | ① 开场发「阅读入口卡」（kind=`reading_intake`）：正在读什么 / 这次想解决什么 / 这块你掌握到哪一步（首次接触·读过一遍·能讲给别人），全为可点选项 + 跳过；② 用户作答后助手复述一句"我理解你要解决 X，基础是 Y"，用户可点「不对，是……」纠正；③ 出建议：**最多 2 条**，每条必须含 `依据 / 预期效果 / 怎么验证有没有用`；④ 建议后置一句"这个方向对吗"；⑤ 用户执行后（或 24h 后）发「效果回访卡」（kind=`effect_check`）：读完了吗 / 能复述核心吗 / 卡在哪。 |
| 规则/算法/数据接口影响 | ① `turns.py` 新增 `suggestion_gate(user_id)`：`reading_context` 缺 `goal` 或 `self_level` → 只允许发澄清卡，`WIRED` 建议类能力全部被拦；② 新增 `app/agent/comprehension.py`：`judge_recall(user_text, item) -> {covered[], missed[], confused[]}`，用 `JSON_TASK_TYPES` 白名单新任务类型 `recall_judge`；③ 新增表 `comprehension_probes`（`id, user_id, item_id, round, self_level, recall_text, covered, missed, source, created_at`）；④ 建议密度由 `self_level` 决定：`first` → 单点 + 类比 + 少术语；`once` → 结构 + 反例；`teach` → 边界 + 争议；⑤ `cards.py` 新增 3 个 kind：`reading_intake` / `suggestion` / `effect_check`。 |
| 页面展示要求 | `web/app.html` 增 3 类卡片渲染；`reading_intake` 用 3 行单选（按钮组，不输文本框）；`suggestion` 卡内每条建议分三行：做什么 / 为什么 / 怎么验证；`effect_check` 卡带「跳过」；`web/assets/style.css` 只加样式，不改结构。 |
| 验收标准 | AT-B1：`reading_context` 为空时请求建议 → 只返回澄清卡，不产生任何建议文本（测试断言）；AT-B2：任一次回复中建议条数 ≤2，且每条三要素齐全；AT-B3：`effect_check` 有回答时写入 `comprehension_probes` 至少 1 行；AT-B4：同一问题在 `self_level=first` 与 `teach` 下，建议文本的术语密度（专业词命中数）差异显著（≥30%），证明真的适配了；AT-B5：开场第 0 轮不含任何具体行动建议（只有问题）。 |

### D. 观点冲突归因分析（P0）

| 要素 | 内容 |
|---|---|
| 现状问题 | `ConflictJudgment` 只有 `relation / conflict_type / detail / suggestion / confidence`，`Conflict` 表同样只有 `detail / suggestion` 两个自由文本。产出只能是"两本书说法对立，建议你对谈一下"——解释了现象，没解释原因，也没告诉用户什么时候各按各的用。 |
| 修改目标 | 把冲突从"发现对立"升级到"解释对立 + 给出适用边界"：① 归因到 6 类原因（前提假设 / 概念定义 / 适用边界 / 证据来源 / 样本范围 / 时效失效）；② 给双方各自成立的条件；③ 给一条可验证判据（用户自己能验）。 |
| 用户交互流程 | 冲突卡右上「为什么会冲突」→ 展开归因区（4 栏：双方前提 / 分歧性质 / 各自适用的场景 / 一条可验证判据）→ 底部三选：A 更对 / B 更对 / 各有适用场景 → 选择写入 `user_state` 与偏好 → 若选"各有适用场景"，提示是否把两个场景写进学习计划。 |
| 规则/算法/数据接口影响 | ① `conflicts` 增 `attribution` JSON（`cause_type, premise_a, premise_b, boundary_a, boundary_b`）、`scene_guidance` JSON（`[{scene, follow, reason}]`）、`probe` JSON（`{question, how_to_check}`）、`attributed_at`；② 新增 `AttributionDraft`（Pydantic）+ `task_type="attributing"`，**独立调用**，不扩 `ConflictJudgment`（避免主判定精度下降）；③ 触发策略：仅 `relation ∈ {矛盾, 断层}` 且 `confidence ≥ 0.6` 才归因；新冲突异步、历史冲突点击时惰性；④ 归因输入 = 双方 `claim.statement` + 各自 `knowledge_item.raw_content` 片段（≤800 字/侧），多送 `title/author`；⑤ `conflict_view.py` 的 `ConflictBrief` 增 `has_attribution`，避免带长文本进开场。 |
| 页面展示要求 | `web/conflicts.html` 每条冲突卡加「归因」折叠区（默认收起，点开才请求）；对话内联 3 行摘要：为什么对立 / 什么时候听 A / 什么时候听 B；`attributed_at` 为空时显示「分析这处冲突」按钮（避免全量预计算）。 |
| 验收标准 | AT-D1：归因结构化 5 个必填项齐全，缺任一项 → 返回 `degraded` 不落库；AT-D2：只对 `矛盾/断层` 且 `conf ≥ 0.6` 触发（测试断言不会对"互补/无关"调模型）；AT-D3：归因失败不影响冲突卡展示（原卡仍可用，仅为空）；AT-D4：同一冲突重复点开 N 次只产生 1 次模型调用（`attributed_at` 幂等）；AT-D5：`scene_guidance` 至少 2 条，每条含 `scene + follow + reason` 三字段（否则视为不合格输出）。 |

### E. 认知缺陷多轮判断与延伸推荐（P0，建议降级）

| 要素 | 内容 |
|---|---|
| 现状问题 | ① 信号只有行为统计（完成比 / 周活跃 / 闲置天数 / 未解冲突数），**把"没摘录"直接当"没理解"**；② 单轮出结论，不问用户，用户不能否认；③ `DiagnosisDraft` 无"反证"字段，模型只会往"你有问题"的方向归因；④ 没有同类书关联与延伸推荐，诊断止于"你要改"。 |
| 修改目标 | ① 先问再判（≤2 问），把"已掌握未摘录"作为独立假设；② 诊断输出必须同时给「支撑信号」与「可能不成立的情况」；③ 用户可推翻，推翻后 7 天收敛；④ 延伸推荐分三级标注依据。 |
| 用户交互流程 | 有明确信号时进对话 → 先发「探查卡」（2 问：这块之前接触过吗 / 用一句话说说核心，可跳过）→ 答案落 `comprehension_probes` → 出诊断卡（结论 / 依据 / 可能不成立 / 建议）→ 用户可「采纳」「不认同」→ 采纳进计划，不认同记偏好并收敛。 |
| 规则/算法/数据接口影响 | ① `BehaviorMetrics` 增 `excerpted_ratio`、`probe_coverage`、`self_reported_familiar`；② `DiagnosisDraft` 增 `evidence_points[]`、`counter_signals[]`、`probe_used`；③ `calibrate_confidence()` 把 `probe_coverage` 当一致性因子：**未做探查 → 置信度上限 0.6**；④ 反证规则（代码判定，不交模型）：自评"熟悉"但复述 `missed` 命中 ≥2 个核心点 → 才判"理解缺口"；自评"熟悉"且复述覆盖 → 判"已掌握，仅缺整理"，不报警；⑤ 推荐复用 `book_orchestrator.recommend()`，输出条目增 `basis ∈ {library, agent_summary, external}` + `external_source`；⑥ 新增 `diagnosis_suppression` 逻辑（按 `pattern` + 时间窗 7 天）。 |
| 页面展示要求 | `web/l5.html` 诊断卡改为 4 栏：结论 / 依据（列出 signal + probe 原文）/ 可能不成立的情况 / 建议；推荐区分两组，组标题固定文案「来自你的知识库」与「外部推荐（未入库，仅作参考）」，外部项带来源名。 |
| 验收标准 | AT-E1：未做探查 → `confidence ≤ 0.6`（测试断言）；AT-E2：用户点"不认同"后 7 天内同 `pattern` 不再产出；AT-E3：100% 推荐项带 `basis`，且 `external` 项在卡片里位于独立分组；AT-E4：构造"自评熟悉 + 复述覆盖"→ 输出不是缺陷结论（反证分支生效）；AT-E5：`evidence_points` 至少 2 条且可追溯到具体信号或 probe。 |

### F. 阅读计划生成逻辑与规则透明化（P0）

| 要素 | 内容 |
|---|---|
| 现状问题 | `generate_plan()` 只把 `goal + priority + deadline + 前 60 条 item_id + 知识上下文`丢给模型，一次性输出 `week_index + subject`。缺：单周负荷上限、任务预估时长、复习点、兴趣权重、新知识/复习配比；`rationale` 是一段自由文本，用户无法判断"凭什么这么排"。 |
| 修改目标 | **规则在代码里算，模型只做内容填充**（与 L4/L5 现有原则一致）：① 所有排期约束显式化、可调；② 计划页展示"依据"面板；③ 用户改参数可即时重排。 |
| 用户交互流程 | 设定目标 → 生成计划前先出「排期参数卡」（每周可用分钟 / 同时读几本 / 复习强度，默认值带解释）→ 生成 → 计划页顶栏「计划依据」（6 条规则 + 参数，可展开）→ 每个任务显示预估时长与"为什么排这周" → 改参数 → 重排（版本 +1）。 |
| 规则/算法/数据接口影响 | ① 代码侧规则引擎：`weekly_minutes`（默认 300）、`parallel_books`（默认 2）、`task_minutes ≤ weekly_minutes / parallel_books` 硬切分、复习点 1/3/7/14 天、兴趣权重按标签命中频次、新:复 = 2:1（第 3 周起 1:1）；② `GeneratedPlan.tasks[]` 增 `estimated_minutes / kind(read·review·discuss) / source_item_ids / rationale`；③ `plan_tasks` 表增同名列（可空，兼容旧数据）；④ `plan.content.rules_snapshot` 存本次所有参数与实际生效规则（用于"依据"面板与复盘）；⑤ `generate_plan` 与 `decide_adjustment` 两处都走同一个 `PlanRules` 对象，禁止两套参数；⑥ 超限处理：模型给的时长超上限 → 代码切分而非重试模型。 |
| 页面展示要求 | `web/l4.html`：顶栏「计划依据」抽屉，6 条规则一行一条，右侧显示当前参数值并可改；任务行显示 `第 N 周 · 阅读 · 40 分钟`；时长超标或超周负荷时红色标注；「为什么排这周」hover 显示 `rationale`。 |
| 验收标准 | AT-F1：生成后 `rules_snapshot` 6 项齐全（缺项即 fail）；AT-F2：单周 `sum(estimated_minutes) ≤ weekly_minutes`，硬断言，超限即 fail；AT-F3：把 `weekly_minutes` 减半后重排，任务总时长按比例下降（±15% 容差）；AT-F4：每个任务 `rationale` 非空且引用至少 1 条规则名；AT-F5：旧计划（无新字段）读取不报错，页面显示"—"而非崩溃。 |

## 五、我的判断（需要你表态的一点）

2 天做 4 个 P0 的"完整版"不现实，**硬做只会得到 4 个半成品**。我建议的取舍是：

- **死守**：B（交互顺序）与 A（依据可溯源）——这是会议纪要里最核心的批评，也是唯一能立刻被感知的改动。
- **死守**：D（冲突归因）与 F（计划依据）——这两项有明确的结构化产出，做完即可演示、可验收。
- **降级**：E 只做"已掌握豁免 + 单轮探查 + 推荐分级"，多轮校准进 P1。理由：多轮需要探查数据积累，2 天内拿不到真实样本，做了也验不出效果。
- **降级**：C 只做"两本已通读的书对比"；第三方 API 只出评估表。
