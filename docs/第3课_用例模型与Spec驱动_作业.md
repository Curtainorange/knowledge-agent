## 一、如何理解"用例分析本质上是一种功能分解技术"（课件 P24）

### 1.1 这句话在说什么

**功能分解**＝把复杂系统"分而治之"，拆成一组较小的、可逐一分析与实现的功能单元。

用例分析做的正是这件事，只是**分解的单位**特殊：

- 课件 P22 对用例的定义：系统为响应参与者引发的一个事件而执行的一系列处理，**该处理为参与者产生一种有价值的结果**。
- 于是"分析整个系统"＝把系统**分解**为一组用例，每个用例回答"**谁**（参与者）想通过系统完成**什么目标**"。
- 分解还会继续向下衔接面向对象：从每个用例的交互过程描述中**发现类**（特征和行为）（课件 P24；网盘示例 P28——从"创建分享"用例发现文件、分享链接、容量账户的对象职责）。

### 1.2 "本质上"是，但与结构化功能分解并不等同

| 维度 | 结构化方法的功能分解（功能树） | 用例分析的功能分解 |
|---|---|---|
| 分解依据 | 按系统内部的模块/处理步骤自顶向下拆 | 按**参与者的用户目标**拆 |
| 视角 | 白盒、面向实现 | 黑盒，站在系统外部看功能（P24） |
| 触发方式 | 无（静态功能层次） | 由**外部事件**触发（P24） |
| 粒度判据 | 子功能、子过程 | **有价值的完整结果**；界面动作与操作步骤不构成独立用例（P27） |
| 产出衔接 | 结构图、流程图 | 用例图＋用例描述 → 发现类（P24） |

**结论**：用例分析继承了"分而治之"的分解思想，所以说它"本质上是一种功能分解技术"；但分解的坐标从"功能层次"换成了"参与者目标"，因此它是一种**以用户目标为单位、天然可追溯到价值与验收**的功能分解。

### 1.3 举例

**例 1｜银行业务系统（课件 P23）**
"银行业务"这个大功能域被分解为：开户、查询账户余额、取款、转账……每一条都是储户（参与者）的一个完整目标，而不是按"账户管理模块 → 校验子模块 → …"去拆内部结构。

**例 2｜超市收银系统（课件 P26–27）**
收银台终端分解出的用例是"**办理商品结算**"（用户价值：形成正确的购买清单并交付凭证）；而"录入商品代码""显示价格""打印购物单"只是这个用例**基本流里的步骤**，不是独立用例——"界面动作不是独立用例的充分理由"。这说明分解的"切法"是按目标切、不按步骤切。

**例 3｜本组项目"认知副驾"**
"个人知识学习智能体"被分解为参与者（学习者）的一组目标级用例：

| 用例（能力层） | 学习者目标 | 可独立验收（举例） |
|---|---|---|
| L1 模糊意图挖掘 | 忘了关键词也能找回收藏 | 只给模糊线索能发起多轮澄清 |
| L2 隐性冲突检测 | 发现知识体系里的"内战" | 低置信度冲突不入库（见下文 BR-L2-01） |
| L3 认知助产 | 得到"该问但没问"的追问 | 追问数 ≤ 3 且指向缺失主题 |
| L4 路径自我修正 | 计划赶不上变化时自主重排 | 连续 3 天无行为触发偏离检测 |
| L5 学习偏误诊断 | 解释行为背后的"病根" | 诊断含归因链而非只给完成率 |

每个用例都对应一个可验收的用户目标——这正是功能分解"分而治之"之后，每块仍能独立分析、实现、验收的体现。

### ② 选一个角色：目标及"对谁的资源可操作"

选角色：**学习者（知识所有者，登录用户）**。

| 角色 | 目标 | 资源与权限（对谁的资源可操作） | 依据 |
|---|---|---|---|
| 学习者 | 发现**本人**知识库中的隐性观点冲突，避免带着矛盾的认知继续学习 | 仅可触发扫描、查看、反馈**本人 user_id** 产生的冲突与条目；**不可**访问、修改其他用户的任何冲突记录或知识条目 | 服务端从 JWT 解出 user_id 并按其过滤（`app/api/deps.py` 的 `get_user_id`）；`l2.py` 全部端点都要求登录用户身份 |

对照课件 P20 角色目标表的写法：**先有真实交互，再确定参与者与权限**；AI 建模助手、内部数据库、LLM 网关都是内部实现，不自动成为运行时角色（P20 红字）。

## 三、退出卡（课件 P58）：指出错误、给证据、说修法

题目：AI 说"**分享接收者可删除文件，上传必须自动创建分享**"。
（本题为课件**网盘案例**，REQ/BR/UC 编号均指课件中的编号体系。）

### 3.1 错误一："分享接收者可删除文件"（按 H1 审查单格式，课件 P50）

| 字段 | 内容 |
|---|---|
| 错误 ID 与位置 | E-01｜用例图：**分享接收者 —（关联）→ 删除文件** 这条关联线 |
| 违反的规则/需求编号 | ① **BR-02**：只能管理自己的文件——每次服务端核验归属，**接收者不得删除/修改**（课件 P44 规则表；P47 验收例"甲删除乙的文件 → 拒绝、数据不变，依据 BR-02"）；② **BR-08**：只读访问不产生所有权（课件 P37 关系审查表）；③ 课件 P20 角色目标表：分享接收者的资源与权限为"仅该链接指向文件；**不得删除或上传**" |
| 业务影响 | 接收者获得写权限，任何拿到链接的人都能删掉所有者的文件，破坏归属校验这条安全底线 |
| 图应怎样修改 | **删除"分享接收者 → 删除文件"的关联线**；接收者只保留与"凭链接下载"（只读）用例的关联；"删除文件"用例仅保留"文件所有者"一个参与者 |
| 描述表应怎样修改 | 相关用例描述的"参与者"字段只保留文件所有者；接收者参与记录的权限改注"只读"；新增失败验收例"接收者尝试删除分享文件 → 拒绝、数据不变（依据 BR-02/08）" |

### 3.2 错误二："上传必须自动创建分享"

| 字段 | 内容 |
|---|---|
| 错误 ID 与位置 | E-02｜用例图：**UC-01（上传）«include» UC-04（创建分享）** 这条包含关系 |
| 违反的规则/需求编号 | ① **REQ-01 与 REQ-04 是两个独立用户目标**——课件 P37 关系审查表首行："上传 include 创建分享 → **删除**，REQ-01/04 是独立目标"；② **BR-05 不要求自动分享**（课件 P50 审查单示范 E05 的证据项）；③ 课件 P32："**上传完成不意味着必须分享**；本网盘中上传与创建分享是独立目标"（P34 同时说明：上传后的分享是另一目标，不因发生在后面就成为 extend） |
| 业务影响 | 所有上传都被迫进入分享行为，违背用户意图，并产生用户没有请求的分享链接，扩大权限暴露面 |
| 图应怎样修改 | **删除 UC-01 «include» UC-04 这条包含关系**（课件 P58 红字预期："删错误关联与 include"）；UC-04 仅保留"文件所有者 → 创建分享"关联 |
| 描述表应怎样修改 | 按 P50 修正意见：**取消该 include；UC-01 的后置条件改为"仅新增本人文件，不产生任何分享"**；UC-01 基本流中删除"创建分享"步骤；**UC-04（创建分享）由所有者的独立请求触发**；在 H1 审查单中记录 E-02 及证据编号 |

### 3.3 追问：想把分享默认 24 小时改成 30 天，谁有权确认？需更新哪些材料？

**定性**：这是**业务变更**（修改 BR-05 的规则值），不是模型修订——两者走不同审批路径（课件 P53 人工决策表）。

**谁有权确认**：**需求负责人（业务方）人工批准**。AI 可以提出变更方案和影响分析，但"AI 能提出方案，**不能代替需求负责人批准业务变化**"（课件 P53）；P58 红字同样强调"业务变更须人工批准"。

**需更新的材料**（课件 P53"业务方希望改 30 天"一行）：

1. **Spec 新版本**（v0.1 → v0.2）：BR-05 有效期 24 小时 → 30 天，记录变更理由、影响与批准人；
2. **模型**：用例图（若图上标注了有效期）与相关用例描述表（如"创建分享"中对 BR-05 的规则引用）；
3. **验收与追踪**：追踪矩阵、验收例边界值同步更新——"恰好 24 小时"类边界例改为"恰好 30 天（可用）/ 30 天＋1 秒（拒绝）"，并保留"已撤销 → 拒绝"等原有用例（对应课件 P47 验收例风格）。

**对照情形**（课件 P53 第一行）：如果只是 **AI 把 24 小时误写成"永久"**，那是模型错误而非业务变更——按**已有 BR-05** 修正模型即可，**Spec v0.1 保持不变**，只更新 R2 模型、描述与修改记录。
