# 下一步建议：让项目「被看见」

> 2026-09-21。写这份的原因是：你反馈「项目不突出、功能有些少」。
> 本文的实测数字来自当前代码库（13 个页面 / 37 个接口路径 / 15 张表 / **353 项测试**）。

## 一、先纠正一个判断：功能不少，是入口太窄

现状盘点——已经建成的能力：

| 类别 | 已有 |
|---|---|
| 能力层 | L1 挖掘、L2 冲突、L3 简报、L4 路径修正、L5 诊断，**五层全部有接口、有页面、有测试** |
| 入口 | 对话工作台（`web/app.html`） |
| 阅读 | txt / epub / pdf 上传解析、滚动阅读器、划词入库、阅读日志 |
| 外部 | 微信读书官方接口同步（划线 + 想法） |
| 底座 | JWT 认证 + 刷新、仓储层强制 user_id 过滤、向量检索（本地 BGE，可降级）、成本计费、事件埋点、推送与调度、备份与导出 |

**这不是一个「功能少」的项目。** 真正的问题是：

1. **对话工作台只接入了 3 项能力**（`app/agent/router.py` 的 `WIRED_CAPABILITIES` 当前为 `{l1, knowledge_add, chat}`），L2–L5 走的是「去哪儿」引导卡。用户说一句话只能叫动 1 层，另外 4 层要自己点进对应页面——**没点开就等于不存在**。
2. **没有一条「60 秒内看到价值」的路径**。空库进去，五个能力全是零；而任何演示场合都不会有人为了看你演示去读一本书。
3. **README 在自我贬低**。开头写「P0 骨架」「验证一次模型调用可追踪可计费」，页面表只列 5 个（实际 13 个），目录结构里还写着 capabilities 是「占位模块（P0 只建边界）」。别人对你的第一印象，来自这几行字。
4. **没有差异化叙事的收口**。五个能力是并列的，没有一个是「主打」。

## 二、定位一句话（建议收窄）

你自己在 `认知副驾.md` 里已经写出了最好的一句，应该把它放到 README 第一行和每次演示的开场白：

> **信息系统帮你「管住」已知；认知副驾帮你「照亮」未知，并「逼你」修正。**

如果只能留一句更短的卖点，建议押在 L2：**「别人帮你记住想法，它帮你发现想法在打架。」**
理由：存、搜、总结、问答是同类产品的地板功能；**敢指出用户自己的知识体系内部矛盾**，才是这套东西不可替代的地方。

## 三、六条建议（按性价比排序）

### P0-1 把 L2–L5 接进对话工作台（不加任何新能力，只是「接线」）

- 改动点：`app/agent/copilot.py` 的 `_handlers()` 补处理器；`app/agent/router.py` 的 `WIRED_CAPABILITIES` 同步放开
  （两者由 `tests/test_agent_router.py` 强制一致）。
- 每个能力必须在 `CAPABILITY_CATALOG` 里补一条**能被本地规则命中**的示例句（测试会逐条验证），例如：
  - 「我最近记的东西有没有互相矛盾？」→ L2 冲突卡
  - 「帮我生成今天的简报」→ L3
  - 「我计划是不是偏了？」→ L4 偏差检查
  - 「我最近的学习状态怎么样？」→ L5 诊断
- **注意：这件事今天已列入 `dev_logs/2026-09-21.md` 的待办，且已识别出两个前置障碍**，直接照做会踩：
  1. **耗时**：L2 扫描、L3/L5 生成要十几秒到几分钟，而当前对话是**同步非流式**——直接接进去就是一个转圈几十秒的白屏。
     接之前要先定**异步 + 进度反馈**方案（先返回「已在生成」卡，完成后回流结果）。
  2. **卡内操作**：L2/L5 的结论需要「采纳 / 忽略」这类动作，涉及 `PATCH` 回写，需要补一套**卡片动作回流协议**。
- **因此建议的接入顺序（由易到难）**：
  1. **L4**（读计划、查偏差，以查询为主，最接近现在已接通的 L1 形态）
  2. **L3**（生成慢，但用户对「正在生成简报」有天然预期，是最容易接受异步文案的一个）
  3. **L3 之后再做 L2 与 L5**（这两个同时要异步和卡内操作，一起做省一次协议设计）
- 收益：用户感知到的能力从 1 层变成 5 层。**这是把「功能少」变成「功能多」的最低成本动作。**


### P0-2 重写 README 前三屏

- 删掉「P0 骨架」「占位模块」「最小可运行」这类措辞；页面表补齐 13 个页面。
- 补一节「能力全景」，用一句话讲清每层解决什么问题（直接搬 `认知副驾.md` 的五层表）。
- 补一节「60 秒怎么看到效果」（见本文第五节）。
- 补实测数字：测试 353 项、接口 37 个、表 15 张、页面 13 个。

### P1-3 把冲突页做成招牌页

`web/conflicts.html` 目前是列表形态。建议改成「证据对照」：

- 左侧放「你 3 月 12 日记的那条」原文与出处，右侧放「你 5 月 8 日写的想法」原文与出处，中间标明冲突类型（事实冲突 / 立场反转 / 概念混用）。
- 每条冲突给三个一键决策：保留前者、保留后者、都保留（标注为「我改变了看法」）。
- 决策结果回写事件流——它同时是 L5 诊断最优质的输入。
- 收益：这是全项目**唯一别人抄不走的一屏**，也是最容易在演示时让人「哦」一声的地方。

### P1-4 一键演示数据（让价值 30 秒内可见）

- 新增 `scripts/seed_demo.py`：为当前账号灌入一套约 20–30 条的样例知识，**刻意埋好**：3 组互相矛盾的条目、1 个有偏差的学习目标、几条可被 L1 模糊线索命中的长文摘录。
- 前端在空库时给一个「载入演示数据」按钮，没有数据时引导点它。
- 收益：任何人在 30 秒内能看到 L1 到 L5 的完整产出，而不是面对五个空页面。

### P1-5 把 L3 下沉到「正在读的地方」

- L3 现在是独立页面：用户不主动去点，它就不存在。
- 建议在划词入库成功后、以及知识条目展开处，加一个「追问」按钮，就地生成「你该问但没问的问题」。
- 收益：把「一个功能」变成「使用习惯」。

### P2-6 做一页「效果自证」

- 新增 `scripts/eval_retrieval.py`：固定 20 条查询 + 人工标注的正确答案，跑 L1 的 recall@5 与 MRR，输出一张表。
- 同样思路可给 L2 做 10 组标注好的冲突样例，报精确率 / 召回率。
- 把数字写进 README。
- 收益：这类项目被问倒最多的一句是「效果怎么保证」。**有数字和没数字，是两个层级的回答。**

## 四、明确不建议做的事

- **不要再加平台**（番茄小说这类没有官方接口的，接了就是违规加脏数据）。
- **不要再加文件格式**（现有三种已覆盖绝大多数场景）。
- **不要再加新页面**：13 个页面已经是「功能密度偏高、可见度偏低」，再加只会更糊。
- 不要为了「看起来功能多」而把同一能力换个名字再做一个入口——那会稀释主线。

判断标准很简单：**新增的东西，能不能让「一句话 → 一张有用的卡」这条链路更短、更准、更早出现？** 不能就别做。

## 五、60 秒演示脚本（可直接用于汇报 / 答辩）

| 秒 | 动作 | 说什么 |
|---|---|---|
| 0–10 | 打开对话工作台 | 「这是我这两周做的东西：知识学习智能体。一句话就能用。」 |
| 10–20 | 点「载入演示数据」 | 「先灌一套样例，代表一个真实学习者两周的积累。」 |
| 20–35 | 输入「我最近记的东西有没有互相矛盾？」 | 「它找出来的不是重复，是矛盾——这条笔记说 A，那条想法说非 A。」 |
| 35–45 | 点「保留后者，标注为改变看法」 | 「冲突不是要消灭，是要被看见、被决策。决策本身会变成下一层诊断的输入。」 |
| 45–60 | 输入「之前存的那段讲查询优化的内容」 | 「最后，遗忘也能对话：模糊线索就能把它找回来。」 |

**这个脚本要成立，前提是 P0-1 和 P1-4 先做完。** P1-4（演示数据）不可省——空库演示等于没有演示；
P0-1 可以分步：来不及把 L2 接进对话时，**退一步的做法**是演示时从对话里的引导卡直接跳到冲突页操作
（卡片本来就带深链），对话入口只用来演示 L1 的「模糊线索找回」。这样「价值可见」的目标不变，
但省掉了异步与卡内操作这两块协议设计。
