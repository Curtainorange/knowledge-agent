第一部分 · 设计基础

1. 文档说明

1.1 文档目的

本文档在《需求分析文档》需求基线上，给出「认知副驾」系统的完整设计说明，作为设计评审与验收的技术依据。具体承担四项职责：

  1. 论证设计合理性：说明系统为何采取当前架构方案、技术选型的依据、关键决策的取舍与代价。
  2. 界定系统结构：自顶向下描述系统的分层结构、模块职责、依赖关系、数据模型与接口契约。
  3. 声明设计约束：明确系统必须遵守的结构性约束（依赖方向、收口点、隔离规则）及其保障机制。
  4. 建立可追溯性：将每条需求关联到设计章节、实现模块与验证方式，实现双向覆盖核查（§16）。
本文档的表述原则：以设计说明书的陈述式表述记录「系统采用什么方案、为什么这样设计、达成何种质量目标」；不重复罗列可直接从代码读取的信息（字段名、函数签名），而重点说明需要跨模块推导才能得到的结论——设计约束、选型依据、复用结构、边界条件。文档的价值在于界定「约束」与「理由」，而非复述「实现」。

2.1 设计目标与优先级

系统的设计目标按优先级排序如下。当目标之间发生冲突时，以序号靠前者为准——这一优先级顺序是后续所有设计取舍的判据。

G1数据安全与用户隔离用户数据不可丢失、不可越权访问；隔离由结构保障而非编码约定§5.4 §7.3
G2功能性完备五大能力 L1~L5 全链路闭合，用例无缺口§3 §6
G3成本可控单位用户智能能力成本可预测、可归因、有上限§6.3.1 §13.3

G5可维护与可扩展分层解耦、复用充分，新增能力不侵入既有代码§7 §8

设计约束是方案选择的前提条件，分为技术约束与业务约束两类。

2.3 设计视图组织

本文档按 IEEE 1016 的多视图方法组织：同一系统从四个视角分别描述，各视图互补且相互引用。

四个视图的划分依据：功能视图回答「系统能做什么」，数据视图回答「系统的信息基础是什么」，结构视图回答「代码如何组织以支撑前两者」，运行视图回答「系统在时间维度上如何运转」。横切论证则给出选型理由、验证方式与需求覆盖核查。

4.3 依赖方向约束

四条约束（违反即判定设计不合规）：

  1. 依赖必须单向向下：api → agent → domain/llm，反向依赖一律禁止。
  2. domain/ 必须保持独立：不得感知模型层的存在。这使领域模型可被任意上层复用，并支持模型层的独立替换。
  3. llm/ 必须对上层无感知：网关不感知调用来源，仅依据 task_type 决定调用策略。因此新增能力无需修改模型层。
  4. capabilities/ 各能力之间不得互相引用：五大能力必须彼此隔离，仅通过领域层共享数据。这使任一能力可被独立重构或移除。
第 4 条约束的必要性：L1~L5 在业务上高度相关（均依赖知识库与模型调用），若不加以约束，极易产生 l3 调用 l2 内部函数的横向耦合，进而导致「调整 L2 阈值引发 L3 异常」的连锁影响。共享逻辑必须下沉至 domain/ 或 llm/ 层，不得横向互调。

4.5 状态机设计

系统中有三处显式状态机，它们是「数据一致性」的核心保障。

4.5.1 异步任务状态机（TaskRun）

失败状态不直接转入死信的设计理由：任务失败后保留在 pending 状态并递增 attempts，由下一轮轮询自然重试，以 updated_at 作为退避时间锚点（2^(n-1) 秒起、上限 60 秒）。该设计使重试机制无需依赖独立的调度组件，单一轮询循环即可完成全部调度职责。

4.5.2 冲突用户状态机（Conflict.user_state）

4.5.3 诊断状态机（CognitiveDiagnosis.status）

状态机的设计意图：这三处状态机的目的不在于「记录状态」，而在于使系统具备可纠正性——用户的忽略或认可反馈将反向收敛后续推荐结果（误报抑制），从而使智能能力的输出质量随使用过程持续改善。

6.5.1 三条核心机制（app/workers/tasks.py）

- **幂等**：TaskRun.idempotency_key 唯一约束。重复入队由数据库挡回
  （IntegrityError → 视为已存在），不依赖应用层「先查再插」那种有竞态的做法。

  退避用 updated_at 作时间锚点，2^(n-1) 起步、上限 60 秒。
- **死信**：attempts ≥ max_attempts 转 dead 保留现场（last_error），不再自动重试。

结构性保障与约定性保障的差别：约定性保障要求「所有实现都记得附加 WHERE user_id = ?」，其有效性依赖编码自觉，存在遗漏可能。结构性保障则将过滤实现于仓储基类，使遗漏在结构上不可表达——上层无法构造出不经过滤的查询。这是本系统数据隔离设计的核心思路，也对应 §2.1 中 G1 目标优先于 G6 的取舍。

设计收益说明
测试确定性262 项测试全部在 Mock 下运行，不依赖网络、不产生费用、结果可重复

离线可用性无网络环境下可完成全部运行与开发工作
测试成本为零自动化测试不产生模型调用费用
异常场景可控可精确构造「模型返回非法 JSON」「模型超时」等异常输入，用于验证降级路径
设计要点：将 LLMProvider 抽象为接口后，Mock 实现成为与真实实现地位对等的可替换组件，而非事后补充的测试替身。这使系统的可靠性设计（降级、重试、异常处理）能够被确定性地验证，而不仅依赖真实服务的偶然异常。这一性质是本设计可测试性的基础。

结语

本设计说明书的核心设计主张可归纳为四条：

  1. 约束以结构保障，不以约定保障。 越权防护实现于仓储基类、任务幂等由数据库唯一约束保障、模型调用收口于单一网关——通过结构使违规实现方式不可表达，其可靠性高于依赖编码规范的约束方式（§7.3）。
  1. 低成本筛选前置，高成本推理后置。 L2 五级候选漏斗、按任务类型的推理开关、增量扫描标记——所有智能能力的成本控制均遵循「先以规则与数据库筛选，再对少量高价值候选执行模型推理」的原则（§6.4）。
  1. 可降级性优先于峰值性能。 未配置密钥时降级至 Mock 实现、向量模型未就绪时降级至关键词检索、调用失败时执行重试与死信处理——每一处外部依赖均有降级路径，保证系统在各类环境条件下均能运行（§10.3）。
  1. 扩展以追加方式实现，不以修改方式实现。 §7.2 的扩展性验证表明，新增能力仅需修改 2 处既有文件（且均为注册式追加）。任何被迫修改既有能力模块的扩展，均表明存在需下沉的耦合——这是本设计解耦有效性的量化判据。
