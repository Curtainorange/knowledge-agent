第一部分 · 认识这个系统

1. 文档说明

1.1 文档目的

本文档将《需求分析文档》中的需求基线，转化为可直接指导编码的设计方案。它不是产品宣传材料，而是开发者每天要打开的工作参照：

  • 新人照着第 2 章就能把系统跑起来，当天下第一个 commit；
  • 开发者接手一个功能时，能在第 6 章找到这个功能落在哪个文件、依赖哪些下层、不许依赖什么；
  • 评审者能用第 7 章的解耦规则与第 9 章的 DoD 机械化地判断一个 PR 合不合格；
  • 测试工程师能从第 14 章与第 16 章追溯矩阵反查出该功能该测哪些用例。
本文档的取舍原则：凡是能从代码里一读就得到的信息（字段名、函数签名），文档不重复抄写；凡是代码里读不出、或需要跨文件才能推出结论的信息（依赖规则、为什么这样选、复用点在哪儿、边界在哪），文档必须写清。文档的价值在于写清「约束」和「理由」，而不是复述「实现」。

1.3 术语表

术语说明
L1~L5五大能力：L1 模糊意图认知挖掘 / L2 冲突检测 / L3 认知助产 / L4 路径自我修正 / L5 偏误诊断
ModelGateway统一模型网关，全系统唯一出网调用点，负责策略路由、重试、成本埋点
Provider单个模型服务封装（DeepSeek / Mock），实现 LLMProvider 接口
Strategy任务类型 → 调用参数（是否开 reasoning、模型名）的映射条目
Orchestrator编排层，负责单条用例的完整流程编排（L1~L5 各有其一）
Repository仓储，唯一允许碰数据库的层，且强制 user_id 过滤
TaskRun异步任务运行记录，承载幂等键、重试次数、死信现场
幂等键（idempotency_key）业务语义去重键（如「某用户 2026 年第 37 周的冲突扫描」），数据库唯一约束兜底
结构性防越权通过在类型系统 / 仓储基类层面强制过滤，而非依赖开发者自觉
收口（choke point）某类操作在全系统中只允许存在一处实现的性质
DoDDefinition of Done，完成的定义（见 9.4）

2. 开发者上手路径

本章回答一个问题：一个新人拿到这套代码，第一天该怎么做。

2.1 五分钟跑起来

# ① 获取代码
git clone <repo-url> && cd 知识学习智能体

# ② 建虚拟环境（Python ≥ 3.12）
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# ③ 装依赖（含开发依赖）
pip install -e ".[dev]"

# ④ 启动（无需任何 API KEY 即可完整跑通）
uvicorn app.main:app --reload --port 8000

打开 <http://127.0.0.1:8000/> 即可看到登录页，注册一个账号即可体验全部五大能力。

无需 API KEY 是本项目的刻意设计：未配置 DEEPSEEK_API_KEY 时，ModelGateway 自动路由到 MockProvider（确定性、零成本、零网络）。这让新人不花钱、不配环境、不申请凭证就能跑通全链路，也保证了测试的确定性与可重复性（见 §10.3）。

可选：配置真实模型以获得真实智能

export DEEPSEEK_API_KEY=sk-xxxx        # Windows PowerShell: $env:DEEPSEEK_API_KEY="sk-xxxx"
uvicorn app.main:app --reload --port 8000

可选：启用本地向量语义检索（首次需下载模型，约 100MB）

export EMBEDDING_BACKEND=local
# 国内网络可加镜像：
export HF_ENDPOINT=https://hf-mirror.com

未启用时，检索自动降级为关键词通道，功能不缺失、只是召回质量下降。

2.2 跑测试（提交前必做）

pytest                    # 254 项，应全绿
pytest tests/test_l2.py   # 只跑冲突检测
pytest -k "conflict"      # 按名称过滤

node --check web/assets/app.js

2.5 第一次改动的推荐路径

新人不要一上来就改 L2 冲突检测（那是全系统最复杂的算法）。推荐的第一次改动顺序，难度递增：

顺序练手任务涉及层为什么适合
1给 GET /api/v1/knowledge/items 加一个排序参数api → repository单层穿透，看清「接口→仓储」的关系

3新增一个异步任务（如「每日统计用户新增知识数」）workers + domain理解幂等键与任务注册表
4给 L5 诊断加一个新的行为模式识别规则agent → llm理解编排层与网关的关系（提示词改动也要走网关）

4.2 架构风格：分层 + 端口适配 + 收口

本系统采用三层主体 + 一个横切收口的结构：

层次职责允许依赖禁止依赖
表现层 api/HTTP 协议转换、参数校验、鉴权、序列化编排层、领域层、core❌ 不许含业务逻辑
❌ 不许直接调 llm/
编排层 agent/单条用例的流程编排、多步协调、降级决策领域层、llm/、retrieval/、workers/❌ 不许直接操作 Session（须经仓储）
领域层 domain/实体定义、持久化、数据完整性core❌ 不许依赖 llm/、api/
❌ 不许依赖 agent/
支撑层 llm/ retrieval/ workers/ core/提供被上层调用的能力core❌ llm/ 不许依赖 agent/

两个关键收口（choke point）——本架构最重要的设计决策：

收口含义工程收益
模型调用收口于 ModelGateway全系统只有这一个地方发 LLM 请求换供应商改 1 个文件；成本/重试/日志在一处统一，不会漏埋点
数据库访问收口于 Repository全系统只有仓储层碰 Session越权防护在基类一处实现，12 个仓储自动继承，不可能漏

四条铁律（违反即 PR 驳回）：

  1. 依赖必须单向向下：api → agent → domain/llm。反向依赖一律禁止。
  2. domain/ 必须保持纯净：它不许知道「有 LLM 这回事」。这样领域模型可以被任何上层复用，也便于未来替换模型层。
  3. llm/ 必须对上层无感知：网关不知道谁在调它，只按 task_type 决定策略。这样新增能力无须改模型层。
  4. capabilities/ 内部互不 import：五大能力必须彼此隔离，只通过领域层共享数据。这样任何一个能力可以独立重构甚至删除。
为什么第 4 条重要：L1~L5 在业务上高度相关（都要用知识库、都要调模型），很容易写出 l3 调 l2 的函数 这种耦合。这会立刻产生「改 L2 阈值导致 L3 崩」的连锁效应。共享逻辑必须下沉到 domain/ 或 llm/，而不是横向互调。

4.5 状态机设计

系统中有三处显式状态机，它们是「数据一致性」的核心保障。

4.5.1 异步任务状态机（TaskRun）

stateDiagram-v2
    [*] --> pending: enqueue（幂等键唯一约束）
    pending --> running: worker 取出
    running --> succeeded: 执行成功
    running --> pending: 失败且 attempts < max<br/>（退避后重试）
    running --> dead: 失败且 attempts ≥ max<br/>（保留 last_error 现场）
    pending --> pending: 重复入队被 DB 挡回<br/>（视为已存在）
    succeeded --> [*]
    dead --> [*]
为什么失败不直接转 dead：失败留在 pending 并递增 attempts，下一轮轮询自然重试，用 updated_at 做退避时间锚点（2^(n-1) 秒起、上限 60 秒）。这样重试不需要额外的调度器，一个轮询循环就够。

4.5.2 冲突用户状态机（Conflict.user_state）

stateDiagram-v2
    [*] --> unseen: 扫描产出
    unseen --> accepted: 用户认可（触发「转学习计划」扩展用例）
    unseen --> ignored: 用户忽略
    ignored --> ignored: 同类型累计 ≥N 次<br/>→ 该类型不再推荐
    accepted --> [*]

4.5.3 诊断状态机（CognitiveDiagnosis.status）

stateDiagram-v2
    [*] --> pending: L5 诊断产出
    pending --> accepted: 用户认可
    pending --> rejected: 用户否决
    accepted --> [*]
    rejected --> [*]
反馈闭环的意义：这三处状态机不是为了「记录状态」，而是为了让系统能被用户纠正——用户的忽略/认可会反过来收敛后续推荐（误报抑制）。

  ▼

  ▼

  ▼

  ▼

6.5 异步任务层（app/workers/）

6.5.1 三条核心机制（app/workers/tasks.py）

- **幂等**：TaskRun.idempotency_key 唯一约束。重复入队由数据库挡回
  （IntegrityError → 视为已存在），不依赖应用层「先查再插」那种有竞态的做法。
- **重试**：失败不改状态为 dead，而是留在 pending、attempts+1，下一轮轮询再试；
  退避用 updated_at 作时间锚点，2^(n-1) 起步、上限 60 秒。
- **死信**：attempts ≥ max_attempts 转 dead 保留现场（last_error），不再自动重试。

10.2 关键选型论证

ADR-01：为什么用 FastAPI

项内容
选它FastAPI
理由① pydantic 原生集成——请求/响应校验免费获得，且能把校验错误翻译成中文（见 §6.1.1）；② 依赖注入——Depends 让 get_session / get_gateway / 鉴权成为可组合的声明式依赖，鉴权出口天然唯一（§6.1.2）；③ 自带 OpenAPI 文档——接口契约自动可查，前后端协作成本低；④ 异步支持好，为流式接口留出空间
放弃Flask（无原生校验与 DI）、Django（对单机小工具过重，ORM 层与本项目「薄领域层 + 重仓储」的设计不合）
何时换基本不需要换。除非要迁到 Serverless 且框架冷启动成为瓶颈

ADR-02：为什么用 SQLAlchemy 2.0 + Repository

项内容
选它SQLAlchemy 2.0（声明式 + Mapped[] 类型注解）+ 自建 Repository 层
理由① Mapped[] 注解让字段类型对 IDE 与类型检查器可见，配合 __table_args__ 声明索引，schema 即文档；② 不直接用 ORM 查询，而是包一层 Repository——这是结构性防越权的前提（§7.3）；③ 仓储层还能隔离「列表与计数条件不一致」类 bug（R-16）
放弃裸 SQL（无类型安全）、Django ORM（与 FastAPI 不搭）
成本每张表要多写一个仓储类。这个成本是刻意支付的——换来的是安全级别从「约定」提升到「结构」
何时换数据量上亿或需要复杂分析查询时，考虑引入专用查询层

ADR-03：为什么 P0 用 SQLite

项内容
选它SQLite 单文件 dev.db
理由① 零部署——个人工具，用户 git clone 后直接能跑，不需要装数据库；② 备份 = 复制一个文件（项目已有一键备份脚本）；③ 单用户场景无并发压力，SQLite 的单写者模型不是瓶颈
放弃PostgreSQL（部署成本高，收益要等数据量上来才体现）
已知限制① 无 pgvector，向量存 pickle bytes、检索时 Python 侧算余弦——数据量大后是瓶颈；② create_all 不给已有表加列（§5.5）；③ 无并发写
何时换当「向量检索变慢」或「需要多实例部署」时。ORM 已抽象，主要改 database_url + 向量存储方案

ADR-11：为什么用 JSON Schema + 顽健解析

项内容
选它要求模型输出 JSON + parse_json 三层退让解析
理由① LLM 输出是自由文本，不能假设它听话；② response_format 约束能提高合规率但不能保证；③ 三层退让（直接解析 → 剥围栏 → 截取花括号）覆盖了实测中 99% 的异常输出
放弃纯正则提取（脆弱）、让模型输出 XML/YAML（模型训练数据少，合规率更低）
何时换若未来模型支持严格的 constrained decoding，可减轻但不应移除兜底

ADR-13：为什么不用 Celery / Redis

项内容
选它单进程「落库排队 + worker 轮询」
理由① 引入 Celery 需要 Redis/RabbitMQ 中间件——违背「零部署」目标（ADR-03）；② 本项目任务量极小（每周几次扫描 + 推送），轮询完全够；③ 数据库唯一约束天然提供幂等（幂等键设计），不需要分布式锁；④ 单进程让调试极简——不需要追踪跨进程状态
放弃Celery（重）、APScheduler（仍需要持久化任务状态的能力，TaskRun 表已提供了）
关键设计enqueue() / run_pending() 被刻意设计成框架无关的接口——将来要换 Celery，只改这 2 个函数
何时换当需要①多实例横向扩展②任务量剧增③任务需要独立资源隔离时。替换成本被控制在 2 个文件内

ADR-14：为什么用 DeepSeek 单一模型 + reasoning 开关

项内容
选它单一模型 deepseek-flash + 每请求 reasoning 开关
理由① 国产、可访问、价格低；② OpenAI 兼容协议 → 未来换供应商改 1 个文件；③ 用 reasoning 开关替代「多模型档位」——业务层只需声明「这个任务要不要深度思考」，不需要知道模型细节；④ DeepSeek 的自动上下文缓存让重复前缀（系统提示词）成本降到 1/50
放弃多模型路由（V2.0 的 Claude 方案已废弃）、自建推理
成本控制策略表把批量提取类任务设为 reasoning=off（省 3~5 倍成本），只有冲突判定、因果推理、L1 定位开思考
何时换需要更强推理能力或更低成本时；或需要多模态时

ADR-15：为什么前端零构建

项内容
选它原生 HTML/JS/CSS，无框架、无打包工具
理由① 零构建 = 零配置 = 零依赖地狱——git clone 就能跑；② 项目是 12 个页面的单机工具，不需要组件化与状态管理；③ 前端资产只有 2 个文件，app.js 承载全部共享逻辑（R-13），style.css 是唯一样式源（R-14）
放弃React/Vue（引入构建链与 npm 依赖，收益不足）
代价无组件复用、无类型检查、需手工管理 DOM。用「页面数量少」换「零维护成本」
配套措施① .html/.js/.css 强制 no-cache（§6.1.1）避免缓存踩坑；② node --check 做语法校验；③ 前端行为用 Node 测试（tests/js/）

11.4 错误响应契约

统一格式，中文可读（踩过的坑：框架默认英文 JSON 直接怼到界面上，复盘第 5 条）：

{
  "detail": "字段「截止日期」格式不正确，应为 ISO 8601 时间"
}
状态码语义示例场景
400请求语义错误参数组合非法
401未认证 / 会话过期Token 失效、过期
403已认证但无权跨用户访问（PermissionError）
404资源不存在条目已被删除
409冲突用户名已存在
422校验失败pydantic 校验不通过（中文提示）
429限流登录失败次数超限
500服务端错误未预期异常（含 request_id 便于定位）

11.5 会话与鉴权流程

sequenceDiagram

    participant A as /auth
    participant S as security
    participant API as 业务接口

    C->>A: POST /login {username, password}
    A->>S: 校验口令（PBKDF2）
    S-->>A: OK
    A->>S: 签发 access(2h) + refresh(7d)

    API-->>C: 200 [...]
机制设计
Access Token2 小时

算法白名单防 alg 混淆攻击（不允许 alg=none）

结语

本文档 V3.0 的核心主张是四句话：

  1. 约束写在结构里，不写在文档里。 越权防护做进 BaseRepository、幂等做进数据库唯一约束、模型调用收口进网关——靠结构让错误写法写不出来，比靠文档提醒开发者「记得加 user_id」可靠得多。
  1. 便宜的手段放前面，贵的放后面。 L2 五级漏斗、reasoning 开关、增量扫描标记——所有智能能力的成本都靠"先用规则/数据库筛，再花大钱推理"压下来。
  1. 可降级比高性能重要。 无 KEY → Mock；无向量模型 → 关键词；模型失败 → 重试 + 死信。每一处外部依赖都有 Plan B，所以系统在任何环境下都能跑。
  1. 加新东西不该改旧东西。 §7.2 的扩展点设计保证新增 L6 只需改 2 个已有文件（main.py + gateway.py 策略表），且必须改的这两处都是「注册式」而非「侵入式」。这是检验解耦是否成功的唯一硬指标。
维护说明：本文档与代码同步演进。任何涉及依赖方向、收口点、复用抽象、schema 结构的改动，必须同步更新对应章节；日常进展记入 dev_logs/，架构级决策记入 dev_logs/设计决策与经验.md，踩坑复盘记入 dev_logs/复盘与教训.md。
