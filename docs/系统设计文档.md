# 第一部分 · 设计基础

## 1. 文档说明

### 1.1 文档目的

本文档在《需求分析文档》需求基线上，给出「认知副驾」系统的**完整设计说明**，作为设计评审与验收的技术依据。具体承担四项职责：

1. **论证设计合理性**：说明系统为何采取当前架构方案、技术选型的依据、关键决策的取舍与代价。
2. **界定系统结构**：自顶向下描述系统的分层结构、模块职责、依赖关系、数据模型与接口契约。
3. **声明设计约束**：明确系统必须遵守的结构性约束（依赖方向、收口点、隔离规则）及其保障机制。
4. **建立可追溯性**：将每条需求关联到设计章节、实现模块与验证方式，实现双向覆盖核查（§16）。

> **本文档的表述原则**：以设计说明书的陈述式表述记录「系统采用什么方案、为什么这样设计、达成何种质量目标」；不重复罗列可直接从代码读取的信息（字段名、函数签名），而重点说明需要跨模块推导才能得到的结论——**设计约束、选型依据、复用结构、边界条件**。文档的价值在于界定「约束」与「理由」，而非复述「实现」。

### 1.2 读者对象与阅读路线

本文档面向设计评审相关方，各类读者可按职责选择关注章节：

### 1.3 术语表

| 术语 | 说明 |
|---|---|
| **L1~L5** | 五大能力：L1 模糊意图认知挖掘 / L2 冲突检测 / L3 认知助产 / L4 路径自我修正 / L5 偏误诊断 |
| **ModelGateway** | 统一模型网关，全系统唯一出网调用点，负责策略路由、重试、成本埋点 |
| **Provider** | 单个模型服务封装（DeepSeek / Mock），实现 `LLMProvider` 接口 |
| **Strategy** | 任务类型 → 调用参数（是否开 reasoning、模型名）的映射条目 |
| **Orchestrator** | 编排层，负责单条用例的完整流程编排（L1~L5 各有其一） |
| **Repository** | 仓储，唯一允许访问数据库的层，且强制 `user_id` 过滤 |
| **TaskRun** | 异步任务运行记录，承载幂等键、重试次数、死信现场 |
| **幂等键（idempotency_key）** | 业务语义去重键（如「某用户 2026 年第 37 周的冲突扫描」），以数据库唯一约束兜底 |
| **结构性防越权** | 在仓储基类层面强制过滤，使越权访问在结构上不可表达，而非依赖编码自觉 |
| **收口（choke point）** | 某类操作在全系统中只允许存在一处实现的设计性质 |
| **设计约束（Design Constraint）** | 系统必须遵守的结构性规则，违反即判定设计不合规（见 §7.1） |

## 2. 设计目标与总体方案

本章给出系统的设计出发点与总体方案框架，说明**设计要达成什么目标、受哪些约束、采用何种总体思路**，并给出关键设计决策索引与系统组成，作为后续各章的论证前提。

### 2.1 设计目标与优先级

系统的设计目标按优先级排序如下。当目标之间发生冲突时，**以序号靠前者为准**——这一优先级顺序是后续所有设计取舍的判据。

| 优先级 | 设计目标 | 具体含义 | 主要落实章节 |
|---|---|---|---|
| **G1** | **数据安全与用户隔离** | 用户数据不可丢失、不可越权访问；隔离由结构保障而非编码约定 | §5.4 §7.3 |
| **G2** | **功能性完备** | 五大能力 L1~L5 全链路闭合，用例无缺口 | §3 §6 |
| **G3** | **成本可控** | 单位用户智能能力成本可预测、可归因、有上限 | §6.3.1 §13.3 |
| **G4** | **可靠性** | 外部依赖失效时可降级或重试，不因单点故障丢失数据 | §13 §10.3 |
| **G5** | **可维护与可扩展** | 分层解耦、复用充分，新增能力不侵入既有代码 | §7 §8 |
| **G6** | **部署轻量** | 零外部中间件，单机可运行 | §10.2 §12.1 |

> **关于优先级的一个典型取舍**：G1 高于 G6。为实现「结构性防越权」，系统在不容许直接使用 ORM 查询的约束下（牺牲部分编码便利、增加一层仓储抽象），换取了越权在结构上不可表达的性质。这类"以抽象换约束"的取舍在 §7.3、§10.2 中反复出现，均遵循本节优先级。

### 2.2 设计约束

设计约束是方案选择的前提条件，分为技术约束与业务约束两类。

**技术约束**（来自运行环境与既有条件）：

| # | 约束 | 对设计的影响 |
|---|---|---|
| C1 | 单机部署，无独立运维条件 | 排除需外部中间件的方案（Celery/Redis/Kafka）→ 采用进程内任务队列（§10.2 ADR-13） |
| C2 | 面向个人用户，数据量级为千级条目 | 允许文件型数据库承载；向量检索暂可内存暴力计算（§15.3 T1） |
| C3 | 模型服务为外部依赖，可用性与价格不可控 | 模型调用必须收口并可降级、可重试、可计费（§6.3） |
| C4 | 前端无构建条件 | 采用原生 HTML/JS/CSS，共享逻辑集中于单一资产文件（§10.2 ADR-15） |
| C5 | 须支持完全离线运行与自动化测试 | 模型层与向量层均须提供可替换的降级实现（§10.3） |

**业务约束**（来自需求与使用场景）：

| # | 约束 | 对设计的影响 |
|---|---|---|
| C6 | 智能能力质量存在不确定性 | 输出须结构化校验、阈值抑制、可反馈纠正（§6.3.2、§4.5.2） |
| C7 | 用户数据敏感 | 软删 + 保留期 + 导出能力；日志不得含正文（§5.4 §12.4） |
| C8 | 推理类操作耗时较长（秒级至分钟级） | 长流程与周期任务须走异步任务框架，不得占用请求线程（§6.5） |
| C9 | 用户使用为长周期持续行为 | 需保留完整行为事件以支撑 L5 归因分析（§5.2 `learning_events`） |

### 2.4 关键设计决策索引

系统的关键设计决策以 ADR 形式记录于《架构设计文档》，其摘要与本文档对应章节如下。评审时可据此定位决策依据。

| 决策编号 | 决策主题 | 核心取舍 | 详细论证 |
|---|---|---|---|
| ADR-01 | Web 框架选型 | 采用 FastAPI 以获取原生校验与依赖注入，未采纳 Flask / Django | §10.2 |
| ADR-02 | 数据访问方式 | 在 ORM 之上增加仓储层，以抽象换结构性安全约束 | §10.2 §7.3 |
| ADR-03 | 存储选型 | P0 采用 SQLite 换取零部署，接受向量检索与并发写的能力上限 | §10.2 §15.3 |
| ADR-09 | 主张（Claim）实体持久化 | 将原子主张落库，把冲突检测由 O(n²) 全集比对降为近邻检索 | §5.2 §6.4 |
| ADR-11 | 结构化输出策略 | JSON Schema + 多层退让解析，不假设模型输出严格合规 | §6.3.2 §10.2 |
| ADR-13 | 异步任务框架 | 进程内「落库排队 + 轮询」替代 Celery/Redis，以框架无关接口保留替换路径 | §6.5 §10.2 |
| ADR-14 | 模型服务与成本策略 | 单一模型 + 每请求 reasoning 开关 + 集中策略表 | §6.3.1 §10.2 |
| ADR-15 | 前端架构 | 原生三件套，零构建 | §10.2 |

> **决策的记录结构**：所有决策按统一四项式记录——**选型内容 / 选型理由 / 未采纳方案及其原因 / 重新评估条件**。其中「重新评估条件」给出可量化的触发条件，避免决策在前提条件变化后仍被机械沿用（详见 §10.2）。

### 2.5 系统组成与模块职责

系统采用模块化单体（Modular Monolith）组织：单进程部署，内部按职责严格分层切分模块。各模块的职责边界与依赖许可如下。

│   ├── api/                     # 接口层（协议转换，不含业务逻辑）
│   │   ├── deps.py              #   依赖注入：会话、网关、鉴权（唯一鉴权出口）
│   │   └── endpoints/           #   13 个端点模块，按业务域划分
│   ├── agent/                   # 编排层（单条用例的流程编排与降级决策）
│   │   ├── orchestrator.py      #   通用对话编排
│   │   ├── l1_orchestrator.py   #   L1 模糊意图 → 定位判断 / 追问分支
│   │   ├── l2_orchestrator.py   #   L2 五级候选漏斗冲突检测

│   │   ├── l5_orchestrator.py   #   L5 行为模式识别与归因推理
│   │   └── push_service.py      #   推送内容装配
│   ├── capabilities/            # 能力包隔离声明（约定五大能力互不依赖）
│   ├── domain/                  # 领域层（业务内核，依赖方向最底层）
│   │   ├── models/              #   16 个 ORM 实体定义
│   │   └── repositories/        #   12 个仓储，全系统唯一数据访问点
│   ├── llm/                     # 模型层（全系统唯一外部模型调用出口）

#### UC-L2-01 扫描观点冲突

| 项 | 内容 |
|---|---|
| **用例编号** | UC-L2-01 |
| **主参与者** | 定时器（周度） / 摄取触发（增量） |
| **前置条件** | 用户已存在；用户知识库中至少存在 2 条已完成主张提取的条目 |
| **触发条件** | ① 用户手动调用 `POST /api/v1/l2/scan`；② 新知识入库后自动触发；③ 每周定时全量扫描 |
| **主成功场景** | 1. 系统构造幂等键（`l2:realtime:{user}:{YYYYMMDDHH}` 或 `l2:weekly:{user}:{ISO年}-W{ISO周}`）<br/>2. 入队 `TaskRun`，重复入队由数据库唯一约束拦截<br/>3. Worker 取出任务，编排层执行五级漏斗：<br/>&nbsp;&nbsp;&nbsp;L2-1 增量筛选：仅取 `claims_scanned_at IS NULL` 的条目<br/>&nbsp;&nbsp;&nbsp;L2-3 同主题预筛：按 `(user_id, topic)` 索引生成候选对<br/>&nbsp;&nbsp;&nbsp;L2-4 立场强度过滤：保留极性相异且表述强度达标者<br/>&nbsp;&nbsp;&nbsp;L2-5 模型判定：调用 `ModelGateway.chat(task_type="conflict_detection")`<br/>&nbsp;&nbsp;&nbsp;L2-6 阈值抑制：丢弃低于置信度阈值或已忽略同类型的候选<br/>4. 经 `pair_key` 去重后写入 `conflicts` 表<br/>5. 更新条目的 `claims_scanned_at` 扫描标记<br/>6. 记录 `CostLog`（含推理 token 与缓存命中量） |
| **扩展场景** | 3a. 模型返回非法 JSON → 以多层退让解析处理；仍失败则跳过该候选对，不影响本批次其余任务<br/>3b. 模型服务不可用 → 网关执行 3 次指数退避重试；仍失败则任务保留于 `pending` 状态等待下轮重试<br/>3c. 重试次数超上限 → 转入 `dead` 死信状态，保留 `last_error` 现场信息 |
| **后置条件** | 新增冲突记录（`user_state=unseen`）；条目扫描标记已更新；本次调用成本已记录 |

### 4.2 架构风格：分层 + 端口适配 + 收口

本系统采用**三层主体 + 一个横切收口**的结构：

| 层次 | 职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| **表现层** `api/` | HTTP 协议转换、参数校验、鉴权、序列化 | 编排层、领域层、core | 不得包含业务逻辑<br/>不得直接调用 `llm/` |
| **编排层** `agent/` | 单条用例的流程编排、多步协调、降级决策 | 领域层、llm/、retrieval/、workers/ | 不得直接操作数据库会话（须经仓储） |
| **领域层** `domain/` | 实体定义、持久化、数据完整性 | core | 不得依赖 `llm/`、`api/`、`agent/` |
| **支撑层** `llm/ retrieval/ workers/ core/` | 提供被上层调用的基础能力 | core | `llm/` 不得依赖 `agent/` |

**两个关键收口（choke point）**——本架构的核心设计决策：

| 收口 | 含义 | 设计收益 |
|---|---|---|
| **模型调用收口于 `ModelGateway`** | 全系统仅此一处发起模型请求 | 更换供应商仅需修改 1 个文件；成本埋点、重试策略、调用日志集中于一处，不存在遗漏路径 |
| **数据访问收口于 Repository** | 全系统仅仓储层访问数据库会话 | 越权防护于基类集中实现，12 个仓储自动继承，越权访问在结构上不可表达 |

### 4.3 依赖方向约束

```mermaid
graph LR
    A["api/"] --> B["agent/"]
    B --> C["domain/"]
    B --> D["llm/"]
    B --> E["retrieval/"]
    B --> F["workers/"]
    A --> C
    D --> G["core/"]
    C --> G
    E --> G
    F --> B

    X["❌ domain → llm"]:::bad
    Y["❌ llm → agent"]:::bad
    Z["❌ api → llm 直连"]:::bad
    W["❌ capabilities 之间互相 import"]:::bad

    classDef bad fill:#ffebee,stroke:#c62828,stroke-width:2px,stroke-dasharray:5 3,color:#b71c1c
```

**四条约束**（违反即判定设计不合规）：

1. **依赖必须单向向下**：`api → agent → domain/llm`，反向依赖一律禁止。
2. **`domain/` 必须保持独立**：不得感知模型层的存在。这使领域模型可被任意上层复用，并支持模型层的独立替换。
3. **`llm/` 必须对上层无感知**：网关不感知调用来源，仅依据 `task_type` 决定调用策略。因此新增能力无需修改模型层。
4. **`capabilities/` 各能力之间不得互相引用**：五大能力必须彼此隔离，仅通过领域层共享数据。这使任一能力可被独立重构或移除。

> **第 4 条约束的必要性**：L1~L5 在业务上高度相关（均依赖知识库与模型调用），若不加以约束，极易产生 `l3` 调用 `l2` 内部函数的横向耦合，进而导致「调整 L2 阈值引发 L3 异常」的连锁影响。**共享逻辑必须下沉至 `domain/` 或 `llm/` 层，不得横向互调。**

### 4.5 状态机设计

系统中有三处显式状态机，它们是「数据一致性」的核心保障。

#### 4.5.1 异步任务状态机（`TaskRun`）

```mermaid
stateDiagram-v2
    [*] --> pending: enqueue（幂等键唯一约束）
    pending --> running: worker 取出
    running --> succeeded: 执行成功
    running --> pending: 失败且 attempts < max<br/>（退避后重试）
    running --> dead: 失败且 attempts ≥ max<br/>（保留 last_error 现场）
    pending --> pending: 重复入队被 DB 挡回<br/>（视为已存在）
    succeeded --> [*]
    dead --> [*]
```

> **失败状态不直接转入死信的设计理由**：任务失败后保留在 `pending` 状态并递增 `attempts`，由下一轮轮询自然重试，以 `updated_at` 作为退避时间锚点（`2^(n-1)` 秒起、上限 60 秒）。该设计使**重试机制无需依赖独立的调度组件**，单一轮询循环即可完成全部调度职责。

#### 4.5.2 冲突用户状态机（`Conflict.user_state`）

```mermaid
stateDiagram-v2
    [*] --> unseen: 扫描产出
    unseen --> accepted: 用户认可（触发「转学习计划」扩展用例）
    unseen --> ignored: 用户忽略
    ignored --> ignored: 同类型累计 ≥N 次<br/>→ 该类型不再推荐
    accepted --> [*]
```

#### 4.5.3 诊断状态机（`CognitiveDiagnosis.status`）

```mermaid
stateDiagram-v2
    [*] --> pending: L5 诊断产出
    pending --> accepted: 用户认可
    pending --> rejected: 用户否决
    accepted --> [*]
    rejected --> [*]
```

> **状态机的设计意图**：这三处状态机的目的不在于「记录状态」，而在于使系统**具备可纠正性**——用户的忽略或认可反馈将反向收敛后续推荐结果（误报抑制），从而使智能能力的输出质量随使用过程持续改善。

### 4.6 运行设计（部署内视图）

单进程内的运行视图：

```
uvicorn 进程
├── 主线程：asyncio 事件循环
│    └── FastAPI 处理 HTTP 请求
│         ├── 中间件链：request_id → static_cache
│         ├── 路由分发 → 编排层 → 领域层
│         └── 静态文件托管（/assets, /xxx.html）
└── 守护线程：Worker 轮询循环（worker_enabled=false 可关）
     └── run_pending() → 取 pending 任务 → 执行处理器 → 更新状态
```

**关键约束**：

| 约束 | 说明 |
|---|---|
| **Worker 与 Web 同进程** | 不引入 Celery/Redis（见 §10.2 ADR-13）。代价是「Web 挂了 Worker 也停」，但单机个人工具可接受 |
| **测试中必须关闭 Worker** | 测试设 `worker_enabled=false`，避免后台线程干扰与不确定的时序 |
| **任务执行是同步的** | Worker 线程内串行执行，不给用户请求造成并发压力 |
| **SQLite 单写者** | 所有写操作串行化，避免 SQLite 写锁竞争 |

### 5.2 表职责与设计要点

| 表 | 职责 | 设计要点 |
|---|---|---|
| `users` | 账号 | `token_version` 支持**全局吊销**既有 JWT（改密或注销后所有令牌立即失效） |
| `knowledge_items` | 知识基本单位 | `claims_scanned_at` 是 L2 增量扫描的**成本控制关键**；`embed_status` 支持向量化失败时的降级 |
| `claims` | 原子主张 | 主张持久化使冲突检测由 O(n²) 全集比对**降为近邻检索**，是 L2 具备可运行性的根本前提 |
| `conflicts` | 冲突检测产物 | `pair_key`（两主张标识排序拼接）作为去重键，使重复扫描不产生重复记录 |
| `books` | 书籍与阅读进度 | `chapters` 以 JSON 存储章节结构；`current_char` 采用字符偏移而非页码（适配任意排版） |
| `learning_goals` / `learning_plans` / `plan_tasks` | L4 路径修正 | `learning_plans.version` 实现**乐观锁**，防止并发更新覆盖 |
| `learning_events` | 行为事件记录 | **追加写入（append-only）**，是 L5 诊断的唯一数据来源；`payload` **禁止**包含正文与敏感字段 |
| `task_runs` | 异步任务 | `idempotency_key` 唯一约束，由数据库约束而非应用逻辑保证幂等 |
| `cost_logs` | 成本记录 | `cached_tokens` 与 `prompt_version` 使成本优化可归因 |
| `push_jobs` / `push_logs` | 推送 | `push_logs.content_hash` 唯一约束保证相同内容不重复推送 |
| `cognitive_diagnoses` | L5 产出 | `reasoning_chain` 保存完整推理链，使诊断结论可解释、可复核 |

### 5.3 索引设计

索引的设立依据为**实际高频查询**，而非无差别添加。每个索引对应一条确定的查询路径：

| 索引 | 表 | 支撑的查询 |
|---|---|---|
| `(user_id, topic)` | `claims` | L2-3 同主题预筛：以 `topic` 与 `user_id` 生成候选对 |
| `(user_id, user_state)` | `conflicts` | 待推送冲突查询：仅取 `unseen` 状态 |
| `user_id` | 几乎所有表 | 用户作用域强制过滤（结构性防越权的物理基础） |
| `idempotency_key` (UNIQUE) | `task_runs` | 幂等入队的数据库级保障 |
| `content_hash` (UNIQUE) | `push_logs` | 推送内容去重 |
| `event_type` / `occurred_at` | `learning_events` | L5 按事件类型与时间聚合行为模式 |
| `pair_key` | `conflicts` | 冲突记录去重查询 |

### 5.4 数据完整性策略

| 策略 | 实现方式 |
|---|---|
| **软删除** | `knowledge_items.is_deleted` / `books.is_deleted` / `users.deleted_at`；物理清除须待保留期届满 |
| **时间戳** | `TimestampMixin` 统一提供 `created_at` / `updated_at`（含时区） |
| **主键** | 统一采用 `String(36)` 存储 UUID4 字符串，**不使用自增整数**，便于将来的水平扩展与外部系统对账 |
| **乐观锁** | `learning_plans.version`，更新时校验版本号 |
| **外键** | 采用逻辑外键（由 SQLAlchemy 维护关系），未启用数据库级外键约束以简化 SQLite 环境下的迁移 |

> **一项已知的取舍**：`users.push_frequency` 与 `embedding` 字段采用 pickle 序列化存储为二进制。其优势为无额外依赖；代价为**不具备跨语言可读性**，需在与外部系统交换数据时迁移（已登记为 §15.3 T1）。

### 5.5 数据模型演进规则

数据模型的结构性变更须遵守以下规则。这些规则针对 SQLite 的特定语义而设立，**违反将导致结构漂移类缺陷**（详见附录 C 第 1、2 条）：

| 规则 | 依据 |
|---|---|
| **新增实体必须注册至 `app/domain/models/__init__.py`** | `Base.metadata.create_all()` 仅扫描已被导入的模型。未注册时表不会被创建，且**不产生显式错误**，缺陷将延后至该表首次被查询时暴露 |
| **不得假设 `create_all` 会为已有表添加列** | SQLite 的 `CREATE TABLE IF NOT EXISTS` 语义对已存在的表不产生任何操作。新增字段须显式执行 `ALTER TABLE` 或重建表 |
| **模型变更后须重启服务** | 不可依赖热重载；结构缓存与连接池会使旧结构继续生效 |
| **模型变更后须执行全量测试** | 测试使用独立数据库，可最快暴露结构漂移问题 |
| **生产环境变更须使用迁移脚本** | Alembic 依赖已引入（`alembic>=1.13`）。P0 阶段采用手工迁移，进入 P1 阶段后须统一使用迁移脚本（§15.3 T2） |

### 6.2 领域层（`app/domain/`）

#### 6.2.1 仓储基类（`app/domain/repositories/base.py`）

```python
class BaseRepository(Generic[_T]):
    def __init__(self, session: Session, user_id: str | None = None): ...

    def _guard(self, owner_user_id: str) -> None:
        """结构性越权防护：绑定用户后，仅允许访问归属本用户的行。"""
        if self._user_id and owner_user_id != self._user_id:
            raise PermissionError(f"跨用户访问被拒（structural guard）")
```

| 项 | 内容 |
|---|---|
| **职责** | 提供会话管理与**越权防护**，被 12 个仓储继承 |
| **关键设计** | 防护写在**基类**：子类只要正常调用 `_guard`，就自动获得保护。**不是**靠每个开发者记得加 `where user_id = ?` |
| **复用收益** | 新增第 13 个仓储时，越权防护代码量 = 0 行 |
| **测试要点** | `tests/test_db.py`：跨用户访问必须抛 `PermissionError` |

| `push_service.py` | UC-30 | 推送内容装配与去重 | `push/` |

**L2 五级漏斗**（全系统最核心的算法，成本与准确率的平衡点）：

```
全量知识条目
  │  L2-1 增量筛选：claims_scanned_at IS NULL  → 只处理新增
  ▼
待提取条目
  │  L2-6 主张提取：LLM 批量抽取原子主张（reasoning=off，省钱）
  ▼
主张集合
  │  L2-3 同主题预筛：按 (user_id, topic) 取同主题候选对  → 避免 O(n²)
  ▼
候选对
  │  L2-4 立场强度过滤：极性相异 且 强度达标
  ▼
高潜候选对（数量已降 1~2 个数量级）
  │  L2-5 LLM 判定：reasoning=on 精细判定（只对高潜对花大钱）
  ▼
疑似冲突
  │  L2-6 阈值抑制：置信度阈值 + 已忽略类型收敛 + pair_key 去重
  ▼
入库 conflicts
```

> **漏斗的核心原则**：**低代价筛选前置，高代价推理后置**。L2-1~L2-4 均为纯数据库查询或规则计算（成本可忽略），仅 1~2% 的候选对进入模型判定阶段。这是 L2 具备单机可运行性的关键设计前提。

### 6.5 异步任务层（`app/workers/`）

#### 6.5.1 三条核心机制（`app/workers/tasks.py`）

```python
- **幂等**：TaskRun.idempotency_key 唯一约束。重复入队由数据库挡回
  （IntegrityError → 视为已存在），不依赖应用层「先查再插」那种有竞态的做法。
- **重试**：失败不改状态为 dead，而是留在 pending、attempts+1，下一轮轮询再试；
  退避用 updated_at 作时间锚点，2^(n-1) 起步、上限 60 秒。
- **死信**：attempts ≥ max_attempts 转 dead 保留现场（last_error），不再自动重试。
```

| 项 | 内容 |
|---|---|
| **注册表** | `HANDLERS: dict[str, Handler]` + `@register("name")` 装饰器（重复注册抛 `ValueError`） |
| **入队** | `enqueue()` 返回 `EnqueueResult(created: bool)`——同 key 返回 `created=False` |
| **执行** | `run_pending()` 批量取 pending 任务并执行 |
| **幂等键构造** | `triggers.realtime_key()` / `weekly_key()` |

幂等键实例：

| 场景 | 幂等键格式 | 效果 |
|---|---|---|
| 实时冲突扫描 | `l2:realtime:{user}:{YYYYMMDDHH}` | 1 小时内同一用户仅执行一次，重复触发不产生额外模型调用成本 |
| 周度冲突扫描 | `l2:weekly:{user}:{ISO年}-W{ISO周}` | 一周一次，跨进程重启也不会重跑 |
| 每周简报 | 含 ISO 周 | 定时器重复触发也只推一次 |

> **幂等键的设计价值**：该设计将「去重」这一业务需求，转化为**数据库唯一约束**这一基础设施能力——无需分布式锁、无需额外中间件、无需状态查询，**唯一约束冲突即表示重复入队**。其正确性由数据库层保证，不依赖应用层存在竞态的「先查询后插入」实现。

#### 6.5.2 任务处理器（`app/workers/handlers.py`）

| 处理器 | 任务名 | 职责 |
|---|---|---|
| `l2_scan` | `l2_scan` | 调用 L2 编排器执行冲突扫描 |
| `push_weekly_digest` | 对应 | 装配并推送每周认知简报 |
| `push_monthly_health` | 对应 | 装配并推送每月学习健康报告 |

**处理器的三条设计约定**：

1. 仅执行「取参数 → 调用编排层 → 记录日志」，**不包含业务逻辑**；
2. 失败时**直接抛出异常**交由框架处理重试，**不得在内部捕获并吞没异常**；
3. 必须**可重复执行且无副作用**（幂等），因执行过程可能发生重试。

## 7. 架构解耦规则

本章给出系统强制遵守的**结构性约束**及其检查方式。每条约束均对应可机械化执行的核查手段，供设计评审与实现合规性检查使用，避免约束的维持依赖主观判断。

### 7.1 依赖方向检查表

| # | 约束 | 检查方式 | 违反后果 |
|---|---|---|---|
| D-1 | `domain/` 不得引用 `llm/`、`agent/`、`api/` | `grep -r "from app.llm\|from app.agent\|from app.api" app/domain/` 应为空 | 领域层与模型层耦合，丧失独立可测性与可复用性 |
| D-2 | `llm/` 不得引用 `agent/` | `grep -r "from app.agent" app/llm/` 应为空 | 网关与具体业务耦合，更换供应商须修改业务代码 |
| D-3 | `api/` 不得直接引用 `llm/` | `grep -r "from app.llm" app/api/` 应为空 | 绕过网关：成本埋点缺失、重试策略失效 |
| D-4 | `api/` 不得直接操作数据库会话 | 须通过 `Depends(get_session)` 交由仓储使用 | 绕过越权防护：数据隔离失效风险 |
| D-5 | `capabilities/` 各能力之间不得互相引用 | `grep -r "from app.capabilities" app/capabilities/` 应为空 | 能力间耦合，变更产生连锁影响 |
| D-6 | `agent/` 不得绕过仓储直接写库 | 仅应出现仓储方法调用 | 绕过越权防护：数据隔离失效 + 事务边界散乱 |

> **约束的自动化保障**：上述 6 条约束均可通过 `grep` 或 `import-linter` 在构建环节自动核查。当前以人工评审配合设计约定保障，已登记为技术债 T3 并列入 §15.2 的 P1 阶段计划。

### 7.2 扩展性验证：新增能力的接入代价

解耦是否有效，可用一个具体场景定量验证：**假设新增「L6 学习风格识别」能力，需要改动多少既有代码？**

| 步骤 | 动作 | 是否改动既有文件 |
|---|---|---|
| 1 | 新建 `agent/l6_orchestrator.py`，实现流程编排（依赖 `domain/` 与 `llm/`） | 否（新建） |
| 2 | 新建 `api/endpoints/l6.py`，定义路由 | 否（新建） |
| 3 | 在 `app/main.py` 增加一行 `include_router(l6.router)` | **是**（注册式，1 行） |
| 4 | 在 `llm/gateway.py` 的 `STRATEGY_TABLE` 增加一条 `task_type` 映射 | **是**（注册式，1 条） |
| 5 | 在 `llm/prompts.py` 增加提示词与版本号 | 追加，不修改既有项 |
| 6 | 如需新实体，在 `domain/models/` 新建并**注册到 `__init__.py`**（见 §5.5） | 追加，不修改既有项 |
| 7 | 在 `tests/` 新建 `test_l6.py` | 否（新建） |

> **扩展性判据**：新增能力时，**不需要修改 L1~L5 的任何代码**；仅有的两处既有文件改动均为「注册式追加」（登记条目），而非「侵入式修改」（改动已有逻辑）。若某次扩展被迫修改了既有能力模块，即表明存在耦合，应将共享逻辑下沉至 `domain/` 或 `llm/` 层。这一判据是本设计解耦效果的量化验收标准。

### 7.3 数据隔离规则

| 规则 | 实现 | 保障级别 |
|---|---|---|
| 所有业务查询必须带 `user_id` | `BaseRepository._guard()` | **结构级**（不是约定级） |
| 跨用户访问抛 `PermissionError` | 基类统一实现 | 无法绕过 |
| JWT 中携带 `user_id` 与 `token_version` | `core/security.py` | 吊销可信 |
| 软删数据默认过滤 | 仓储的 `list_*` 方法 | 默认安全 |

> **结构性保障与约定性保障的差别**：约定性保障要求「所有实现都记得附加 `WHERE user_id = ?`」，其有效性依赖编码自觉，存在遗漏可能。结构性保障则将过滤实现于仓储基类，使**遗漏在结构上不可表达**——上层无法构造出不经过滤的查询。这是本系统数据隔离设计的核心思路，也对应 §2.1 中 G1 目标优先于 G6 的取舍。

### 7.4 可替换性设计

| 可替换项 | 替换方式 | 影响范围 |
|---|---|---|
| **LLM 供应商** | 实现新的 `LLMProvider` 子类 + 改 `_build_provider()` | 1 个文件 |
| **向量模型** | 实现新的 `EmbeddingModel` 子类 + 改配置 | 0 个业务文件 |
| **数据库** | 改 `database_url`（ORM 已抽象） | 1 个配置项（需处理 SQLite 特有语义） |
| **检索策略** | 改 `Retriever` 的融合权重或加通道 | 1 个文件 |
| **异步框架** | `tasks.py` 的 `enqueue`/`run_pending` 是接口边界，可换成 Celery | 1~2 个文件 |

> **ADR-13 的保留意见**：当前不引入 Celery/Redis（见 §10.2）。但 `enqueue()` / `run_pending()` 被设计成**框架无关的接口**，未来若需横向扩展，替换成本被控制在 2 个文件内。

### 8.4 复用约定的落地方式

扩展系统时，下表给出「该需求应复用的既有能力」与「应避免的重复实现」，是 §7.1 依赖约束在复用维度的具体化：

| 需求场景 | 应复用的既有能力 | 应避免的重复实现 |
|---|---|---|
| 访问数据库 | `BaseRepository` 子类 | 直接使用 `session.query()` |
| 调用模型 | `ModelGateway.chat(task_type=...)` | 自行构造 HTTP 请求 |
| 解析模型 JSON 输出 | `parse_json()` | 直接使用 `json.loads` |
| 计算 token 成本 | `cost.py` 的计价函数 | 在业务代码中硬编码价格 |
| 读取配置 | `settings.xxx` | 直接读环境变量 |
| 增加异步任务 | `@register` + `enqueue` | 自行创建线程 |
| 增加限流 | `FailureThrottle` | 自行实现滑动窗口 |
| 模型调用失败重试 | 网关已内置 | 在外层重复包装重试 |

> 该约定的设计意图：**每一类横切关注点在全系统只实现一次**，使「策略调整」只需改动一处，也使「行为审计」（如成本归集、重试计数）不存在遗漏点。

### 8.5 复用边界：不应被复用的部分

复用并非无约束——**过度抽象同样构成设计缺陷**。以下模式在本设计中明确不予采用：

| 不予采用的模式 | 原因 |
|---|---|
| 抽取统一的「万能业务基类」 | 五大能力业务差异显著，强行统一将产生大量能力分支判断，降低内聚性 |
| L1~L5 之间互相调用 | 违反 D-5 约束，将产生改动连锁效应；共享逻辑应下沉至 `domain/` 或 `llm/` |
| 将提示词拼接在业务代码中 | 提示词须集中于 `prompts.py`，否则无法进行版本管理与效果回归 |
| 以通用 `dict` 传递结构化数据 | 应使用 dataclass（如 `L1Route`、`ExtractedClaim`）表达结构，借助类型系统检查 |
| 前后端共享同一份数据模型定义 | 前端无构建工具，强行共享将引入非常规依赖；当前以接口契约（§11）保证一致性 |

## 9. 工程实现与质量保障

### 9.2 代码组织标准

为维持 §7.1 的依赖约束，实现须遵守以下组织标准：

| 标准 | 内容 |
|---|---|
| **分层归属** | 每个文件必须归属于唯一层次（`api`/`agent`/`domain`/`llm`/`retrieval`/`workers`/`core`），不得跨层混合职责 |
| **按业务域分包** | 接口层按业务域划分端点模块（`l1.py`~`l5.py`、`knowledge.py` 等），不按技术类型划分 |

| **模型集中注册** | 新增 ORM 实体**必须**在 `app/domain/models/__init__.py` 中注册，否则元数据不生效且不产生显式错误 |
| **提示词集中管理** | 提示词统一置于 `llm/prompts.py` 并携带版本号，以支撑效果回归与变更追溯 |
| **横切能力收口** | 配置、安全、限流、日志、链路追踪统一置于 `core/`，不得在业务模块中重复实现 |

### 9.4 配置与变更控制

**版本控制策略**：采用主干开发配合短生命周期特性分支；每次变更对应一个独立的原子提交，使任意设计条目可定位到确定的历史版本。

**提交信息规范**：采用 `<类型>: <说明>` 形式，类型取值 `feat`（功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`perf`（性能）、`chore`（杂项）。规范化提交信息使**变更性质可统计、可审计**，例如可通过 `fix` 类提交的分布定位设计的薄弱环节：

```
feat: 知识库列表分页（加载更多）+ 关键词搜索
fix: 会话过期后页面变空壳（记录消失 + 账号不显示 + 退出无效）
docs: 登记知识库分页与搜索完成
fix: 前端静态资源改为「先校验再使用」，避免拿旧 JS 跑新后端
```

**敏感信息控制**：密钥、令牌等敏感配置**必须**经环境变量注入；`dev.db`、`data/`、`backups/` 等运行数据不纳入版本控制，并由备份机制保障（§12.4）。

**数据模型变更控制**：SQLite 的 `CREATE TABLE IF NOT EXISTS` 语义对已存在的表不产生任何效果，因此模型变更**必须**按 §5.5 规则显式执行结构调整，并重启服务、重跑全量测试。

### 10.2 关键选型论证

各决策按下述四项结构记录：**选型内容 / 选型理由 / 未采纳方案及其原因 / 重新评估条件**。

#### ADR-01：Web 框架选型（FastAPI）

| 项 | 内容 |
|---|---|
| **选型内容** | FastAPI |
| **选型理由** | ① 与 pydantic 原生集成，请求与响应校验无需额外实现，并支持将校验错误统一转换为中文提示（§6.1.1）；② 提供依赖注入机制，使会话、网关与鉴权成为可组合的声明式依赖，鉴权出口天然唯一（§6.1.2）；③ 自动生成 OpenAPI 契约文档，降低接口协作成本；④ 原生异步支持，为流式接口预留实现空间 |
| **未采纳方案** | Flask（缺少原生校验与依赖注入机制）；Django（对单机应用而言过重，其 ORM 组织方式与本设计「薄领域层 + 重仓储层」的结构不匹配） |
| **重新评估条件** | 基本无需变更；仅在迁移至 Serverless 环境且框架冷启动成为瓶颈时评估 |

#### ADR-02：数据访问方式选型（SQLAlchemy 2.0 + 仓储层）

| 项 | 内容 |
|---|---|
| **选型内容** | SQLAlchemy 2.0（声明式 + `Mapped[]` 类型注解），在其上自建仓储层 |
| **选型理由** | ① `Mapped[]` 注解使字段类型对 IDE 与类型检查器可见，配合 `__table_args__` 声明索引，使模型定义同时充当数据结构文档；② 业务层不直接使用 ORM 查询，而经仓储层封装——这是**结构性防越权得以成立的前提**（§7.3）；③ 仓储层同时消除了「列表查询与计数查询条件不一致」一类缺陷（复用点 R-16） |
| **选型代价** | 每张实体表需额外实现一个仓储类。该代价为**有意承担**——所换取的是数据隔离保障级别由「编码约定」提升至「结构约束」 |
| **未采纳方案** | 原生 SQL（缺少类型安全）；Django ORM（与 FastAPI 技术栈不匹配） |
| **重新评估条件** | 数据规模达亿级或需复杂分析型查询时，考虑引入专用查询层 |

#### ADR-03：存储选型（SQLite）

| 项 | 内容 |
|---|---|
| **选型内容** | SQLite 单文件数据库（`dev.db`） |
| **选型理由** | ① **零部署成本**——本系统为个人应用，获取代码后即可运行，无需安装独立数据库服务；② 备份操作等价于复制单个文件（已提供一键备份脚本）；③ 单用户场景下无并发写压力，SQLite 的单写者模型不构成瓶颈 |
| **未采纳方案** | PostgreSQL（部署成本较高，其收益需在数据规模增长后方能体现） |
| **已知能力边界** | ① 无 pgvector 支持，向量以 pickle 存储并由应用层计算相似度，**数据量增长后将成为性能瓶颈**；② `create_all` 不为已存在的表添加列（§5.5）；③ 不支持并发写入 |
| **重新评估条件** | 出现「向量检索性能下降」或「需多实例部署」时。由于 ORM 层已作抽象，主要变更为数据库连接配置与向量存储方案 |

#### ADR-11：结构化输出策略选型（JSON Schema + 多层退让解析）

| 项 | 内容 |
|---|---|
| **选型内容** | 要求模型输出 JSON，并以 `parse_json` 实现多层退让解析 |
| **选型理由** | ① 模型输出本质为自由文本，**设计上不可假定其严格符合格式约定**；② `response_format` 参数可提高合规率但不构成保证；③ 三层退让策略（直接解析 → 剥离代码围栏 → 截取最外层花括号）可覆盖实测中的绝大多数异常输出 |
| **未采纳方案** | 正则表达式提取（鲁棒性不足）；要求模型输出 XML / YAML（模型训练语料较少，合规率更低） |
| **重新评估条件** | 若模型服务支持严格的约束解码（constrained decoding），可减轻解析复杂度，但**不应移除兜底解析逻辑** |

#### ADR-13：异步任务框架选型（进程内任务队列）

| 项 | 内容 |
|---|---|
| **选型内容** | 单进程内「任务落库排队 + 轮询执行」模式 |
| **选型理由** | ① 引入 Celery 需配套 Redis / RabbitMQ 等中间件，与「零部署」目标（ADR-03）冲突；② 本系统任务量小（每周数次扫描与推送），轮询机制足以满足；③ **数据库唯一约束天然提供幂等保障**（幂等键设计），无需分布式锁；④ 单进程模型简化调试路径，无需追踪跨进程状态 |
| **未采纳方案** | Celery（引入额外中间件依赖）；APScheduler（其任务状态持久化需求已由 `TaskRun` 表满足） |
| **关键设计** | `enqueue()` 与 `run_pending()` 被设计为**与框架无关的接口**，替换实现仅需修改这两个函数 |
| **重新评估条件** | 出现下述情形之一时：需多实例横向扩展、任务量显著增长、任务需独立资源隔离。**替换代价已控制在 2 个文件范围内** |

#### ADR-14：模型服务与成本策略选型（单一模型 + reasoning 开关）

| 项 | 内容 |
|---|---|
| **选型内容** | 单一模型 `deepseek-flash`，配合每请求 `reasoning` 开关 |
| **选型理由** | ① 服务可稳定访问且单价较低；② 采用 OpenAI 兼容协议，更换供应商仅需修改 1 个文件；③ 以 `reasoning` 开关替代「多模型档位」设计，**业务层仅需声明「该任务是否需要深度推理」，无需感知模型细节**；④ 服务端提供自动上下文缓存，重复前缀（系统提示词）部分的成本可降至约 1/50 |
| **未采纳方案** | 多模型路由方案（早期 Claude 方案已废弃）；自建推理服务 |
| **成本控制措施** | 策略表将批量提取类任务设为 `reasoning=off`（可降低约 3~5 倍成本），仅冲突判定、因果推理、L1 意图定位三类任务开启推理 |
| **重新评估条件** | 需要更强推理能力、更低成本，或需要多模态支持时 |

#### ADR-15：前端架构选型（零构建方案）

| 项 | 内容 |
|---|---|
| **选型内容** | 原生 HTML / JS / CSS，不使用框架与打包工具 |
| **选型理由** | ① 零构建即零配置，不引入依赖管理复杂度，获取代码即可运行；② 本系统为 12 个页面的单机应用，**不需要组件化与状态管理机制**；③ 前端资产仅 2 个文件：`app.js` 承载全部共享逻辑（复用点 R-13），`style.css` 为唯一样式来源（R-14） |
| **未采纳方案** | React / Vue（引入构建链与包管理依赖，相对收益不足） |
| **选型代价** | 缺少组件复用与类型检查能力，需手工管理 DOM。该代价以**页面数量有限**为前提被接受，换取零维护的构建环节 |
| **配套措施** | ① 对 `.html / .js / .css` 设置协商缓存响应头（§6.1.1），避免静态资源缓存导致变更未生效；② 以 `node --check` 进行语法校验；③ 前端行为纳入 Node 环境自动化验证（`tests/js/`） |

### 10.3 Mock 实现的设计价值

`MockProvider` 的作用不限于「未配置密钥时的降级路径」，其同时是**测试策略的基础设施**：

| 设计收益 | 说明 |
|---|---|
| **测试确定性** | 262 项测试全部在 Mock 下运行，不依赖网络、不产生费用、结果可重复 |
| **环境无关性** | 未配置密钥即可完成全链路运行，便于部署验证与功能演示 |
| **离线可用性** | 无网络环境下可完成全部运行与开发工作 |
| **测试成本为零** | 自动化测试不产生模型调用费用 |
| **异常场景可控** | 可精确构造「模型返回非法 JSON」「模型超时」等异常输入，用于验证降级路径 |

> **设计要点**：将 `LLMProvider` 抽象为接口后，Mock 实现成为**与真实实现地位对等的可替换组件**，而非事后补充的测试替身。这使系统的可靠性设计（降级、重试、异常处理）能够被确定性地验证，而不仅依赖真实服务的偶然异常。这一性质是本设计可测试性的基础。

### 10.4 依赖管理原则

| 原则 | 说明 |
|---|---|
| **运行时依赖最小化** | 当前仅 9 个。每增加一个依赖都会提高环境重建成本与供应链风险 |
| **既有能力可解决时不引入库** | 例：限流功能以约 40 行实现 `FailureThrottle`，不引入额外限流库 |
| **重依赖须可降级** | 向量模型为可选依赖，缺失时自动降级为关键词检索，功能不缺失 |
| **引入依赖须说明理由** | 需论证「为何现有能力无法解决」，并评估其降级方案 |

### 11.3 关键接口契约示例

#### `POST /api/v1/l1/mine` —— L1 模糊意图挖掘

**请求**
```json
{ "query": "我好像在哪看过关于复利的讨论" }
```

**响应（定位成功 `decision=located`）**
```json
{
  "decision": "located",
  "items": [
    {
      "id": "uuid",
      "title": "《穷查理宝典》笔记",
      "snippet": "复利效应是……",
      "reason": "标题与内容均命中「复利」主题，且表述与查询意图一致",
      "is_readable": true,
      "source_locator": { "chapter_index": 3, "char_start": 1200, "char_end": 1500 }
    }
  ],
  "cost": { "prompt_tokens": 812, "completion_tokens": 96, "estimated_cost": 0.0021 }
}
```

**响应（需追问 `decision=clarify`）**
```json
{
  "decision": "clarify",
  "candidates": [
    { "id": "uuid", "title": "《穷查理宝典》笔记", "snippet": "……" }
  ],
  "question": "你是指「复利」这个概念的定义，还是某个具体场景下的复利应用？"
}
```

> **契约设计要点**：`decision` 采用**判别式字段**设计，客户端据此分支渲染。相较返回两个互为可选、可能同时为空的结果字段，该设计语义更明确，同时也是「证据不足时不作出定位判断」这一业务规则在接口层面的体现。

#### `PATCH /api/v1/l2/conflicts/{id}/state` —— 冲突反馈

**请求**
```json
{ "user_state": "ignored" }
```

**响应**
```json
{ "id": "uuid", "user_state": "ignored", "suppressed_type": false }
```

> `suppressed_type=true` 表示「同类型忽略次数已达阈值，该类型后续不再推荐」。该字段使**误报抑制机制的作用结果对用户显式可见**，而非静默生效。

### 11.4 错误响应契约

错误响应采用统一结构，**提示信息为中文且面向用户可理解**。框架默认的错误格式为英文结构化输出，不适合直接呈现给用户，因此须经统一转换（见附录 C 第 5 条）：

```json
{
  "detail": "字段「截止日期」格式不正确，应为 ISO 8601 时间"
}
```

| 状态码 | 语义 | 示例场景 |
|---|---|---|
| 400 | 请求语义错误 | 参数组合非法 |
| 401 | 未认证 / 会话过期 | Token 失效、过期 |
| 403 | 已认证但无权 | 跨用户访问（`PermissionError`） |
| 404 | 资源不存在 | 条目已被删除 |
| 409 | 冲突 | 用户名已存在 |
| 422 | 校验失败 | pydantic 校验不通过（**中文提示**） |
| 429 | 限流 | 登录失败次数超限 |
| 500 | 服务端错误 | 未预期异常（含 `request_id` 便于定位） |

### 11.5 会话与鉴权流程

```mermaid
sequenceDiagram
    participant C as 客户端
    participant A as /auth
    participant S as security
    participant API as 业务接口

    C->>A: POST /login {username, password}
    A->>S: 校验口令（PBKDF2）
    S-->>A: OK
    A->>S: 签发 access(2h) + refresh(7d)
    S-->>A: tokens（含 user_id + token_version）
    A-->>C: 200 {access_token, refresh_token}

    C->>API: GET /l2/conflicts<br/>Authorization: Bearer <access>
    API->>S: 验证签名 + 算法白名单 + token_version
    S-->>API: user_id
    API->>API: 仓储 _guard(user_id)
    API-->>C: 200 [...]
```

| 机制 | 设计 |
|---|---|
| **Access Token** | 2 小时 |
| **Refresh Token** | 7 天 |
| **算法白名单** | 防 alg 混淆攻击（不允许 `alg=none`） |
| **token_version** | 改密/注销后自增 → **所有旧 token 立即失效**（无需黑名单） |
| **`?token=` 兜底** | 仅用于 `<img src>` 场景（浏览器直发请求无法带头） |

> **会话失效必须可恢复**：401 响应需区分两类语义——「凭证错误」（应直接向用户报错）与「会话过期」（应触发重新认证）。若将二者等同处理，会话过期后界面将停留在无效状态而无法恢复（见附录 C 第 7 条）。**因此任何标识会话过期的 401 都必须触发重新认证流程，不得静默失败。**

#### 12.4.2 运维操作要点

| 场景 | 操作要点 |
|---|---|
| **服务重启** | 须确认原进程完全退出后再启动。`--reload` 模式下的子进程可能继承监听端口，导致新配置未生效（见附录 D 运行环境类条目） |
| **数据备份** | 执行一键备份脚本（备份 `dev.db` 与 `data/` 目录），或通过 `GET /api/v1/knowledge/export` 导出知识数据 |
| **数据模型变更** | 停服 → 执行结构调整（`ALTER TABLE` 或重建库，见 §5.5）→ 重启 → 执行全量测试 |
| **功能异常定位** | 按「数据层 → 服务层 → 前端」顺序分层排查：先确认数据完整性与服务可用性，再检查前端运行状态 |
| **数据异常排查** | 全程只读操作，避免排查过程引入二次变更（用户数据敏感） |
| **成本异常定位** | 查询 `cost_logs`，按 `task_type` 聚合定位成本来源（见 §13.3） |

> **关于排查顺序的说明**：系统曾出现「页面数据为空」的现象，其可能成因包括数据缺失、服务不可用、会话失效三类，且三者表象相同。设计中明确了分层排查顺序——**数据层（数据是否存在）→ 服务层（接口是否正常）→ 前端层（会话与渲染状态）**，前两层可通过只读查询与接口探测快速排除，从而将问题范围精确收敛。该排查路径已作为运维规范固化。

## 13. 出错处理与可观测性

### 13.1 出错处理策略（分层）

| 层 | 错误类型 | 处理策略 |
|---|---|---|
| **接口层** | 参数校验失败 | pydantic → 422 + 中文提示 |
| **接口层** | 未认证 | 401，前端统一跳转登录 |
| **仓储层** | 跨用户访问 | 抛 `PermissionError` → 403 |
| **编排层** | LLM 返回非法 JSON | `parse_json` 三层退让；仍失败则跳过该候选，不中断整批 |
| **编排层** | LLM 服务不可用 | 网关重试 3 次指数退避；仍失败则向上抛 |
| **编排层** | 向量模型不可用 | 降级为关键词检索 |
| **任务层** | 处理器异常 | 留在 pending，`attempts+1`，退避重试 |
| **任务层** | 重试超上限 | 转 `dead`，保留 `last_error` 现场 |
| **推送层** | 重复内容 | `content_hash` 唯一约束挡回 |
| **全局** | 未预期异常 | 500 + `request_id`，服务端记完整堆栈 |

### 13.2 可观测性三支柱

| 支柱 | 实现 | 设计用途 |
|---|---|---|
| **日志** | `core/logging.py` + `request_id` 全链路贯穿 | 支持从用户反馈定位到具体请求的完整执行记录 |
| **成本埋点** | `cost_logs` 表：`task_type` / `model` / `reasoning` / `prompt_version` / `cached_tokens` / `estimated_cost` | 成本归因分析与异常成本发现 |
| **业务事件** | `learning_events`（append-only）：`event_type` + `occurred_at` + `payload` | L5 归因分析的事实依据与行为统计基础 |

### 13.3 成本可观测性设计

`cost_logs` 的字段设置以**支持具体成本归因问题**为目的，每个字段对应一类可回答的问题：

| 字段 | 可回答的问题 |
|---|---|
| `task_type` | 成本主要来源于哪一能力 |
| `reasoning` | 开启推理的任务占成本比例（用于验证 §6.3.1 策略表配置合理性） |
| `model` | 模型切换前后的成本对比 |
| `prompt_version` | 提示词变更是否引起 token 用量增长 |
| `cached_tokens` | 上下文缓存命中情况（命中单价约为普通输入的 1/50，是主要成本优化点） |
| `request_id` | 该次调用归属的用户请求 |
| `estimated_cost` | 分时计价后的实际成本（人民币） |

> **成本埋点置于网关层的设计理由**：这是模型调用「唯一收口」的直接收益——由于全系统仅网关一处发起模型调用，**不存在遗漏埋点的调用路径**，成本数据的完整性由结构保证。

### 13.4 已知的可靠性边界

以下为当前设计中**明确接受的能力边界**，其取舍依据见 §2.1 设计目标优先级与 §10.2 选型论证：

| 场景 | 当前行为 | 影响 | 设计考量 |
|---|---|---|---|
| Web 进程停止 | Worker 线程随之停止 | 任务积压，重启后自动继续 | 单进程部署的固有取舍（§10.2 ADR-13），对单机应用可接受 |
| SQLite 文件损坏 | 服务无法启动 | 需从备份恢复 | 依赖备份机制（§12.4），已提供一键备份与导出能力 |
| 向量模型未就绪 | 降级为关键词检索 | 召回质量下降 | 功能不缺失，符合 §10.3 可降级设计原则 |
| 未配置模型密钥 | 路由至 Mock 实现 | 无真实智能输出 | 为环境无关验证与自动化测试所必需（§10.3） |
| 存储空间耗尽 | 写库失败 | 任务转入死信状态 | 需外部监控配合，已列入 §15.1 风险项 |

### 14.4 质量评测集（Golden Set）

`tests/golden/` 保存**人工标注的评测样本**，用于验证智能能力的**输出质量**，区别于功能正确性验证：

| 用途 | 说明 |
|---|---|
| 回归防护 | 提示词变更后比对能力输出，检测质量退化 |
| 阈值调优 | 调整 L2 漏斗阈值时评估召回率损失 |
| 提示词版本对比 | 以同一评测集比较不同提示词版本的效果差异 |

> **功能性测试与质量评测的作用区分**：262 项自动化测试验证「实现是否符合设计预期」（即功能正确性与异常处理），具有确定性，可作为交付门禁；Golden Set 验证「智能能力输出是否有效」，具有统计性，作为调优与回归评估依据。二者不可相互替代——前者保证系统可靠运行，后者保证设计目标 G2（功能性完备）在语义层面达成。

|---|---|---|---|
| 1 | 新增 ORM 实体但未在 `__init__.py` 注册 | §5.5、§9.2 | 必须注册；未注册时不产生显式错误，缺陷具有隐蔽性 |
| 2 | 假设 `create_all` 会为已存在的表添加列 | §5.5 | 显式执行结构调整（`ALTER TABLE` 或重建） |

## 结语

本设计说明书的核心设计主张可归纳为四条：

1. **约束以结构保障，不以约定保障。** 越权防护实现于仓储基类、任务幂等由数据库唯一约束保障、模型调用收口于单一网关——**通过结构使违规实现方式不可表达**，其可靠性高于依赖编码规范的约束方式（§7.3）。

2. **低成本筛选前置，高成本推理后置。** L2 五级候选漏斗、按任务类型的推理开关、增量扫描标记——所有智能能力的成本控制均遵循「先以规则与数据库筛选，再对少量高价值候选执行模型推理」的原则（§6.4）。

3. **可降级性优先于峰值性能。** 未配置密钥时降级至 Mock 实现、向量模型未就绪时降级至关键词检索、调用失败时执行重试与死信处理——**每一处外部依赖均有降级路径**，保证系统在各类环境条件下均能运行（§10.3）。

4. **扩展以追加方式实现，不以修改方式实现。** §7.2 的扩展性验证表明，新增能力仅需修改 2 处既有文件（且均为注册式追加）。**任何被迫修改既有能力模块的扩展，均表明存在需下沉的耦合**——这是本设计解耦有效性的量化判据。
