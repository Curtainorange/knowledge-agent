# 第一部分 · 认识这个系统

## 1. 文档说明

### 1.1 文档目的

本文档将《需求分析文档》中的需求基线，转化为**可直接指导编码的设计方案**。它不是产品宣传材料，而是开发者每天要打开的工作参照：

- 新人**照着第 2 章就能把系统跑起来**，当天下第一个 commit；
- 开发者接手一个功能时，能在第 6 章找到**这个功能落在哪个文件、依赖哪些下层、不许依赖什么**；
- 评审者能用第 7 章的解耦规则与第 9 章的 DoD **机械化地判断一个 PR 合不合格**；
- 测试工程师能从第 14 章与第 16 章追溯矩阵**反查出该功能该测哪些用例**。

> **本文档的取舍原则**：凡是能从代码里一读就得到的信息（字段名、函数签名），文档不重复抄写；凡是代码里读不出、或需要跨文件才能推出结论的信息（依赖规则、为什么这样选、复用点在哪儿、边界在哪），文档必须写清。**文档的价值在于写清「约束」和「理由」，而不是复述「实现」。**

### 1.2 读者对象与阅读路线

| 读者角色 | 建议路线 | 重点关注 |
|---|---|---|
| **新加入的后端开发** | 1 → 2 → 4 → 6 → 9 | 环境搭建、代码地图、DoD、模块归属 |
| **接手某个能力的开发** | 3 → 6.x → 7 → 8 | 该能力的用例、所属文件、可用抽象、禁止依赖 |
| **评审者 / Tech Lead** | 7 → 9 → 10 | 解耦规则、DoD、技术选型理由 |
| **测试工程师** | 3 → 11 → 14 → 16 | 用例图、接口契约、测试策略、追溯矩阵 |
| **前端 / 客户端开发** | 3 → 11 | 用例图、REST 契约、鉴权与会话 |
| **运维 / SRE** | 12 → 13 | 部署拓扑、配置项、可观测性、出错处理 |
| **产品 / 评审人员** | 1 → 3 → 15 → 16 | 功能视图、演进路线、需求覆盖 |

### 1.3 术语表

| 术语 | 说明 |
|---|---|
| **L1~L5** | 五大能力：L1 模糊意图认知挖掘 / L2 冲突检测 / L3 认知助产 / L4 路径自我修正 / L5 偏误诊断 |
| **ModelGateway** | 统一模型网关，全系统唯一出网调用点，负责策略路由、重试、成本埋点 |
| **Provider** | 单个模型服务封装（DeepSeek / Mock），实现 `LLMProvider` 接口 |
| **Strategy** | 任务类型 → 调用参数（是否开 reasoning、模型名）的映射条目 |
| **Orchestrator** | 编排层，负责单条用例的完整流程编排（L1~L5 各有其一） |
| **Repository** | 仓储，唯一允许碰数据库的层，且强制 `user_id` 过滤 |
| **TaskRun** | 异步任务运行记录，承载幂等键、重试次数、死信现场 |
| **幂等键（idempotency_key）** | 业务语义去重键（如「某用户 2026 年第 37 周的冲突扫描」），数据库唯一约束兜底 |
| **结构性防越权** | 通过在类型系统 / 仓储基类层面强制过滤，而非依赖开发者自觉 |
| **收口（choke point）** | 某类操作在全系统中只允许存在一处实现的性质 |
| **DoD** | Definition of Done，完成的定义（见 9.4） |

## 2. 开发者上手路径

本章回答一个问题：**一个新人拿到这套代码，第一天该怎么做。**

### 2.1 五分钟跑起来

```bash
# ① 获取代码
git clone <repo-url> && cd 知识学习智能体

# ② 建虚拟环境（Python ≥ 3.12）
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# ③ 装依赖（含开发依赖）
pip install -e ".[dev]"

# ④ 启动（无需任何 API KEY 即可完整跑通）
uvicorn app.main:app --reload --port 8000
```

打开 <http://127.0.0.1:8000/> 即可看到登录页，注册一个账号即可体验全部五大能力。

> **无需 API KEY 是本项目的刻意设计**：未配置 `DEEPSEEK_API_KEY` 时，`ModelGateway` 自动路由到 `MockProvider`（确定性、零成本、零网络）。这让**新人不花钱、不配环境、不申请凭证就能跑通全链路**，也保证了测试的确定性与可重复性（见 §10.3）。

**可选**：配置真实模型以获得真实智能

```bash
export DEEPSEEK_API_KEY=sk-xxxx        # Windows PowerShell: $env:DEEPSEEK_API_KEY="sk-xxxx"
uvicorn app.main:app --reload --port 8000
```

**可选**：启用本地向量语义检索（首次需下载模型，约 100MB）

```bash
export EMBEDDING_BACKEND=local
# 国内网络可加镜像：
export HF_ENDPOINT=https://hf-mirror.com
```

未启用时，检索自动降级为**关键词通道**，功能不缺失、只是召回质量下降。

### 2.2 跑测试（提交前必做）

```bash
pytest                    # 254 项，应全绿
pytest tests/test_l2.py   # 只跑冲突检测
pytest -k "conflict"      # 按名称过滤
```

前端改动额外做语法校验（项目只有两个前端资产文件）：

```bash
node --check web/assets/app.js
```

> **铁律**：`pytest` 不全绿不许提交。前端 JS 改动必须过 `node --check`。

### 2.3 代码地图：我要改的东西在哪儿

这是新人最需要的表。**按「我想做什么」查，而不是按目录名猜。**

| 我想…… | 去哪儿 | 关键文件 |
|---|---|---|
| 加一个 API 接口 | `app/api/endpoints/` | 按业务域选文件（如 `l2.py`），加 `@router.post(...)` |
| 改数据库表结构 | `app/domain/models/` | 对应实体文件；新增表**必须**在 `app/domain/models/__init__.py` 注册 |
| 写数据库查询 | `app/domain/repositories/` | 继承 `BaseRepository`，用 `_guard()` 做越权防护 |
| 改某个能力的业务流程 | `app/agent/` | `l1_orchestrator.py` ~ `l5_orchestrator.py` |
| 改调用大模型的方式 | `app/llm/` | **只改网关**。业务代码不许直接碰 provider |
| 改提示词 | `app/llm/prompts.py` | 集中管理，改完必须更新 `prompt_version` |
| 加一个后台任务 | `app/workers/handlers.py` | 用 `@register("task_name")` 注册处理器 |
| 加一个定时/触发条件 | `app/workers/triggers.py` | 构造幂等键并入队 |
| 改检索逻辑 | `app/retrieval/` | `retriever.py` 是入口 |
| 改业务事件的埋点 | `app/feedback/events.py` | `LearningEvent` 是 append-only 的 |
| 改前端页面 | `web/` | 页面 `.html`，共享逻辑与样式在 `web/assets/` |
| 改全局样式 | `web/assets/style.css` | **全站唯一一份**，改这里即全站生效 |
| 改配置项 | `app/core/config.py` | pydantic-settings，支持环境变量覆盖 |
| 加一个测试 | `tests/` | 按模块命名，如 `test_l2.py` |
| 查历史踩坑 | `dev_logs/复盘与教训.md` | 遇到诡异 bug 先来这里搜 |

### 2.5 第一次改动的推荐路径

新人**不要**一上来就改 L2 冲突检测（那是全系统最复杂的算法）。推荐的第一次改动顺序，难度递增：

| 顺序 | 练手任务 | 涉及层 | 为什么适合 |
|---|---|---|---|
| 1 | 给 `GET /api/v1/knowledge/items` 加一个排序参数 | api → repository | 单层穿透，看清「接口→仓储」的关系 |
| 2 | 在 `KnowledgeItem` 上加一个字段并透出到接口 | model → repository → api | 走完一次完整的纵向切片 |
| 3 | 新增一个异步任务（如「每日统计用户新增知识数」） | workers + domain | 理解幂等键与任务注册表 |
| 4 | 给 L5 诊断加一个新的行为模式识别规则 | agent → llm | 理解编排层与网关的关系（**提示词改动也要走网关**） |
| 5 | 优化 L2 候选漏斗的某个阈值 | agent + config | 最复杂，需要理解五级漏斗与成本权衡 |

> 每完成一项，**必须**同步更新测试与 `dev_logs/` 当日日志（见 §9.5）。

## 3. 系统功能视图（用例图）

本章给出系统的**功能边界**：谁在用、能用它做什么、哪些用例彼此包含或扩展。这是 V2.2 缺失、本次补齐的核心图表。

### 3.1 参与者（Actor）识别

| 参与者 | 类型 | 说明 |
|---|---|---|
| **学习者（Learner）** | 主参与者 | 系统的唯一真实用户。所有能力的服务对象 |
| **定时器（Scheduler）** | 系统参与者 | 驱动周期性用例：每周简报、每月健康报告、周度冲突扫描 |
| **摄取触发（Ingest Trigger）** | 系统参与者 | 知识入库后驱动增量冲突扫描 |
| **DeepSeek 模型服务** | 外部系统 | 被 `ModelGateway` 调用，提供推理能力 |
| **本地向量模型（BGE）** | 外部系统 | 被检索层调用，提供语义向量 |

> **设计要点**：本系统是**单用户视角的个人工具**，不存在「管理员」角色。所有数据访问均以 `user_id` 为强制作用域（见 §7.3），因此「越权」在结构中不可能发生，而非靠权限校验拦截。

### 4.2 架构风格：分层 + 端口适配 + 收口

本系统采用**三层主体 + 一个横切收口**的结构：

| 层次 | 职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| **表现层** `api/` | HTTP 协议转换、参数校验、鉴权、序列化 | 编排层、领域层、core | ❌ 不许含业务逻辑<br/>❌ 不许直接调 `llm/` |
| **编排层** `agent/` | 单条用例的流程编排、多步协调、降级决策 | 领域层、llm/、retrieval/、workers/ | ❌ 不许直接操作 `Session`（须经仓储） |
| **领域层** `domain/` | 实体定义、持久化、数据完整性 | core | ❌ 不许依赖 `llm/`、`api/`<br/>❌ 不许依赖 `agent/` |
| **支撑层** `llm/ retrieval/ workers/ core/` | 提供被上层调用的能力 | core | ❌ `llm/` 不许依赖 `agent/` |

**两个关键收口（choke point）**——本架构最重要的设计决策：

| 收口 | 含义 | 工程收益 |
|---|---|---|
| **模型调用收口于 `ModelGateway`** | 全系统只有这一个地方发 LLM 请求 | 换供应商改 1 个文件；成本/重试/日志在一处统一，不会漏埋点 |
| **数据库访问收口于 Repository** | 全系统只有仓储层碰 `Session` | 越权防护在基类一处实现，12 个仓储自动继承，不可能漏 |

```mermaid

```

**四条铁律**（违反即 PR 驳回）：

1. **依赖必须单向向下**：`api → agent → domain/llm`。反向依赖一律禁止。
2. **`domain/` 必须保持纯净**：它不许知道「有 LLM 这回事」。这样领域模型可以被任何上层复用，也便于未来替换模型层。
3. **`llm/` 必须对上层无感知**：网关不知道谁在调它，只按 `task_type` 决定策略。这样新增能力无须改模型层。
4. **`capabilities/` 内部互不 import**：五大能力必须彼此隔离，只通过领域层共享数据。这样任何一个能力可以独立重构甚至删除。

> **为什么第 4 条重要**：L1~L5 在业务上高度相关（都要用知识库、都要调模型），很容易写出 `l3 调 l2 的函数` 这种耦合。这会立刻产生「改 L2 阈值导致 L3 崩」的连锁效应。**共享逻辑必须下沉到 `domain/` 或 `llm/`，而不是横向互调。**

### 4.5 状态机设计

系统中有三处显式状态机，它们是「数据一致性」的核心保障。

#### 4.5.1 异步任务状态机（`TaskRun`）

```mermaid
stateDiagram-v2
    [*] --> pending: enqueue（幂等键唯一约束）
    pending --> running: worker 取出
    running --> succeeded: 执行成功
    running --> pending: 失败且 attempts < max<br/>（退避后重试）
    running --> dead: 失败且 attempts ≥ max<br/>（保留 last_error 现场）
    pending --> pending: 重复入队被 DB 挡回<br/>（视为已存在）
    succeeded --> [*]
    dead --> [*]
```

> **为什么失败不直接转 dead**：失败留在 `pending` 并递增 `attempts`，下一轮轮询自然重试，用 `updated_at` 做退避时间锚点（`2^(n-1)` 秒起、上限 60 秒）。这样**重试不需要额外的调度器**，一个轮询循环就够。

#### 4.5.2 冲突用户状态机（`Conflict.user_state`）

```mermaid
stateDiagram-v2
    [*] --> unseen: 扫描产出
    unseen --> accepted: 用户认可（触发「转学习计划」扩展用例）
    unseen --> ignored: 用户忽略
    ignored --> ignored: 同类型累计 ≥N 次<br/>→ 该类型不再推荐
    accepted --> [*]
```

#### 4.5.3 诊断状态机（`CognitiveDiagnosis.status`）

```mermaid
stateDiagram-v2
    [*] --> pending: L5 诊断产出
    pending --> accepted: 用户认可
    pending --> rejected: 用户否决
    accepted --> [*]
    rejected --> [*]
```

> **反馈闭环的意义**：这三处状态机不是为了「记录状态」，而是为了让系统**能被用户纠正**——用户的忽略/认可会反过来收敛后续推荐（误报抑制）。

### 4.6 运行设计（部署内视图）

单进程内的运行视图：

```
uvicorn 进程
├── 主线程：asyncio 事件循环
│    └── FastAPI 处理 HTTP 请求
│         ├── 中间件链：request_id → static_cache
│         ├── 路由分发 → 编排层 → 领域层
│         └── 静态文件托管（/assets, /xxx.html）
└── 守护线程：Worker 轮询循环（worker_enabled=false 可关）
     └── run_pending() → 取 pending 任务 → 执行处理器 → 更新状态
```

**关键约束**：

| 约束 | 说明 |
|---|---|
| **Worker 与 Web 同进程** | 不引入 Celery/Redis（见 §10.2 ADR-13）。代价是「Web 挂了 Worker 也停」，但单机个人工具可接受 |
| **测试中必须关闭 Worker** | 测试设 `worker_enabled=false`，避免后台线程干扰与不确定的时序 |
| **任务执行是同步的** | Worker 线程内串行执行，不给用户请求造成并发压力 |
| **SQLite 单写者** | 所有写操作串行化，避免 SQLite 写锁竞争 |

### 5.2 表职责与设计要点

| 表 | 职责 | 设计要点 |
|---|---|---|
| `users` | 账号 | `token_version` 用于**全局吊销**旧 JWT（改密/注销后所有旧 token 立即失效） |

| `books` | 书籍与阅读进度 | `chapters` 存 JSON 章节结构；`current_char` 是字符偏移而非页码（适配任意重排） |

| `cost_logs` | 成本埋点 | `cached_tokens` 与 `prompt_version` 让成本优化可归因 |
| `push_jobs` / `push_logs` | 推送 | `push_logs.content_hash` 唯一 → **同内容绝不重复推** |
| `cognitive_diagnoses` | L5 产出 | `reasoning_chain` 存完整推理链，让诊断**可解释、可质疑** |

### 5.3 索引设计

索引不是「加了就好」——每个索引都对应一条**真实的高频查询**。

| 索引 | 表 | 支撑的查询 |
|---|---|---|
| `(user_id, topic)` | `claims` | L2-3 同主题预筛：`topic` 与 `user_id` 组成候选对生成索引 |
| `(user_id, user_state)` | `conflicts` | 待推送冲突查询：只看 `unseen` |
| `user_id` | 几乎所有表 | 强制用户作用域过滤（结构性防越权的物理基础） |
| `idempotency_key` (UNIQUE) | `task_runs` | 幂等入队的数据库级保障 |
| `content_hash` (UNIQUE) | `push_logs` | 推送去重 |
| `event_type` / `occurred_at` | `learning_events` | L5 按类型与时间聚合行为模式 |
| `pair_key` | `conflicts` | 冲突去重查询 |

### 5.4 数据完整性策略

| 策略 | 实现 |
|---|---|
| **软删** | `knowledge_items.is_deleted` / `books.is_deleted` / `users.deleted_at`，物理清除须等保留期 |
| **时间戳** | `TimestampMixin` 统一提供 `created_at` / `updated_at`（带时区） |
| **主键** | 统一 `String(36)` 存 UUID4 字符串——**不用自增 int**，便于未来分库与外部系统对账 |
| **乐观锁** | `learning_plans.version`，更新时校验版本号 |
| **外键** | 逻辑外键（SQLAlchemy 层维护关系），未启用数据库级 FK 约束以简化 SQLite 迁移 |

> **一个已知取舍**：`users.push_frequency` 与 `embedding` 用 pickle 存 bytes。好处是零依赖；代价是**跨语言不可读**（未来接外部系统时需迁移，已列为 §15 演进项）。

### 5.5 Schema 演进规则

**这是本项目踩过的坑，必须遵守**（详见 `dev_logs/复盘与教训.md` 第 2 条）：

| 规则 | 原因 |
|---|---|
| **新增表必须注册到 `app/domain/models/__init__.py`** | `Base.metadata.create_all()` 只扫描被 import 过的模型。漏注册 = 表不存在，且**不报错**，直到该表被查询时才炸 |
| **`create_all` 不会给已有表加列** | SQLite 的 `CREATE TABLE IF NOT EXISTS` 语义对已存在的表是空操作。加字段必须手工 `ALTER TABLE` 或重建库 |
| **改 schema 后必须重启服务器** | 不要只信 `--reload`；schema 缓存与连接池会让旧结构继续生效 |
| **改 schema 后必须跑全量 pytest** | 测试用独立库，能最快暴露「表结构漂移」 |
| **生产迁移用 Alembic** | 依赖已装（`alembic>=1.13`），P0 阶段手工迁移，P1 起必须走迁移脚本 |

#### 6.2.1 仓储基类（`app/domain/repositories/base.py`）

class BaseRepository(Generic[_T]):
    def __init__(self, session: Session, user_id: str | None = None): ...

    def _guard(self, owner_user_id: str) -> None:
        """结构性越权防护：绑定用户后，仅允许访问归属本用户的行。"""
        if self._user_id and owner_user_id != self._user_id:

**L2 五级漏斗**（全系统最核心的算法，成本与准确率的平衡点）：

```
全量知识条目
  │  L2-1 增量筛选：claims_scanned_at IS NULL  → 只处理新增
  ▼
待提取条目
  │  L2-6 主张提取：LLM 批量抽取原子主张（reasoning=off，省钱）
  ▼
主张集合
  │  L2-3 同主题预筛：按 (user_id, topic) 取同主题候选对  → 避免 O(n²)
  ▼
候选对
  │  L2-4 立场强度过滤：极性相异 且 强度达标
  ▼
高潜候选对（数量已降 1~2 个数量级）
  │  L2-5 LLM 判定：reasoning=on 精细判定（只对高潜对花大钱）
  ▼
疑似冲突
  │  L2-6 阈值抑制：置信度阈值 + 已忽略类型收敛 + pair_key 去重
  ▼
入库 conflicts
```

> **漏斗的核心思想**：**便宜的手段放前面，贵的手段放后面**。L2-1~L2-4 都是纯数据库/规则计算（几乎零成本），只有 1~2% 的候选对会进入 LLM 判定。这是 L2 能在个人机器上跑得动的原因。

### 6.5 异步任务层（`app/workers/`）

#### 6.5.1 三条核心机制（`app/workers/tasks.py`）

```python
- **幂等**：TaskRun.idempotency_key 唯一约束。重复入队由数据库挡回
  （IntegrityError → 视为已存在），不依赖应用层「先查再插」那种有竞态的做法。
- **重试**：失败不改状态为 dead，而是留在 pending、attempts+1，下一轮轮询再试；
  退避用 updated_at 作时间锚点，2^(n-1) 起步、上限 60 秒。
- **死信**：attempts ≥ max_attempts 转 dead 保留现场（last_error），不再自动重试。
```

| 项 | 内容 |
|---|---|
| **注册表** | `HANDLERS: dict[str, Handler]` + `@register("name")` 装饰器（重复注册抛 `ValueError`） |
| **入队** | `enqueue()` 返回 `EnqueueResult(created: bool)`——同 key 返回 `created=False` |
| **执行** | `run_pending()` 批量取 pending 任务并执行 |
| **幂等键构造** | `triggers.realtime_key()` / `weekly_key()` |

幂等键实例：

| 场景 | 幂等键格式 | 效果 |
|---|---|---|
| 实时冲突扫描 | `l2:realtime:{user}:{YYYYMMDDHH}` | **1 小时内同用户只扫一次**，用户狂点按钮也不会重复烧钱 |
| 周度冲突扫描 | `l2:weekly:{user}:{ISO年}-W{ISO周}` | 一周一次，跨进程重启也不会重跑 |
| 每周简报 | 含 ISO 周 | 定时器重复触发也只推一次 |

> **幂等键是本项目最优雅的设计之一**：它把「去重」这个业务需求，转化为**数据库唯一约束**这个基础设施能力。不需要分布式锁、不需要 Redis、不需要状态查询——**插入失败就是重复**。

#### 6.5.2 任务处理器（`app/workers/handlers.py`）

| 处理器 | 任务名 | 职责 |
|---|---|---|
| `l2_scan` | `l2_scan` | 调 L2 编排器执行冲突扫描 |
| `push_weekly_digest` | 对应 | 装配并推送每周认知简报 |
| `push_monthly_health` | 对应 | 装配并推送每月学习健康报告 |

**处理器的三条纪律**：
1. 只做「取参数 → 调编排层 → 记日志」，**不含业务逻辑**；
2. 失败**直接抛异常**，交给框架重试——不要自己 try/except 吞掉；
3. 必须可以**重复执行而无副作用**（幂等），因为可能被重试。

### 6.6 检索层（`app/retrieval/`）

| 项 | 内容 |
|---|---|
| **入口** | `Retriever`（`retriever.py`） |
| **双通道** | 向量通道（BGE 余弦相似度）+ 关键词通道（`keyword.py`） |
| **融合** | 加权求和，`vec_weight=0.7`（可配） |
| **向量后端** | `BGEHesEmbedding`：`BAAI/bge-small-zh-v1.5`，512 维，**惰性加载** |
| **序列化** | `EmbeddingModel.dumps()` / `loads()`（pickle → bytes 存库） |
| **降级** | 向量模型不可用 → 仅关键词通道，功能不缺失 |
| **测试要点** | `tests/test_retrieval.py`（4 项）+ `test_embedding.py`（10 项） |

> **为什么坚持双通道**：向量召回质量高但**依赖模型下载与计算**；关键词召回质量一般但**永远可用**。两条通道让系统在「模型没下好 / 内网无网 / 内存不足」时仍能工作。**可降级比高性能更重要**。

## 7. 架构解耦规则

本章是**评审者的检查清单**。每一条都可以机械化地判断「违反 / 未违反」。

### 7.1 依赖方向检查表

| # | 规则 | 检查方式 | 违反后果 |
|---|---|---|---|
| D-1 | `domain/` 不许 import `llm/`、`agent/`、`api/` | `grep -r "from app.llm\|from app.agent\|from app.api" app/domain/` 应为空 | 领域层被模型层污染，无法独立测试与复用 |
| D-2 | `llm/` 不许 import `agent/` | `grep -r "from app.agent" app/llm/` 应为空 | 网关产生对具体业务的耦合，换供应商要改业务代码 |
| D-3 | `api/` 不许直接 import `llm/` | `grep -r "from app.llm" app/api/` 应为空 | 绕过网关 → 成本漏埋点、重试策略失效 |
| D-4 | `api/` 不许直接操作 `Session` | 只见 `Depends(get_session)` 传给仓储 | 绕过 `_guard` → 越权风险 |
| D-5 | `capabilities/` 内部互不 import | `grep -r "from app.capabilities" app/capabilities/` 应为空 | 能力耦合，改动连锁崩溃 |
| D-6 | `agent/` 不许自己 `session.add()` 写库 | 只见仓储方法调用 | 绕过仓储 → 越权 + 事务散乱 |

> **建议**：这 6 条可以在 CI 里用 `grep` 或 `import-linter` 自动化守卫。当前靠人工评审 + 约定，已列入 §15 演进项。

### 7.2 扩展点设计：如何加一个新能力

假设要新增「L6 学习风格识别」。**正确的做法**（全程不改动任何已有文件，除了注册）：

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 在 `agent/` 新建 `l6_orchestrator.py` | 编排流程，依赖 `domain/` 与 `llm/` |
| 2 | 在 `api/endpoints/` 新建 `l6.py` | 定义路由，调 `l6_orchestrator` |
| 3 | 在 `app/main.py` 加一行 `include_router(l6.router)` | **唯一需要改的已有文件** |
| 4 | 在 `llm/gateway.py` 的 `STRATEGY_TABLE` 加一条 `task_type` | **唯一需要改的模型层文件** |
| 5 | 在 `llm/prompts.py` 加提示词 + 版本号 | 集中管理 |
| 6 | 在 `domain/models/` 加实体（如有），并**注册到 `__init__.py`** | 见 §5.5 |
| 7 | 在 `tests/` 加 `test_l6.py` | 见 §9.4 |

> **衡量解耦是否成功的标准**：加这个新能力时，**没有修改任何 L1~L5 的代码**。如果被迫改了，说明有耦合需要下沉。

### 7.3 数据隔离规则

| 规则 | 实现 | 保障级别 |
|---|---|---|
| 所有业务查询必须带 `user_id` | `BaseRepository._guard()` | **结构级**（不是约定级） |
| 跨用户访问抛 `PermissionError` | 基类统一实现 | 无法绕过 |
| JWT 中携带 `user_id` 与 `token_version` | `core/security.py` | 吊销可信 |
| 软删数据默认过滤 | 仓储的 `list_*` 方法 | 默认安全 |

> **结构性 vs 约定性的差别**：约定性防护是「所有开发者都要记得写 `WHERE user_id = ?`」——总有人会忘。结构性防护是把过滤做进基类，**忘不掉**。这是本项目安全设计的核心思路。

### 7.4 可替换性设计

| 可替换项 | 替换方式 | 影响范围 |
|---|---|---|
| **LLM 供应商** | 实现新的 `LLMProvider` 子类 + 改 `_build_provider()` | 1 个文件 |
| **向量模型** | 实现新的 `EmbeddingModel` 子类 + 改配置 | 0 个业务文件 |
| **数据库** | 改 `database_url`（ORM 已抽象） | 1 个配置项（需处理 SQLite 特有语义） |
| **检索策略** | 改 `Retriever` 的融合权重或加通道 | 1 个文件 |
| **异步框架** | `tasks.py` 的 `enqueue`/`run_pending` 是接口边界，可换成 Celery | 1~2 个文件 |

> **ADR-13 的保留意见**：当前不引入 Celery/Redis（见 §10.2）。但 `enqueue()` / `run_pending()` 被设计成**框架无关的接口**，未来若需横向扩展，替换成本被控制在 2 个文件内。

### 8.4 新代码的复用指引

| 需求 | 复用 | 不要自己写 |
|---|---|---|
| 要访问数据库 | `BaseRepository` 子类 | ❌ 不要直接 `session.query()` |
| 要调 LLM | `ModelGateway.chat(task_type=...)` | ❌ 不要 `httpx.post(deepseek)` |

| 要算 token 成本 | `cost.py` 的计价函数 | ❌ 不要硬编码价格 |

| 要加异步任务 | `@register` + `enqueue` | ❌ 不要 `threading.Thread` |
| 要加限流 | `FailureThrottle` | ❌ 不要自己写滑动窗口 |
| 要发 LLM 请求失败重试 | 网关已内置 | ❌ 不要在外层再包一层重试 |

### 8.5 反面清单：什么不该被复用

**过度复用同样有害**。以下模式在本项目中**明确禁止**：

| 反模式 | 为什么禁止 |
|---|---|
| 抽一个「万能 `BaseService`」 | 五大能力业务差异大，强行统一会产生大量 `if capability == 'l2'` 分支 |
| L1~L5 之间互相调函数 | 违反 D-5，会产生改动连锁效应。共享逻辑下沉到 `domain/` 或 `llm/` |
| 把 prompt 拼在业务代码里 | 提示词必须集中在 `prompts.py`，否则无法做版本管理与 A/B |
| 通用 `dict` 到处传 | 用 dataclass（如 `L1Route`、`ExtractedClaim`）表达结构，让类型系统帮忙检查 |
| 前后端共享「同一份数据模型文件」 | 前后端无构建工具，强行共享会引入奇怪依赖。当前用接口契约（§11）保证一致 |

### 10.2 关键选型论证

#### ADR-01：为什么用 FastAPI

| 项 | 内容 |
|---|---|
| **选它** | FastAPI |
| **理由** | ① **pydantic 原生集成**——请求/响应校验免费获得，且能把校验错误翻译成中文（见 §6.1.1）；② **依赖注入**——`Depends` 让 `get_session` / `get_gateway` / 鉴权成为可组合的声明式依赖，鉴权出口天然唯一（§6.1.2）；③ **自带 OpenAPI 文档**——接口契约自动可查，前后端协作成本低；④ 异步支持好，为流式接口留出空间 |
| **放弃** | Flask（无原生校验与 DI）、Django（对单机小工具过重，ORM 层与本项目「薄领域层 + 重仓储」的设计不合） |
| **何时换** | 基本不需要换。除非要迁到 Serverless 且框架冷启动成为瓶颈 |

#### ADR-02：为什么用 SQLAlchemy 2.0 + Repository

| 项 | 内容 |
|---|---|
| **选它** | SQLAlchemy 2.0（声明式 + `Mapped[]` 类型注解）+ 自建 Repository 层 |
| **理由** | ① `Mapped[]` 注解让**字段类型对 IDE 与类型检查器可见**，配合 `__table_args__` 声明索引，schema 即文档；② 不直接用 ORM 查询，而是包一层 Repository——**这是结构性防越权的前提**（§7.3）；③ 仓储层还能隔离「列表与计数条件不一致」类 bug（R-16） |
| **放弃** | 裸 SQL（无类型安全）、Django ORM（与 FastAPI 不搭） |
| **成本** | 每张表要多写一个仓储类。**这个成本是刻意支付的**——换来的是安全级别从「约定」提升到「结构」 |
| **何时换** | 数据量上亿或需要复杂分析查询时，考虑引入专用查询层 |

#### ADR-03：为什么 P0 用 SQLite

| 项 | 内容 |
|---|---|
| **选它** | SQLite 单文件 `dev.db` |
| **理由** | ① **零部署**——个人工具，用户 `git clone` 后直接能跑，不需要装数据库；② 备份 = 复制一个文件（项目已有一键备份脚本）；③ 单用户场景无并发压力，SQLite 的单写者模型不是瓶颈 |
| **放弃** | PostgreSQL（部署成本高，收益要等数据量上来才体现） |
| **已知限制** | ① 无 pgvector，向量存 pickle bytes、检索时 Python 侧算余弦——**数据量大后是瓶颈**；② `create_all` 不给已有表加列（§5.5）；③ 无并发写 |
| **何时换** | 当「向量检索变慢」或「需要多实例部署」时。ORM 已抽象，主要改 `database_url` + 向量存储方案 |

#### ADR-11：为什么用 JSON Schema + 顽健解析

| 项 | 内容 |
|---|---|
| **选它** | 要求模型输出 JSON + `parse_json` 三层退让解析 |
| **理由** | ① LLM 输出是自由文本，**不能假设它听话**；② `response_format` 约束能提高合规率但不能保证；③ 三层退让（直接解析 → 剥围栏 → 截取花括号）覆盖了实测中 99% 的异常输出 |
| **放弃** | 纯正则提取（脆弱）、让模型输出 XML/YAML（模型训练数据少，合规率更低） |
| **何时换** | 若未来模型支持严格的 constrained decoding，可减轻但**不应移除**兜底 |

#### ADR-13：为什么不用 Celery / Redis

| 项 | 内容 |
|---|---|
| **选它** | 单进程「落库排队 + worker 轮询」 |
| **理由** | ① 引入 Celery 需要 **Redis/RabbitMQ 中间件**——违背「零部署」目标（ADR-03）；② 本项目任务量极小（每周几次扫描 + 推送），轮询完全够；③ **数据库唯一约束天然提供幂等**（幂等键设计），不需要分布式锁；④ 单进程让调试极简——不需要追踪跨进程状态 |
| **放弃** | Celery（重）、APScheduler（仍需要持久化任务状态的能力，`TaskRun` 表已提供了） |
| **关键设计** | `enqueue()` / `run_pending()` 被刻意设计成**框架无关的接口**——将来要换 Celery，只改这 2 个函数 |
| **何时换** | 当需要①多实例横向扩展②任务量剧增③任务需要独立资源隔离时。**替换成本被控制在 2 个文件内** |

#### ADR-14：为什么用 DeepSeek 单一模型 + reasoning 开关

| 项 | 内容 |
|---|---|
| **选它** | 单一模型 `deepseek-flash` + 每请求 `reasoning` 开关 |
| **理由** | ① **国产、可访问、价格低**；② OpenAI 兼容协议 → 未来换供应商改 1 个文件；③ 用 `reasoning` 开关替代「多模型档位」——**业务层只需声明「这个任务要不要深度思考」**，不需要知道模型细节；④ DeepSeek 的**自动上下文缓存**让重复前缀（系统提示词）成本降到 1/50 |
| **放弃** | 多模型路由（V2.0 的 Claude 方案已废弃）、自建推理 |
| **成本控制** | 策略表把批量提取类任务设为 `reasoning=off`（省 3~5 倍成本），只有冲突判定、因果推理、L1 定位开思考 |
| **何时换** | 需要更强推理能力或更低成本时；或需要多模态时 |

#### ADR-15：为什么前端零构建

| 项 | 内容 |
|---|---|
| **选它** | 原生 HTML/JS/CSS，无框架、无打包工具 |
| **理由** | ① **零构建 = 零配置 = 零依赖地狱**——`git clone` 就能跑；② 项目是 12 个页面的单机工具，**不需要组件化与状态管理**；③ 前端资产只有 2 个文件，`app.js` 承载全部共享逻辑（R-13），`style.css` 是唯一样式源（R-14） |
| **放弃** | React/Vue（引入构建链与 npm 依赖，收益不足） |
| **代价** | 无组件复用、无类型检查、需手工管理 DOM。**用「页面数量少」换「零维护成本」** |
| **配套措施** | ① `.html/.js/.css` 强制 `no-cache`（§6.1.1）避免缓存踩坑；② `node --check` 做语法校验；③ 前端行为用 Node 测试（`tests/js/`） |

### 10.3 MockProvider 的工程价值

`MockProvider` 不只是「没 KEY 时的降级」，它是**测试策略的基石**：

| 收益 | 说明 |
|---|---|
| **测试确定性** | 254 项 pytest 全部在 Mock 下运行，不依赖网络、不花钱、结果可重复 |
| **新人零门槛** | 不申请 KEY 就能跑通全链路 |
| **离线开发** | 无网环境可完整开发 |
| **成本归零** | CI 上跑测试不产生 API 费用 |
| **边界可控** | Mock 可精确构造「模型返回非法 JSON」「模型超时」等异常场景 |

> **这是本项目最值得强调的工程决策之一**：把 `LLMProvider` 抽象出来，Mock 就自然成为一等公民，而不是事后补的测试替身。

### 10.4 依赖管理原则

| 原则 | 说明 |
|---|---|
| **运行时依赖必须少** | 当前仅 9 个。每加一个依赖都在增加「新人上手成本」与「供应链风险」 |
| **不在框架能解决时引入库** | 例：限流自己写 40 行 `FailureThrottle`，不引 `slowapi` |
| **重依赖必须可降级** | 向量模型是可选依赖，缺失时自动降级关键词检索 |
| **加依赖必须说明理由** | 在 PR 描述里写清「为什么不能用现有能力解决」 |

### 11.3 关键接口契约示例

#### `POST /api/v1/l1/mine` —— L1 模糊意图挖掘

**请求**
```json
{ "query": "我好像在哪看过关于复利的讨论" }
```

**响应（定位成功 `decision=located`）**
```json
{
  "decision": "located",
  "items": [
    {
      "id": "uuid",
      "title": "《穷查理宝典》笔记",
      "snippet": "复利效应是……",
      "reason": "标题与内容均命中「复利」主题，且表述与查询意图一致",
      "is_readable": true,
      "source_locator": { "chapter_index": 3, "char_start": 1200, "char_end": 1500 }
    }
  ],
  "cost": { "prompt_tokens": 812, "completion_tokens": 96, "estimated_cost": 0.0021 }
}
```

**响应（需追问 `decision=clarify`）**
```json
{
  "decision": "clarify",
  "candidates": [
    { "id": "uuid", "title": "《穷查理宝典》笔记", "snippet": "……" }
  ],
  "question": "你是指「复利」这个概念的定义，还是某个具体场景下的复利应用？"
}
```

> **契约设计要点**：`decision` 是**判别式字段**，客户端按它分支渲染。这比返回两个可选字段（可能都为 null）更明确，也是「不做无中生有定位」这条业务规则的接口体现。

#### `PATCH /api/v1/l2/conflicts/{id}/state` —— 冲突反馈

**请求**
```json
{ "user_state": "ignored" }
```

**响应**
```json
{ "id": "uuid", "user_state": "ignored", "suppressed_type": false }
```

> `suppressed_type=true` 表示「同类型忽略已达阈值，该类型后续不再推荐」——**把误报抑制的效果如实告知用户**，而不是静默生效。

### 11.4 错误响应契约

统一格式，**中文可读**（踩过的坑：框架默认英文 JSON 直接怼到界面上，复盘第 5 条）：

```json
{
  "detail": "字段「截止日期」格式不正确，应为 ISO 8601 时间"
}
```

| 状态码 | 语义 | 示例场景 |
|---|---|---|
| 400 | 请求语义错误 | 参数组合非法 |
| 401 | 未认证 / 会话过期 | Token 失效、过期 |
| 403 | 已认证但无权 | 跨用户访问（`PermissionError`） |
| 404 | 资源不存在 | 条目已被删除 |
| 409 | 冲突 | 用户名已存在 |
| 422 | 校验失败 | pydantic 校验不通过（**中文提示**） |
| 429 | 限流 | 登录失败次数超限 |
| 500 | 服务端错误 | 未预期异常（含 `request_id` 便于定位） |

### 11.5 会话与鉴权流程

```mermaid
sequenceDiagram
    participant C as 客户端
    participant A as /auth
    participant S as security
    participant API as 业务接口

    C->>A: POST /login {username, password}
    A->>S: 校验口令（PBKDF2）
    S-->>A: OK
    A->>S: 签发 access(2h) + refresh(7d)
    S-->>A: tokens（含 user_id + token_version）
    A-->>C: 200 {access_token, refresh_token}

    C->>API: GET /l2/conflicts<br/>Authorization: Bearer <access>
    API->>S: 验证签名 + 算法白名单 + token_version
    S-->>API: user_id
    API->>API: 仓储 _guard(user_id)
    API-->>C: 200 [...]
```

| 机制 | 设计 |
|---|---|
| **Access Token** | 2 小时 |
| **Refresh Token** | 7 天 |
| **算法白名单** | 防 alg 混淆攻击（不允许 `alg=none`） |
| **token_version** | 改密/注销后自增 → **所有旧 token 立即失效**（无需黑名单） |
| **`?token=` 兜底** | 仅用于 `<img src>` 场景（浏览器直发请求无法带头） |

> **会话过期必须能回到登录页**：踩过的坑——401 被错误地排除在白名单外，导致页面变成空壳（复盘第 7 条）。**任何 401 都必须触发前端重新登录，不允许静默失败。**

### 12.4 运维要点

| 场景 | 操作 |
|---|---|
| **重启服务** | 杀进程后重启。⚠️ **必须确认旧进程真的死了**——`--reload` 的僵尸子进程会继承端口，导致「重启了却还是旧行为」（复盘第 8、9 条） |
| **备份** | 跑一键备份脚本（复制 `dev.db` + `data/`），或 `GET /api/v1/knowledge/export` |
| **改 schema** | 停服 → 手工 `ALTER TABLE` 或重建库 → 重启 → 跑全量 pytest |
| **排查「功能全崩」** | **第一步先确认是不是同一个服务器**（复盘第 8 条） |
| **排查「数据没了」** | 只读排查，不边查边改（用户数据敏感）；顺序见 `dev_logs/复盘与教训.md` 第 11 条 |
| **成本异常** | 查 `cost_logs` 按 `task_type` 聚合，看是哪个能力在烧钱 |

## 13. 出错处理与可观测性

### 13.1 出错处理策略（分层）

| 层 | 错误类型 | 处理策略 |
|---|---|---|
| **接口层** | 参数校验失败 | pydantic → 422 + 中文提示 |
| **接口层** | 未认证 | 401，前端统一跳转登录 |
| **仓储层** | 跨用户访问 | 抛 `PermissionError` → 403 |
| **编排层** | LLM 返回非法 JSON | `parse_json` 三层退让；仍失败则跳过该候选，不中断整批 |
| **编排层** | LLM 服务不可用 | 网关重试 3 次指数退避；仍失败则向上抛 |
| **编排层** | 向量模型不可用 | 降级为关键词检索 |
| **任务层** | 处理器异常 | 留在 pending，`attempts+1`，退避重试 |
| **任务层** | 重试超上限 | 转 `dead`，保留 `last_error` 现场 |
| **推送层** | 重复内容 | `content_hash` 唯一约束挡回 |
| **全局** | 未预期异常 | 500 + `request_id`，服务端记完整堆栈 |

### 13.2 可观测性三支柱

| 支柱 | 实现 | 用途 |
|---|---|---|
| **日志** | `core/logging.py` + `request_id` 贯穿 | 从用户报错 → 定位到具体请求的全部日志 |
| **成本埋点** | `cost_logs` 表：`task_type` / `model` / `reasoning` / `prompt_version` / `cached_tokens` / `estimated_cost` | 成本归因；发现异常烧钱 |
| **业务事件** | `learning_events`（append-only）：`event_type` + `occurred_at` + `payload` | L5 诊断的事实基础；行为分析 |

### 13.3 成本可观测性设计

`cost_logs` 的字段设计是为了**回答具体的追问**：

| 字段 | 能回答什么问题 |
|---|---|
| `task_type` | 哪个能力最烧钱？ |
| `reasoning` | 开思考的任务占了多少成本？（验证策略表是否合理） |
| `model` | 模型切换前后的成本对比 |
| `prompt_version` | 改提示词有没有导致 token 膨胀？ |
| `cached_tokens` | 上下文缓存命中率如何？（命中价 1/50，是关键优化点） |
| `request_id` | 这次调用属于哪个用户请求？ |
| `estimated_cost` | 分时计价后的真实成本（人民币） |

> **成本埋点必须在网关上做**——这是「唯一收口」的又一收益：不可能有调用漏埋点。

### 13.4 已知的可靠性边界

| 场景 | 当前行为 | 影响 | 是否可接受 |
|---|---|---|---|
| Web 进程挂掉 | Worker 同时停止 | 任务积压，重启后自动继续 | ✅ 单机工具可接受 |
| SQLite 文件损坏 | 无法启动 | 需从备份恢复 | ⚠️ 依赖备份习惯 |
| 向量模型未下载 | 降级关键词检索 | 召回质量下降 | ✅ 功能不缺失 |
| 无 API KEY | 路由到 Mock | 无真实智能 | ✅ 开发/测试可接受 |
| 磁盘满 | 写库失败 | 任务转 dead | ⚠️ 需监控 |

## 结语

本文档 V3.0 的核心主张是四句话：

1. **约束写在结构里，不写在文档里。** 越权防护做进 `BaseRepository`、幂等做进数据库唯一约束、模型调用收口进网关——**靠结构让错误写法写不出来**，比靠文档提醒开发者「记得加 user_id」可靠得多。

2. **便宜的手段放前面，贵的放后面。** L2 五级漏斗、`reasoning` 开关、增量扫描标记——所有智能能力的成本都靠"先用规则/数据库筛，再花大钱推理"压下来。

3. **可降级比高性能重要。** 无 KEY → Mock；无向量模型 → 关键词；模型失败 → 重试 + 死信。**每一处外部依赖都有 Plan B**，所以系统在任何环境下都能跑。

4. **加新东西不该改旧东西。** §7.2 的扩展点设计保证新增 L6 只需改 2 个已有文件（`main.py` + `gateway.py` 策略表），且必须改的这两处都是「注册式」而非「侵入式」。**这是检验解耦是否成功的唯一硬指标。**

> **维护说明**：本文档与代码同步演进。任何涉及依赖方向、收口点、复用抽象、schema 结构的改动，**必须同步更新对应章节**；日常进展记入 `dev_logs/`，架构级决策记入 `dev_logs/设计决策与经验.md`，踩坑复盘记入 `dev_logs/复盘与教训.md`。
