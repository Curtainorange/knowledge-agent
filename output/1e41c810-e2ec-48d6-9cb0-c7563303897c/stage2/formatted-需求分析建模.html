一、建模范围与方法

1.1 项目与选题

项目：认知副驾（Cognitive Copilot）——个人知识学习 AI 智能体。一句话定位：信息系统帮你"管住"已知；认知副驾帮你"照亮"未知，并"逼你"修正。

本次建模的两层范围（两层不同，避免混淆）：

层覆盖范围理由
用例模型项目级：账号偏好、知识资产、阅读接入、L1–L5 认知能力、推送巡检用例模型回答"系统外部可观察行为"，须覆盖完整系统边界，否则边界与参与者无从判断（课件 P09–P12）
对象模型部分：只展开 L2 关联层的三个关键用例（UC-12／UC-13／UC-14）课件要求"选一个关键用例"深入（第 4 课 P54）；对象模型按用例展开才不至于沦为"名词罗列"

为什么选 L2 作为对象模型的展开用例：L2 隐性冲突检测是项目"主动性"的起点（从"存"到"照"的第一跳），且它同时具备状态机、可判真假的数值规则、跨对象一致性、越权边界四类建模难点——最能检验模型是否真正表达了约束，而不是只画了几个框。本报告沿用第 3 课作业已冻结的 Spec 编号（IN-01／OUT-01／BR-L2-01／BR-L2-02／TABLE 8），使三份作业共用一套证据链。

1.3 证据规则（动笔红线）

  1. 范围只能来自项目决策，不能来自"别的产品都有"（第 3 课 P12）。
  2. 无需求依据的类、属性、操作、关系只能删除或列为待确认（第 4 课 P07）。
  3. 规则必须可判真假，含边界值；模糊表述（"内容不能太多"）不算规则（第 3 课 P44）。
  4. 业务变更与模型修订走不同审批路径：模型写错了按已有 BR 改模型；想改规则值则须需求负责人批准并升级 Spec 版本（第 3 课 P53）。

2.3 用例识别与粒度

用例的判据是有价值且完整的用户目标，不是界面动作，也不是内部步骤（第 3 课 P27）。据此先剔除三类伪用例：

  • 界面动作："点击导出按钮""展开全文""拖滑块记录进度"——都是某用例基本流里的步骤。
  • 内部步骤："提取主张""LLM 判定""向量化"——写入相应用例的基本流，不单独成用例。
  • 交互渠道："打开对话工作台"——对话是渠道，不是目标；同一个目标既可由对话触发、也可由功能页触发。

课件要求"先读规则，再看箭头"，关系必须同时满足方向正确与业务条件成立（第 3 课 P35、P37）。下表逐条审查本项目的候选关系，包括被否决的候选——否决同样要给出证据。

参与者泛化（如"学习者"泛化出"重度用户"）不画无已确认的差异权限或目标；同一人可兼任角色不能推出角色继承（第 3 课 P26）
用例泛化（如"生成计划"泛化出"生成周计划／月计划"）不画无差异规则或差异状态；泛化只在出现已确认的差异行为时才建（第 4 课 P39）

审查结论：本模型只保留 1 条关系（UC-20 extends UC-19），其余 8 条候选全部否决并留有证据。关系少不是缺陷——课件反复强调"不是强行拆用例的理由"；强行加 include／extend 只会制造假依赖。

UC-12 扫描隐性冲突

描述项内容
用例名称扫描隐性冲突
用例描述系统对学习者本人的知识库做一次冲突扫描：提取主张、配对、逐对判定，产出带置信度与类型的冲突记录，并按规则过滤低置信结果
参与者学习者（触发）、DeepSeek 模型服务（判定）
触发学习者在对话或冲突页主动发起扫描
前置条件已登录；本人知识库中至少有两条可提取主张的条目
后置条件新增冲突记录（可能为 0 条）均归属本次请求者；本次扫描的每一对判定都写入判定日志，不论最终是否入库
基本操作流程① 学习者发起扫描；② 系统取本人知识库条目，按规则截取待分析范围；③ 系统为每条目提取核心主张，超出上限的部分本轮不参与并记录；④ 系统按语义相似度生成候选主张对，取前 N 对；⑤ 系统调用模型服务逐对判定，得到类型与置信度；⑥ 系统对每对结果执行置信度门槛判定，低于门槛的丢弃（不入库、不推送），达标的保留；⑦ 达标结果写入冲突记录，状态置为"未查看"；⑧ 系统向学习者返回本次扫描摘要（扫描条目数、候选对数、入库冲突数）
可选操作流程②a 可分析条目不足两条 → 直接返回"暂无可比对内容"，不产生任务。③a 提取主张失败（模型不可用）→ 本次扫描标记失败，已产生的部分结果不写入，提示可稍后重试。⑤a 判定调用超时／返回不可解析 → 该对判定记为"未得出"，不写入冲突记录，但写入判定日志以便复核。⑥a 全部候选对均低于门槛 → 本次入库 0 条，正常返回（不是错误）
对应规则BR-01、BR-02、BR-03、BR-06、BR-08

3.5 属性与操作的设计说明

三个高频错误在本模型里被显式避免（第 4 课 P12、P17、P22）：

  1. 不用外键式 ID 替代关系。分析类图里没有 ownerId／claimAId／claimBId 这类字符串字段——对象之间的联系由关联与多重性表达；ID 只在实体内部用于标识自身。
  2. 状态与类型用枚举／值对象，不用裸 String。UserState、ConflictType、Verdict 是枚举；ClaimPair 是值对象（按值相等），因为"同一对主张"必须能被稳定识别（BR-07 的配对键）。
  3. 规则由实体操作保护，不暴露通用 setter。Conflict 上没有 setConfidence / setUserState；取而代之的是：
  • evaluate(confidence)：执行门槛判定（BR-01）；
  • mark(state, by)：状态迁移并核验操作者归属（BR-03）；
  • isConverged()：判断是否已达忽略收敛（BR-02）；
  • belongsTo(l)：归属校验，支撑越权防护。

这四条操作合起来保证：绕过规则的路径在模型上不存在，而不是靠调用方自觉。

作用域：所有属性均为对象作用域（每条冲突的置信度、状态各不相同）；枚举常量为类层次共享；不设静态计数器（应查询统计，第 4 课 P25）。

3.6 对象图验证

类图必须能解释正例与反例，尤其是失败路径（第 4 课 P37、P52）。

  • 正例：u1 拥有条目 i1（含主张 c1、c2），由 u1 发起的扫描 s1 产出冲突 x（归属 u1，置信度 0.70 ≥ 0.5）。x.evaluate(0.70) 保留 → 可查询，符合 AT-01／BR-01。
  • 反例：u2 对 x 调用 mark(ACCEPTED)。x.belongsTo(u2) = false → 拒绝（404/403），x.userState 仍为 UNSEEN、ignoreCount 仍为 0、u1 的数据不变，符合 AT-04／BR-03。

反例能通过，说明"归属校验"不是写在文档里的口号，而是模型里可执行的约束。

5.3 一句话结论

用例模型回答"谁为了什么目标与系统交互"——本项目只有一个人类角色（学习者）与两个外部系统参与者，21 个用户目标级用例，通过关系审查只保留 1 条 «extend»；对象模型回答"哪些对象共同完成目标"——L2 的职责由 Conflict／KnowledgeItem／Claim／ConflictScan／JudgmentLog 五个领域对象分担，规则写在实体操作里而不是服务里，越权与门槛在模型上不可绕过，并由对象图的正例与反例共同验证。
