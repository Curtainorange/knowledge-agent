## 零、答题总则

### 四步答法（所有技术题通用）

1. **一句话结论**——先说这是什么、我的答案是什么，别绕。
2. **我实际怎么做的**——带数字、参数、文件位置。这一步是「真做过」和「背概念」的分水岭。
3. **取舍理由**——为什么选 A 不选 B，说清 B 的代价。
4. **边界**——哪部分我没做、做到什么程度。**主动交代没做的部分，比全说做了更得分。**

### 三档兜底话术（答不上来时说这个，别硬编）

- **会一点**：「这个我做到了可用，但**底层原理是我下一步要补的**——我目前的实现是 X，再往里我就说不准了。」
- **完全不会**：「这块我**没有做**，我知道有两种做法，但选型理由是……所以我把它列进了下一步。」
- **被指出错误**：「您说得对，我这里确实考虑不足。我记下来——这个点我回去按您说的验证一遍。」**认错要快，不要辩解。**

### ⚠️ 四句不能说的话

| 别说 | 改说 |
|---|---|
| 「我用的是最先进的技术」 | 「我选它的理由是……，代价是……」 |
| 「这个我没测过，应该没问题」 | 「这个我还没验过，我登记为下一步」 |
| 「AI 帮我写的」 | 「我全程用 AI 辅助编程，把关方式是 647 项测试 + 逐日日志」 |
| 「数据量上来再说」 | 「瓶颈我登记在案，触发条件是 X，迁移方案是 Y」 |

## 二、第一梯队 · 几乎必问（5 题）

### Q1. 什么是智能体？它和大模型是什么关系？和豆包这类有什么区别？

**【30 秒答法】**
> 大模型提供的是**理解和生成**能力，本身**无状态**——一段输入、一段输出，结束。智能体是在模型外面再包一层：**记忆 + 工具 + 规划 + 自主性**，模型在里面只是一个被调用的组件。类比是：模型是引擎，智能体是车。
> 在我项目里这层是具体的：**记忆**是知识条目、观点主张、589 条行为事件持久化在库里，跨会话累积；**工具**是 10 项能力，不只回答问题，还能写库、改学习计划、同步外部阅读数据；**规划**是把学习目标拆成周计划、检测偏离后重排；**自主**是到点自己扫冲突、推简报。
> 判它是不是智能体，我用四个问题：有没有跨会话持久状态？能不能改变外部世界？会不会主动发起？输出能不能反向改进自己？——豆包类几乎全是「否」，我的系统全是「是」。

**加分补充**：我系统里**模型是插拔的**——我接过两家供应商，运行时可以整体切换，切换时模型名、输出约束、计费口径全部重算。**如果换个模型系统就散架，那它本质上是给某个模型套了个壳。**

**追问：「带联网搜索的模型算智能体吗？」**
→ 那叫检索增强，不算。「它解决的是**知道更多**，没解决**能做什么**和**会不会自己动**」，四个判定问题它最多答对一个，而且取到的是公共知识，不是关于「你」的持久状态。

**红线**：不要说「我的系统是自主智能体」。要说**「规则 + 模型混合」**——能用规则确定的（分流、阈值、计数）一律不交给模型，自主行为目前限于定时扫描和主动推送。

### Q2. RAG 你了解哪些技术？你的检索链路怎么造的？

**【30 秒答法】**
> RAG 完整链路是八个环节：**切分 → 向量化 → 入库索引 → 混合召回 → 融合排序 →（可选重排）→ 组装上下文 → 生成 → 评估**。我逐个说我的做法或取舍：
> **切分**——我的数据源是结构化笔记和划词，天然是条目化单元，所以**以「知识条目」为块，不再二次切分**，这是数据形态决定的，不是没做；
> **向量化**——BAAI/bge-small-zh-v1.5，512 维，L2 归一化，本地 ONNX 离线跑；
> **索引**——统一 VectorStore 接口，两个实现：进程内暴力余弦（默认）、PostgreSQL + pgvector 库内检索；
> **混合召回**——双通道，向量语义为主、关键词 n-gram 兜底，**向量化失败的条目也带文本进索引**，走关键词通道，不丢条目；
> **融合**——用 RRF，按排名融合；
> **重排**——cross-encoder 和 LLM 重排我都了解，**但没上**，单用户 top-5 场景收益小于复杂度和延迟；
> **生成**——输出用 JSON Schema 在服务端约束；
> **评估**——建了金标评估集，20 条语料 16 条查询，护栏 recall@5 ≥ 0.95、recall@1 ≥ 0.75。

**加分补充**：**每个名词我都落到「我怎么做」或者「我为什么不做」。** 尤其「没做的部分」我是主动交代的，不是在藏。

**追问：「为什么不用 LangChain？」** → 见 Q7。

### Q3. 向量模型和向量库你用的什么？为什么这么选？

**【30 秒答法】**
> 向量模型用 **BAAI/bge-small-zh-v1.5，512 维，本地 ONNX 离线部署**，最后做 **L2 归一化**（这是 BGE 官方推荐用法，归一化后余弦相似度等价于点积，计算更省）。
> 选本地的理由有三条：**第一，向量化不依赖模型供应商**——我用的对话模型没有标准 embedding 接口，向量来源必须独立选址；**第二，离线可复现**——不联网也能跑出同一批向量，测试和评估集才稳定；**第三，零调用成本**。
> 向量库我抽象成统一的 VectorStore 接口，两个实现：默认**进程内暴力余弦**，可切 **PostgreSQL + pgvector**，用余弦距离算子 `<=>` 在库内排序取 top-k。
> 还有一个容易被忽略的设计：**每条内容记了「用了哪个模型、多少维」**——换过嵌入模型后旧向量不可比，所以我只增量重建「模型不一致或缺失」的陈旧条目，不盲刷全库。

**追问：「归一化和不归一化差在哪？」**
→ 不归一化时余弦相似度和向量长度纠缠，同一个语义、不同长度的文本分数会漂移；归一化后长度信息被抹掉，只比方向，而且内积等于余弦，索引和计算都更简单。

**追问：「为什么是 512 维不是 768 / 1024？」**
→ 这由模型决定，bge-small 就是 512 维。选 small 而不是 large 的原因是：**单用户几百到几千条的规模，small 的召回已经够用**（评估集 recall@5 实测 ≥ 0.95），而 large 的推理延迟和内存是它的数倍。**这是按规模选的，不是按名气选的。**

### Q4. 大模型输出不可控，你怎么保证它不胡说、格式不坏？

**【30 秒答法】**
> 这个问题我做过对比实验，同一个简报任务各跑 6 次：
> **自由文本 + 本地宽容解析**：3 次里挂 1 次——JSON 真的被写坏了，本地救不回来；
> **让服务端返回 JSON 对象**：5/6——能解析，但**嵌套结构被压平**，结构校验失败；
> **让服务端按给定 Schema 约束**：**6/6 全过**。
> 结论是：**「必须是什么形状」这件事，讲给服务端听，比事后在本地修补可靠。** 本地再多兜底也救不了「语法已经坏掉的 JSON」——兜底能处理格式不规范，处理不了已经写错。
> 还有个工程细节：**Schema 不是手写的，是从数据模型自动派生**的（`model_json_schema()`）。手写 9 份的结果一定是改一处忘一处、和本地校验器漂移。

**加分补充**：不是一刀切——另一家供应商在思考模式下对这类约束有已知兼容弱点，所以最终做成**按供应商能力位分派**：声明支持哪种就用哪种，两边各拿各自最优解。另外 JSON 校验失败还有**一轮修复**：把破损输出和失败原因回灌给模型再要一次，只修一轮。

**追问：「Schema 约束了格式，能约束内容不说错吗？」**
→ **不能，这是两件事。** 格式约束解决的是「解析不了」，内容正确性我靠三层：**检索证据**（生成前把相关条目注入上下文，让它有据可依）、**额度闸门**（注入条数和长度有硬上限）、**置信度与复核对低置信判定二次判定**。而且我明确不追求零幻觉——**我追求的是「错的时候能被发现」**，所以有评估集和自检端点。

### Q5. 你的测试/质量保障是怎么做的？

**【30 秒答法】**
> 647 项自动化测试全绿，从项目第一天的 7 项长上来的。三个特点：
> **第一，全程不联网、不调真实模型**——用确定性的哈希向量和模拟供应商，所以秒级就能全量回归，一天可以跑几十次；
> **第二，测试断言的是行为不是实现**——比如检索护栏直接断言 recall@5 ≥ 0.95，改任何检索参数跑一次就知道变好还是变坏，不用靠感觉；
> **第三，测试是给「已经踩过的坑」立的碑**——我踩过的每一个静默失败，都会补一条测试把它钉住。比如数据库 SQL 绑定参数被框架正则误判那个坑，我加了 14 项不连库的测试，核心断言是「框架识别到的参数集合，必须和代码传进去的完全一致」。

**追问：「647 项测试是不是刷数量？」**
→ 不是。我说两个分布你就知道：网关回退与修复 13 项、向量库与数据库后端 22 项、冲突产出入口 20 项——**每一项都对应一个具体缺陷或一条契约**。而且数量本身不是目的，**目的是让「改坏了」立刻可见**。

**追问：「测试全绿能证明系统没问题吗？」**
→ **不能，这一点我很清醒。** 我踩过最阴的一个坑就是：**构造 SQL 不报错、不连库的测试全绿、失败还被上层降级接住**——表现不是报错，而是检索质量悄悄变差。所以我额外做了两件事：**建评估集看质量数字**，以及**一个自检端点**一次检查数据库、模型、嵌入、向量索引一致性、陈旧向量五项。**测试保证「不报错」，评估保证「没变差」，这是两套东西。**

## 三、第二梯队 · 很可能问（8 题）

### Q6. 混合检索为什么用 RRF，不用加权求和？

**【30 秒答法】**
> 我原来是「分数归一化加权 + 给单通道乘一个 0.1 的硬编码惩罚」。问题是**这两个参数是拍脑袋定的**：向量余弦分数都挤在 0.9 以上的高分区，关键词分数量纲完全不同，归一化之后再乘权重，**有效权重总是偏离我设的值**。
> 改成 RRF 按排名融合：`score = w_vec/(60 + rank_vec) + w_kw/(60 + rank_kw)`。**它对分数尺度不敏感**——只看名次不看分数；而且天生消掉了单通道命中的惩罚系数，因为只出现在一路里的条目自然只加一项。
> 更重要的是：**换了我有依据**——评估集强制要求新融合方式**不得差于旧方案**，旧方案保留为可选项做对照。

**加分补充**：常数 60 是 RRF 论文的常用值，它的作用是**压平头部差距**：排名 1 和排名 2 的差距是 1/61 对 1/62，很接近；主要区分的是「前 5 名」和「第 50 名」。

**追问：「这两个通道各自解决什么？」**
→ 向量通道管**语义相近但字面不同**（「拖延症」和「执行力差」）；关键词通道管**字面必须精确命中**（人名、术语、代码符号、「B+树」）。第二类恰恰是向量的弱项，所以两路互补，不是冗余。

### Q7. 为什么不用 LangChain / Celery / Redis / 向量数据库这些现成框架？

**【30 秒答法】**
> 我的判断是：**在这个规模上，引入框架的复杂度大于它带来的收益**，而且我有明确的迁移路径。
> **编排层**：我的链路是固定的（检索 → 组装上下文 → 约束生成 → 校验），LangChain 的价值在灵活编排，而我需要的是**确定性和可调试**——出问题时我要能一眼看到是哪一环。另外我不希望业务逻辑被框架版本牵着走。
> **异步**：没用 Celery/Redis，用了**项目内一个最小任务框架**——幂等键唯一约束、退避重试、死信、stale 回收，全都落在**已有的关系库**里。好处是**零额外基础设施**，而且任务状态和业务数据在一个事务边界内，不用处理「Redis 里有、库里的没有」这类一致性问题。代价是单进程轮询、不适合高并发——**这个代价我认，因为我是单用户规模。**
> **向量库**：我没上独立向量数据库，而是抽象了 VectorStore 接口，内存实现和 pgvector 各一份。**因为接口在，迁移成本已经被压到「换一个开关」**。

**追问：「那你不是造轮子吗？」**
→ 三个自研里只有任务框架算真造轮子，**约 200 行**；而且我造它不是因为想造，是因为**它的可靠性语义（幂等键、死信、stale 回收）必须和我的业务幂等语义对齐**——用现成的反而要写适配层。检索和向量库那两处，我是**抽象接口 + 两个实现**，这不是造轮子，是留迁移口。

### Q8. 为什么用 SQLite？数据量大了怎么办？

**【30 秒答法】**
> **SQLite 对单人规模是负复杂度的选择**：零运维、零安装、单文件、可整库备份，而且 SQLAlchemy 已经把数据库方言差异挡住了——`database_url` 改成 PostgreSQL 连接串就能切。
> 我知道它的边界：**写并发弱**（库级锁）、不适合多 worker。所以我做了两件兜底：**第一，所有慢操作走异步任务，不占请求线程**；**第二，所有查询走 ORM 或参数化 SQL，没有写死的方言特性**——这也让我切 PG 时不用改业务代码。
> 数据量上来先撞到的不是 SQLite，是**向量检索规模**和**冲突候选对的平方级复杂度**，这两个我都登记在案，迁移方案（切 pgvector 后端、用向量近邻缩候选）已经实现或已设计。

**追问：「那多用户怎么办？」**
→ 多用户我现在**没做**，这是我主动划的边界。但架构上没有堵死：仓储层**结构性强制 user_id 隔离**（不是靠每个查询自觉带条件），所以从单用户走向多用户主要是加配额和调度的活，不是重写数据层。

### Q9. 异步操作怎么做的？用户会不会干等？

**【30 秒答法】**
> 不会干等。链路是：**先发一张「进行中」的卡，后台跑完就地改写那条消息**。用户重新打开页面看到的是最终结果，而不是一条永远转圈的卡。
> 三个细节值得说：
> **第一，异步回合不引入新表、也不引入消息队列**——复用项目已有的任务框架（自带幂等、重试、死信），**状态直接落在会话消息上**。这样结果不需要另找地方存。
> **第二，同步和异步共用同一段执行逻辑**——异步只改「在哪儿跑」，不改「跑什么」。不这么做，同一个能力迟早会有两套实现并静默分叉。
> **第三，没有后台进程时自动退回同步执行**，否则那张卡会永远转圈，用户既看不到结果也等不到失败。
> 另外后台进程原本是固定间隔轮询，我改成**可被唤醒的事件等待**——否则「异步」会退化成纯等待。

**追问：「任务失败了怎么办？」**
→ 有三级：**退避重试**（2 的 n-1 次方，最多 3 次）→ **死信**（超过上限转 `dead`，保留 last_error 现场，不再自动重试）→ **卡片落成明确的失败卡并给出重试落点**。还有 `running` 超时回收（10 分钟），防止进程崩溃后任务卡死。

### Q10. 冲突检测怎么做？复杂度怎么控？阈值怎么定？

**【30 秒答法】**
> L2 冲突检测的核心难点是**两两比较是平方级的**——1000 条主张就是 50 万对，全送模型不现实。所以我做的是**先向量后模型**的漏斗：
> **第一层，向量距离带筛候选**：算主张向量之间的余弦，**太近（> 0.95）说明是重复表述，太远（< 0.35）说明根本无关，两端都排除**，只留中间带——实测「相关但立场不同」的主张对多落在 0.4~0.85。
> **第二层，硬上限闸门**：单次扫描最多送 **20 对**给模型判定，这是成本闸门，超出的下轮再排。
> **第三层，置信度过滤**：模型给出的置信度低于 **0.5** 直接丢弃。
> **第四层，低置信复核对判定质量把关**：置信度落在 **0.35~0.75** 的「矛盾」判定，自动换角度重判一次（每轮预算最多 5 次）——**下沿是被丢弃判定的翻案候选，上沿是勉强入库的判定**，高置信不复核。
> 效果我做了真实评测：**关系判定准确率 0.83，矛盾判定的准确率、召回率、F1 都是 1.0**，而且这是我给的回归承诺基线，后续迭代不低于它。

**追问：「阈值 0.35 / 0.95 是怎么定的？」**
→ **不是拍的，是看数据定的。** 我先跑了一批人工看过的主张对，观察它们的余弦分布：立场相反但主题相同的对集中在 0.4~0.85，>0.95 的基本是同义重复（同一句话换个说法），<0.35 的是不同主题。参数是**按实测分布切的**，而且全在配置里，可以随数据校准。

**红线**：不要说「阈值是经验值」。要说**「按实测分布校准，并且参数可配置」**。

---

### Q11. 你怎么知道检索质量变好还是变坏？评估集怎么建的？

**【30 秒答法】**
> 我建了一个金标评估集：**20 条语料、16 条查询**，然后设护栏线——**recall@5 不低于 0.95、recall@1 不低于 0.75**，写成断言。这样以后改任何检索参数，**跑一次测试就知道是变好还是变坏，不用靠感觉**。
> 建的方式是人工标注：我先准备一批有明确目标的查询，逐条标出**应该被召回的条目**，再让检索跑一遍算命中率。语料是我自己真实的知识条目，不是通用数据集——**这样测的是我的真实场景，不是别人的场景。**

**加分补充**：护栏还加了一条**相对约束**：新的融合方式**不得差于旧的加权方式**。这比一个绝对阈值更有意义，因为它防的是「改坏了但还在及格线上」。

**追问：「20 条语料够吗？」**
→ **不够，只能说够用。** 它的作用不是给出一个精确的分数，而是**当一个回归哨兵**——如果某次改动让召回率明显掉了，20 条也能立刻看出来。要更细的评估就得扩到几百条并分层标注，这是我下一步的事，**我现在不假装它是个严谨的 benchmark。**

---

### Q12. 安全和多用户：密码怎么存、接口会不会被滥用？

**【30 秒答法】**
> 认证是 **JWT，HS256，Access Token 2 小时、Refresh Token 7 天**，前端统一管理会话和续期。
> 密码**只存 PBKDF2 派生值，迭代 60 万次**（对齐 OWASP 推荐量级），不存明文、不可逆推。
> 防滥用做了两层限流：**登录按账号 5 次失败 / 5 分钟窗口、锁 5 分钟**；**按来源 IP 20 次**——IP 阈值故意放宽，因为 NAT 后面的正常用户不该被连带。注册另加 IP 限流（10 次），因为**每次注册都要跑 PBKDF2，是个可被利用的 CPU 消耗点**。
> 数据隔离是**结构性的**：仓储层强制带 `user_id` 条件，不是靠每个查询自觉。

**追问：「第三方凭据怎么保护的？」**
→ **微信读书的 Key 和模型 API Key 一律走配置注入、不进代码、不进仓库**，`.gitignore` 覆盖了 `.env` 和书籍原文件。Key 等同账号访问凭据，我按凭据标准对待。

**追问：「多用户能支持吗？」**
→ 目前**不支持，我主动划的边界**：限流是进程内计数、任务框架是单进程轮询、SQLite 写并发弱。所以现在的定位是**单人自托管的个人系统**，不是多租户 SaaS。要支持多用户，改的是配额和调度层，数据层因为有隔离约束不用动。

### Q13. 大模型成本怎么控？

**【30 秒答法】**
> 四个闸门：
> **第一，按任务类型开关思考模式**——配表驱动。深度推理、冲突判定、因果归因、复核裁判开思考，**标准对话、意图分流、规划、简报全部关**。因为它们不是深度推理任务，而思考模式下单价显著更高；尤其**分流每一轮都要跑**，必须关。
> **第二，条数和长度硬闸门**——注入上下文的条目有上限（比如 L3 单次最多 60 条、冲突上下文最多 3 条），模型输出的追问数有上限。
> **第三，便宜的向量先筛，别让贵的模型瞎看**——冲突检测先用向量把 50 万对压到 20 对。
> **第四，记账按实际服务的模型取价**——回退发生时是备用供应商在干活，按主供应商单价记账会让整笔错记；另外**缓存命中的输入价只有未命中的五十分之一**，我的提示词前缀是稳定的，这一项不能忽略，不然成本会估高一个量级。

**追问：「你实际花了多少钱？」**
→ 单次调用级别都有日志（token 数、耗时、模型名、是否回退），累积成本可查。日常个人使用量级很小，**真正的成本教训不是花多了，而是「差点按错误的单价记账」**。

## 四、第三梯队 · 有难度、也容易变成陷阱（8 题）

### Q14. 分块（chunking）怎么切的？为什么不做语义切分？

**【30 秒答法】**
> 我**没有二次切分**——我的数据源是结构化笔记、划词想法和书评，**本身已经是条目的粒度**，直接以「知识条目」为块。
> 不做的理由是：**切分是为了解决「长文档超上下文」**，而我的条目平均只有几百字，不存在这个问题；反而**二次切分会把一条完整的观点切断**，让「这条主张是什么」变得不可判定——而我的 L2 冲突检测恰恰要判整个条目的主张。
> 我知道业界有定长、递归、语义切分三种，也知道书籍通读那一块**必须切**——那里我是按章节和分块提要点再做汇总，跟条目这条路是分开的。

**加分补充**：**「没做」和「不需要做」是两回事，我会分清是哪种。** 条目这条路是不需要；重排（rerank）那条是「做了收益不划算」，我会说清区别。

---

### Q15. 为什么没做重排？查询改写呢？HyDE 呢？

**【30 秒答法】**
> 这三个我都了解，**都是主动不做的，理由各自不同**：
> **重排（cross-encoder / LLM rerank）**——它能把 top-20 精排到 top-5，但我的场景是**单用户、top-5 结果、语料几百到几千条**，向量加关键词的两路召回已经能进护栏（recall@5 ≥ 0.95），**再加一个 cross-encoder 是增加延迟和复杂度换一点点收益**。等语料上万、或者 top-5 不够用了我再上。
> **查询改写**——我的查询是**短意图**（「帮我找那个讲拖延的」「记一下…」），不是长的自然语言问题，改写的收益不明显。而且我有一层更前置的处理：**意图路由先把一句话变成「能力 + 参数」**，命令式的说法走本地确定性规则、零模型调用，这一步已经把查询规整过了。
> **HyDE**——用「假设答案」的向量去检索，原理我清楚，但同样服务的是长问题召不准的场景，**我的短查询用不上**。

**红线**：**不要背名词**。老师问哪个就说哪个的**取舍**。说不出取舍的，就说「这个我了解原理、没实现」。

---

### Q16. 为什么没给向量建 ANN 索引？HNSW 和 ivfflat 了解吗？

**【30 秒答法】**
> 我知道这两个：**ivfflat 是聚类分桶**，先用 k-means 把向量聚成若干个桶，查询时只扫最近的几个桶，**建索引需要在数据写入之后**（要先有数据才能聚类）；**HNSW 是分层可导航小世界图**，查询时在图上做贪心搜索，精度和速度都更好，代价是**内存占用和建索引时间更大**。
> 但我**没有建**，理由是：**我是全表顺序扫描 + 余弦距离算子，单用户几百条无感**；而 ANN 是**近似**最近邻——**在几百条的规模上，它带来的近似误差大于它省下的时间，是负优化。** 上万条才值得建，而且那时候要在数据写入之后建，否则聚类是空的。

**加分补充**：我现在用的是 `<=>` 余弦距离算子在库内 `ORDER BY ... LIMIT k`，把排序下推到数据库。**「知道什么时候不该用」比「知道怎么用」更重要。**

### Q17. pgvector 后端真机验证了吗？

**【30 秒答法】（这题必须诚实）**
> **还没有，这是我明确登记在案的欠账。** 现在的状态是：SQL 契约已经用「不连真库的测试」钉住了——**14 项测试断言绑定参数集合与代码传参完全一致**；但**「真的能取到近邻」「向量字面量能被扩展的输入函数解析」「建表和扩展安装在真库上跑得通」这三件，只有连上真实 PostgreSQL 才算验过**。
> 我也说清为什么它危险：我这个后端曾经踩过一个坑——**SQL 里写了 `:vec::vector` 这种类型强转，框架识别绑定参数的正则把它认成了 `ve`，构造时不报错、不连库的测试全绿、失败还被上层降级成「只用关键词通道」接住**。结果**不是报错，而是检索质量悄悄变差。** 所以我把真机验证列成下一步第一项，切后端时按清单走一遍。

**加分补充**：默认后端是**内存实现**，所以 pgvector 是 **opt-in**，不验也不影响现在演示。这个边界我会主动交代。

### Q18. 降级/兜底会不会把 bug 掩盖掉？这是不是设计缺陷？

**【30 秒答法】（这是老师最可能拿来压难度的一题，要正面接）**
> **会，这是我吃过最深的教训，所以我把它当成一等风险在处理。**
> 我最危险的一个缺陷就是这种形状：**构造 SQL 不报错 → 不连库的测试全绿 → 调用失败被上层兜底接住、降级成「只有关键词通道」**。三个条件叠在一起，表现不是报错，而是**检索质量悄悄变差**。同类还有两个：**改了配置没生效**（配置只在进程启动时读，旧进程还在跑旧配置），**向量每轮重算却从没被读过**（写和读各写了一套文本处理逻辑，改一个常量就会静默分叉）。
> 所以我的原则是：**第一，失败要可见**——重试、回退、降级都记日志，并且落事件可查；**第二，容错不能伪装成成功**——**模拟实现永远不作为真实失败的回退目标**，否则「模型挂了」会被伪装成「模型答了」，这是最危险的假象，因为它让你带着错误结论继续走；**第三，用质量指标兜住**——测试保证「不报错」，评估集保证「没变差」，这是两套东西。
> 我也承认：**容错的可观测性现在还不够**——回退和降级目前主要在日志里，界面和监控看不到「这一周有几次是靠备用救回来的」。我已经把它列进下一步。

**加分句**：**「不报错，不等于跑通了。」** 这句是我这 24 天最大的收获。

### Q19. 模型幻觉怎么防？

**【30 秒答法】**
> 我不追求零幻觉，**我追求的是「错的时候能被发现、并且错的代价可控」**，具体四层：
> **第一，让它有据可依**——生成前把检索到的相关条目注入上下文，而不是让它自由发挥；证据不足时宁可不生成。
> **第二，给它的输出留后路**——凡是要进库、要影响计划的结论，都过结构化校验和业务校验；判不出来的落「待确认」而不是硬猜。
> **第三，给它一个能被推翻的机制**——冲突判定有置信度、低置信会复核；我标记某个冲突是误报，同类冲突以后就不再算（被忽略 3 次就收敛该类推荐），**这是闭环**。
> **第四，让它说实话**——诊断和归因都要求给出**依据链**，不只给结论，这样我能核。
> 边界也说清：**L2 判定我做了真实评测（P/R/F1 = 1.0），但这个评测集是我自己标的，规模有限**，不能等同于通用 benchmark。

**【30 秒答法】**

> 一个要说明的边界：**模型调用这一段确实是外部服务**，要做到完全不外传就得换本地大模型——那是下一步可以考虑的选项，不是现在的能力。

### Q21. 多轮对话的上下文和指代你怎么处理？

## 六、概念速查卡（万一被要求背定义）

| 概念 | 一句话 |
|---|---|
| RAG 八环节 | 切分 → 向量化 → 入库索引 → 混合召回 → 融合排序 →（重排）→ 组装上下文 → 生成 → 评估 |
| 余弦相似度 | 只比方向不比长度；归一化后等价于内积 |
| RRF | `Σ w/(k + rank)`，k 常取 60；对分数尺度不敏感、免调参 |
| ivfflat | 聚类分桶的近邻索引，**需数据写入后再建**（要先有数据聚类） |
| HNSW | 分层可导航小世界图，精度高、查询快，内存与建索引成本更大 |
| ANN 近似 | 近似最近邻，规模小的时候是负优化 |
| chunking | 定长 / 递归 / 语义切分；解决长文档超上下文 |
| 幂等键 | 唯一约束入库，重复入队被数据库挡回，不是靠代码判重 |
| 退避重试 | 间隔按 2 的 n-1 次方增长，避免失败任务互相踩踏 |
| 死信 | 超过重试上限转 `dead` 并保留错误现场，不再自动重试 |
| JWT | 无状态令牌；Access 2h、Refresh 7d |
| PBKDF2 | 密码派生，迭代 60 万次，对齐 OWASP 推荐量级 |
| Schema 约束 | 在服务端约束输出形状，比本地事后修补可靠（实测 6/6 vs 3 挂 1） |
| 温度 / 思考模式 | 按任务配表开关；思考模式更贵，只在深度推理类任务开 |

## 七、临场上桌前的三条

1. **先答结论，再给证据。** 老师问「为什么」，第一句就是答案，不要从背景讲起。
2. **每个答案都带一个参数或数字。** 「阈值 0.35」比「我设了个阈值」可信十倍。
3. **主动交边界。** 每答完一个技术点，最后补一句「这块我没做 / 只做到 X」——**这比多讲一个技术点更能加分**，因为它证明你知道自己站在哪里。
